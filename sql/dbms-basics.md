## Что такое СУБД и какие они бывают?

**Коротко.** База данных — организованный набор данных. СУБД — программа,
которая ими управляет: хранит, обеспечивает конкурентный доступ, целостность и
восстановление после сбоев.

Деление на «реляционные и нереляционные» — грубое, но с него обычно начинают:

- **Реляционные (SQL)** — данные в таблицах, связи через ключи, есть схема и
  транзакции: PostgreSQL, MySQL, MS SQL Server, Oracle, SQLite.
- **Нереляционные (NoSQL)** — общего определения нет, это несколько разных
  семейств:
  - документные — MongoDB;
  - ключ-значение — Redis, etcd;
  - колоночные — ClickHouse, Cassandra;
  - графовые — Neo4j.

**Подвох.** Redis обычно называют кешем, и это верно по типичному применению, но
формально это key-value СУБД с персистентностью. Точно так же ClickHouse
использует SQL, но реляционной СУБД общего назначения не является — он
аналитический и колоночный.

**Глубже.** Для Python-разработчика полезно различать сущности PostgreSQL,
которые часто путают: **кластер** (один инстанс сервера) содержит несколько
**баз данных**, каждая база — несколько **схем** (`public` по умолчанию), а уже
схема содержит таблицы. Соединение открывается к конкретной базе, и запросом
перейти в другую базу нельзя.

## Что такое таблица, строка и столбец?

**Коротко.** Таблица — набор данных в виде строк и столбцов. Столбец (поле)
задаёт имя и тип, строка (запись) — один экземпляр.

В терминах реляционной модели у этого есть формальные синонимы, которые могут
спросить отдельно:

| Практический термин | Термин реляционной модели |
|---|---|
| таблица | отношение (relation) |
| строка | кортеж (tuple) |
| столбец | атрибут (attribute) |
| тип и множество допустимых значений столбца | домен (domain) |
| количество столбцов | степень (degree) |
| количество строк | кардинальность (cardinality) |

## Что такое сущности и связи?

**Коротко.** Сущность — объект предметной области, о котором хранятся данные
(клиент, заказ, товар). Связь — отношение между сущностями.

Три вида связей и то, как они реализуются:

- **Один к одному (1:1)** — внешний ключ с ограничением `UNIQUE` в одной из
  таблиц. Встречается редко, обычно при выносе редко используемых полей.
- **Один ко многим (1:N)** — самая частая: внешний ключ на стороне «многих».
  У клиента много заказов → `orders.customer_id` ссылается на `customers.id`.
- **Многие ко многим (M:N)** — напрямую в реляционной модели невозможна, нужна
  **связующая таблица** с двумя внешними ключами. Студенты и курсы →
  `enrollments(student_id, course_id)`.

```sql
CREATE TABLE enrollments (
    student_id int REFERENCES students(id),
    course_id  int REFERENCES courses(id),
    PRIMARY KEY (student_id, course_id)   -- составной ключ
);
```

**Подвох.** Вопрос «как реализовать многие-ко-многим» задают почти всегда, и
ответ «через третью таблицу» стоит сразу дополнять тем, что её первичный ключ —
составной из двух внешних, и что в неё удобно класть атрибуты самой связи
(дату зачисления, оценку).
