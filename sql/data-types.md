## В чём разница между `CHAR` и `VARCHAR`?

**Коротко.** `CHAR(n)` — строка фиксированной длины: короткие значения
дополняются пробелами до `n`. `VARCHAR(n)` — переменной: хранится ровно столько,
сколько занимает значение, а `n` задаёт верхний предел.

```sql
CREATE TABLE t (a CHAR(10), b VARCHAR(10));
INSERT INTO t VALUES ('ab', 'ab');
-- a хранится как 'ab        ' (дополнено пробелами)
-- b хранится как 'ab'
```

**Подвох.** Формулировка «`CHAR(10)` может хранить только строки длиной ровно
10» неверна — более короткие он хранит прекрасно, просто дополняет пробелами.
А при **превышении** длины `CHAR` и `VARCHAR` ведут себя одинаково: выдают
ошибку. Разница между ними — в способе хранения и в семантике конечных
пробелов, а не в том, что «влезает».

**Глубже.** Для PostgreSQL это важный практический вопрос: в нём **`char(n)` не
даёт никакого выигрыша в производительности** и официально не рекомендуется.
`char(n)` там обычно даже медленнее из-за дополнения пробелами. Рекомендация
самой документации Postgres — использовать `text` или `varchar` без указания
длины, а ограничение длины задавать через `CHECK`, если оно действительно
бизнес-требование. В MySQL `CHAR` может быть немного быстрее на очень коротких
полях фиксированной длины.

## Какие числовые типы использовать?

| Тип | Когда |
|---|---|
| `SMALLINT` / `INTEGER` / `BIGINT` | Целые. `INTEGER` до ~2,1 млрд, дальше `BIGINT` |
| `NUMERIC(p, s)` / `DECIMAL` | Точная десятичная арифметика |
| `REAL` / `DOUBLE PRECISION` | Приблизительные вычисления (IEEE 754) |

**Подвох.** «Почему деньги не хранят во `FLOAT`?» — тот же вопрос, что и про
[`float` в Python](../python/float.md): двоичная дробь не может точно
представить `0.1`, и на суммировании миллионов операций ошибка накапливается.
Для денег — `NUMERIC(12, 2)` или целое число копеек.

## Как хранить дату и время?

| Тип | Что хранит |
|---|---|
| `DATE` | Только дату |
| `TIME` | Только время |
| `TIMESTAMP` | Дату и время **без** часового пояса |
| `TIMESTAMPTZ` | Дату и время **с** учётом часового пояса |

**Подвох.** Для PostgreSQL почти всегда правильный выбор — `TIMESTAMPTZ`.
Вопреки названию, он не хранит пояс: он приводит значение к UTC при записи и
разворачивает обратно в пояс клиента при чтении. `TIMESTAMP` же хранит «голое»
время без привязки, и два сервера в разных поясах поймут его по-разному.

## Что такое `JSONB` и чем он отличается от `JSON`?

**Коротко.** PostgreSQL. `JSON` хранит текст как есть, `JSONB` — разобранное
двоичное представление. Для работы почти всегда нужен `JSONB`.

```sql
CREATE TABLE events (id serial, payload JSONB);

SELECT payload->>'user_id' FROM events;          -- значение как текст
SELECT * FROM events WHERE payload @> '{"type": "click"}';   -- содержит

CREATE INDEX idx_payload ON events USING GIN (payload);
```

`JSONB` теряет порядок ключей и дубликаты, зато его можно индексировать (GIN) и
искать по содержимому. Без GIN-индекса такие запросы сканируют таблицу целиком —
см. [Индексы](indexes.md).

**Подвох.** `JSONB` — не повод отказываться от нормализации. Он хорош для
действительно неструктурированных данных (payload вебхука, настройки), но
поиск и джойны по полям внутри JSON заметно дороже, чем по обычным столбцам.

## Что ещё стоит знать

- **`BOOLEAN`** — в PostgreSQL полноценный тип; в MySQL это синоним `TINYINT(1)`,
  и `TRUE` там буквально равен `1`.
- **`UUID`** — отдельный тип в Postgres (16 байт), а не строка на 36 символов.
- **`ARRAY`** — расширение Postgres: `integer[]`, с поиском через `ANY` и
  GIN-индексом.

  ```sql
  SELECT ARRAY[1, 2, 3] || ARRAY[4, 5];  -- {1,2,3,4,5}
  ```

- **`ENUM`** — перечисление; в Postgres добавление значения требует `ALTER TYPE`,
  поэтому часто предпочитают справочную таблицу с внешним ключом.

  ```sql
  CREATE TYPE mood AS ENUM ('sad', 'ok', 'happy');
  ```
