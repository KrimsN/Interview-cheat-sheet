## Strategy и Template Method

**Коротко.** Оба выделяют изменяемый шаг алгоритма. Strategy выносит его в
отдельный объект и подменяет **композицией в рантайме**; Template Method
фиксирует скелет алгоритма в базовом классе и оставляет шаги наследникам —
подмена происходит **наследованием на этапе компиляции**.

```python
# strategy: политика передаётся снаружи и меняется на лету
def checkout(cart, pricing):          # pricing — любая функция/объект
    return pricing(cart.total)

checkout(cart, lambda t: t * 0.9)
```

Template Method удобен, когда порядок шагов действительно общий и его нельзя
нарушать (подключиться → прочитать → закрыть). Цена — жёсткая связь с базовым
классом и все проблемы наследования из
[связей между классами](oop-relations.md).

**Подвох.** «Стратегия — это же просто передать функцию?» В языках с функциями
первого класса — да, и это правильная реализация паттерна, а не его отсутствие.
Отдельный класс нужен, когда у стратегии есть состояние, несколько методов
или её нужно конфигурировать.

**В Python:** функции как объекты, `functools.partial`, `key=` в сортировке —
[функциональный стиль](../python/functional-programming.md) и
[сортировка](../python/sorting.md).

## Observer

**Коротко.** Observer задаёт зависимость «один ко многим»: при изменении
состояния субъекта все подписчики уведомляются автоматически. Основа
событийных моделей, UI-биндингов, брокеров сообщений в миниатюре.

```python
class EventBus:
    def __init__(self) -> None:
        self._subs: dict[str, list] = {}

    def subscribe(self, topic: str, handler) -> None:
        self._subs.setdefault(topic, []).append(handler)

    def publish(self, topic: str, payload) -> None:
        for handler in self._subs.get(topic, []):
            handler(payload)          # порядок вызова — деталь реализации
```

**Подвох.** Три классические проблемы: (1) исключение в одном подписчике
обрывает уведомление остальных, если не изолировать вызовы; (2) подписчики,
которых забыли отписать, живут вечно — утечка памяти (lapsed listener);
(3) поток управления становится неявным — по коду не видно, что произойдёт
после `publish`, и отладка усложняется.

**Глубже.** Порядок уведомления подписчиков в общем случае не гарантирован —
опираться на него нельзя. Если подписчик во время уведомления подписывается
или отписывается, наивная итерация по списку падает или пропускает элементы;
поэтому уведомляют по копии списка. Для решения утечки применяют слабые
ссылки на подписчиков.

**В Python:** слабые ссылки и жизненный цикл объектов —
[управление памятью](../python/memory-management.md); асинхронные подписчики
и групповая обработка ошибок — [`asyncio.TaskGroup`](../python/asyncio-taskgroup.md)
и [группы исключений](../python/exception-groups.md).

## Command, Chain of Responsibility, State

**Коротко.** Command упаковывает вызов (получатель + метод + аргументы) в
объект — отсюда очереди задач, отмена операций, журнал действий, повтор.
Chain of Responsibility передаёт запрос по цепочке обработчиков, пока кто-то
не обработает — так устроены middleware и фильтры. State выносит поведение,
зависящее от состояния, в отдельные объекты-состояния, заменяя большой
`switch` по полю `status`.

```python
# chain of responsibility: middleware вокруг обработчика
def with_auth(next_handler):
    def handler(req):
        if not req.get("token"):
            return {"status": 401}
        return next_handler(req)
    return handler
```

**Подвох.** Command часто путают с любым «объектом-действием». Признак
настоящего паттерна — наличие второй операции (`undo`, повтор, сериализация
в очередь); без неё это просто функция.

**Глубже.** State и Strategy структурно идентичны, но State предполагает,
что объекты состояний **знают о переходах** и сами переключают контекст,
а стратегии друг о друге не знают и выбираются снаружи. Формализованный
вариант State — конечный автомат с явной таблицей переходов; для сложных
жизненных циклов (заказ, платёж) таблица переходов надёжнее россыпи `if`.

**В Python:** замена `switch` по типу и структуре данных —
[match / case](../python/pattern-matching.md); замыкания для цепочек —
[область видимости и замыкания](../python/scoping-closures.md).

## Iterator

**Коротко.** Iterator даёт последовательный доступ к элементам коллекции,
не раскрывая её внутреннее устройство. В большинстве современных языков это
встроенная возможность языка, а не паттерн, который пишут руками.

Ценность формулировки GoF в том, что она отделяет **обход** от **хранения**:
один и тот же алгоритм работает с массивом, деревом, файлом и сетевым потоком.
Ленивый итератор дополнительно снимает требование держать всю коллекцию
в памяти.

**Подвох.** Изменение коллекции во время итерации — неопределённое поведение
почти везде: либо исключение, либо пропущенные и продублированные элементы.
Правильный приём — итерировать по копии или собирать изменения и применять
их после обхода.

**В Python:** протокол `__iter__`/`__next__`, разница iterable и iterator —
[итератор](../python/iterators.md); генераторы и `yield from` —
[генератор](../python/generators.md); готовые ленивые блоки —
[`itertools`](../python/itertools.md).

## Mediator

**Коротко.** Mediator убирает прямые связи между множеством компонентов,
заставляя их общаться только через центральный объект-посредник — компоненты
знают о медиаторе, но не знают друг о друге.

```python
class DialogMediator:
    def __init__(self) -> None:
        self.submit_button = Button(on_click=self.handle_submit)
        self.name_field = TextField(on_change=self.handle_change)

    def handle_change(self, value: str) -> None:
        self.submit_button.enabled = bool(value)   # поля влияют друг на друга

    def handle_submit(self) -> None:
        print("отправлено:", self.name_field.value)
```

**Подвох.** Mediator путают с Facade и Observer, потому что все трое «убирают
связанность через посредника». Разница в направлении общения: Facade даёт
один упрощённый интерфейс к подсистеме **в одну сторону** (клиент → подсистема,
подсистема о клиенте не знает); Observer уведомляет подписчиков **без
обратной связи** (subject не ждёт ответа от них); Mediator организует
**двустороннее** общение множества равноправных компонентов друг с другом
через один хаб — компоненты и посылают события медиатору, и реагируют на
события от него.

**Глубже.** Плата за убранную связанность — медиатор со временем разрастается
и превращается в god object, знающий обо всех деталях каждого компонента.
Работает, пока в диалоге/форме, которую он координирует, ограниченное число
участников; для действительно сложной маршрутизации сообщений уместнее
event bus (см. [Observer](#observer)) с более слабой связанностью.

## Visitor

**Коротко.** Visitor добавляет новую операцию над иерархией классов, не
изменяя сами классы — через двойную диспетчеризацию: элемент вызывает
`accept(visitor)`, а тот сам решает, какой метод посетителя вызвать в
зависимости от типа элемента.

```python
class Circle:
    def accept(self, visitor): return visitor.visit_circle(self)

class Square:
    def accept(self, visitor): return visitor.visit_square(self)

class AreaVisitor:
    def visit_circle(self, c): return 3.14 * c.radius ** 2
    def visit_square(self, s): return s.side ** 2

shapes = [Circle(radius=2), Square(side=3)]
total = sum(shape.accept(AreaVisitor()) for shape in shapes)
```

Это прямая иллюстрация Open/Closed из [SOLID](solid.md): чтобы добавить
операцию `Perimeter`, пишут новый visitor и не трогают `Circle`/`Square`.

**Подвох.** Trade-off обратный обычному полиморфизму: добавить **новую
операцию** — дёшево (один новый visitor), а добавить **новый тип элемента**
в иерархию — дорого (нужно дописать метод `visit_...` во все существующие
visitor'ы). Если в системе типы элементов стабильны, а новые операции
появляются часто — Visitor выигрывает; если наоборот — он усложняет код без
пользы, и обычный полиморфизм проще.

**В Python:** двойную диспетчеризацию по типу аргумента без ручного if/elif
даёт `functools.singledispatch` — см.
[декораторы](../python/decorators.md).

## Repository и Unit of Work

**Коротко.** Не из каталога GoF, но спрашивают часто. Repository — коллекция
доменных объектов с интерфейсом в терминах домена (`orders.by_customer(id)`),
скрывающая способ хранения. Unit of Work отслеживает изменения объектов за
время бизнес-операции и сохраняет их одной транзакцией.

Смысл Repository — [инверсия зависимостей](solid.md): домен объявляет
интерфейс, инфраструктура его реализует; в тестах подставляется in-memory
реализация. Смысл Unit of Work — атомарность: либо применились все изменения
операции, либо ни одного.

**Подвох.** Репозиторий, повторяющий CRUD базы (`save`, `update`, `delete`
плюс `find_by_*` на каждое поле), — обёртка ради обёртки. Он должен говорить
языком предметной области и возвращать доменные объекты, а не строки таблицы.

**В SQL:** транзакции и уровни изоляции, на которых стоит Unit of Work, —
[ACID и изоляция](../sql/acid-and-null.md); стоимость запросов, которые
прячет репозиторий, — [индексы](../sql/indexes.md).
