## Какие антипаттерны и запахи кода вы знаете?

**Коротко.** Запах кода — не ошибка, а симптом: код работает, но его дорого
менять. Антипаттерн — типовое решение, которое выглядит разумным и системно
приводит к проблемам. Разница в масштабе: запах локален, антипаттерн — про
устройство системы.

Часто спрашиваемые запахи:

- **God object / God class** — класс, который знает и делает всё; нарушает
  [SRP](solid.md), меняется по любому поводу.
- **Long method** — метод, который не помещается на экран и содержит несколько
  уровней абстракции сразу.
- **Feature envy** — метод больше работает с данными чужого объекта, чем
  своего: логику надо переселить туда, где данные.
- **Shotgun surgery** — одно изменение требует правок в десятке файлов;
  обратная сторона — **divergent change**, когда один класс меняется по
  множеству независимых причин.
- **Primitive obsession** — предметные понятия выражены строками и числами
  (`str` для email, `float` для денег) вместо типов, которые хранят инвариант.
- **Flag argument** — булев параметр, переключающий ветку внутри функции;
  это control coupling, обычно нужны две функции.
- **Магические числа и строки** — литералы без имени, разбросанные по коду.
- **Swallowed exception** — пустой `except`/`catch`, который прячет ошибку.

Антипаттерны уровня системы: **spaghetti code** (нет структуры, поток
управления непредсказуем), **big ball of mud** (нет границ между модулями),
**anemic domain model** (объекты без поведения, вся логика — в сервисах),
**lava flow** (мёртвый код, который боятся удалять), **golden hammer** (одно
любимое решение на все задачи), **premature optimization**.

**Подвох.** Не каждый запах нужно лечить. Критерий — цена изменений: если
модуль не менялся два года и не планируется, длинный метод в нём не проблема.
Рефакторинг оправдан там, где код активно развивается.

**Глубже.** Отдельно стоит уметь ответить про **технический долг**. Полезная
классификация (квадранты Фаулера): долг может быть намеренным (сознательно
срезали угол ради срока) и случайным (не знали, как лучше), плюс
осмотрительным или безрассудным. Намеренный и осмотрительный долг — нормальный
инженерный инструмент при условии, что он записан и возвращён; безрассудный
случайный — то, что убивает проекты.

**В Python:** пустой `except` и правильная обработка ошибок —
[исключения](../python/exceptions.md); линтеры и типизация как автоматическая
ловушка для запахов — [инструменты разработчика](../python/dev-tools.md) и
[базовый `typing`](../python/typing-basics.md).

## Что такое рефакторинг и как его делают безопасно?

**Коротко.** Рефакторинг — изменение внутренней структуры кода **без изменения
внешнего поведения**. Ключевое условие безопасности — тесты: сначала покрываем
поведение, потом меняем структуру мелкими шагами, прогоняя тесты после каждого.

Базовый набор преобразований: extract method / extract class, inline,
переименование, замена условия полиморфизмом, замена магического литерала
константой, введение параметра-объекта, разделение цикла, замена вложенных
условий ранним возвратом.

```python
# до: вложенность и неявные правила
def price(order):
    if order.items:
        if order.customer.is_vip:
            return order.total * 0.8
        else:
            return order.total
    return 0

# после: ранние возвраты, именованная константа
VIP_DISCOUNT = 0.8

def price(order):
    if not order.items:
        return 0
    if order.customer.is_vip:
        return order.total * VIP_DISCOUNT
    return order.total
```

**Подвох.** «Мы переписали модуль» — это не рефакторинг, а замена. Рефакторинг
не меняет поведение, поэтому и не требует изменения тестов: если тесты
пришлось править, вы поменяли поведение и должны честно это назвать.
Смешивать рефакторинг и новую функциональность в одном коммите — верный
способ получить нерецензируемый диф.

**Глубже.** Приём для крупных изменений — **strangler fig**: новая реализация
растёт рядом со старой, вызовы постепенно переключаются на неё, старая
удаляется, когда трафик ушёл. Для изменения схемы данных аналог — expand /
migrate / contract: сначала добавить новое поле и писать в оба, потом
перенести чтение, потом удалить старое. Оба приёма позволяют не
останавливать систему и в любой момент откатиться.

**В SQL:** обратная сторона схемных изменений — блокировки и транзакции при
DDL, см. [DDL/DML/DCL](../sql/ddl-dml-dcl.md) и
[ACID и изоляция](../sql/acid-and-null.md).
