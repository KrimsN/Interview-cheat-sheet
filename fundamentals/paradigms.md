## Какие парадигмы программирования вы знаете и чем они отличаются?

**Коротко.** Парадигма — это способ описывать вычисление. Императивная говорит
*как* получить результат (пошаговое изменение состояния), декларативная — *что*
должно получиться. ООП и процедурная — ветки императивной, функциональная и
логическая — декларативной; SQL — декларативный язык запросов.

Разделение проходит по одному вопросу: где живёт состояние и кто им управляет.

- **Процедурная.** Программа — последовательность процедур над общими данными.
  Состояние глобальное или передаётся в аргументах. Пример: C, скрипты на bash.
- **Объектно-ориентированная.** Состояние спрятано внутри объектов, снаружи
  доступны только методы. Программа — сеть объектов, обменивающихся
  сообщениями. Пример: Java, C#, Python.
- **Функциональная.** Вычисление — применение функций к неизменяемым данным.
  Нет присваивания и побочных эффектов, функция при тех же аргументах всегда
  даёт тот же результат. Пример: Haskell, Erlang, F#.
- **Декларативная в узком смысле.** Описывается желаемый результат, а
  исполнитель сам выбирает алгоритм: SQL, HTML, Prolog, конфигурация Terraform.

```python
# императивно: как
total = 0
for x in [1, 2, 3, 4]:
    if x % 2 == 0:
        total += x

# функционально: что
total = sum(x for x in [1, 2, 3, 4] if x % 2 == 0)
```

**Подвох.** «Какая парадигма лучше?» — вопрос-ловушка. Промышленные языки
мультипарадигменные, и код обычно смешанный: ООП для структуры системы,
функциональный стиль для преобразования данных, декларативный — для запросов
и конфигурации. Правильный ответ — какая парадигма подходит задаче.

**Глубже.** Ключевое практическое следствие функционального стиля —
*ссылочная прозрачность*: выражение можно заменить его значением без изменения
поведения программы. Отсюда бесплатно вытекают кеширование (мемоизация),
безопасное распараллеливание и воспроизводимые тесты. Именно поэтому
неизменяемые данные и чистые функции проникли в ООП-языки, а не потому,
что «функциональщина модная».

**В Python:** функциональный инструментарий — [функциональный стиль](../python/functional-programming.md),
[`itertools`](../python/itertools.md), [comprehensions](../python/comprehensions.md).
**В SQL:** декларативность в чистом виде — [DDL/DML/DCL](../sql/ddl-dml-dcl.md),
а планировщик решает *как* выполнять запрос — [индексы и `EXPLAIN`](../sql/indexes.md).

## Что такое чистая функция и побочный эффект?

**Коротко.** Чистая функция зависит только от аргументов и ничего не меняет
за своими пределами. Побочный эффект — любое наблюдаемое изменение вне
возвращаемого значения: запись в файл, в БД, в глобальную переменную,
мутация аргумента, печать в лог.

```python
# нечистая: мутирует аргумент и зависит от внешнего состояния
DISCOUNT = 0.1
def apply_discount(cart):
    cart["total"] *= (1 - DISCOUNT)     # мутация аргумента
    return cart

# чистая: тот же вход — тот же выход, ничего снаружи не тронуто
def discounted(total: float, discount: float) -> float:
    return total * (1 - discount)
```

**Подвох.** «Значит, побочные эффекты — это плохо?» Нет: программа без эффектов
бесполезна, она не может ни прочитать запрос, ни записать в базу. Задача не в
том, чтобы убрать эффекты, а в том, чтобы **сдвинуть их к границам системы**:
ядро с бизнес-логикой — чистое и тестируемое, эффекты — в тонком слое адаптеров.
Это ровно то, к чему приходит [гексагональная архитектура](architecture.md).

**Глубже.** Побочный эффект ломает не только тесты, но и оптимизации: чистую
функцию можно кешировать, переупорядочить, выполнить лениво или параллельно.
Идемпотентность — родственное, но другое свойство: эффект есть, но повторный
вызов с теми же аргументами не меняет результат (`PUT` в HTTP, `DELETE` по id).
В распределённых системах это важнее чистоты, потому что retry неизбежен.
