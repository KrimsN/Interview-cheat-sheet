## Что такое O-нотация?

**Коротко.** O-большое описывает, как растёт время (или память) алгоритма
при росте размера входа, с точностью до константы и младших членов. Это
верхняя оценка **асимптотики**, а не измерение скорости: `O(n)` ничего не
говорит о том, быстрее ли алгоритм на входе из десяти элементов.

Порядок роста по возрастанию: `O(1)` → `O(log n)` → `O(n)` → `O(n log n)` →
`O(n²)` → `O(2ⁿ)` → `O(n!)`.

```python
# O(n^2): для каждой пары — сравнение
def has_duplicate_slow(items):
    for i, a in enumerate(items):
        for b in items[i + 1:]:
            if a == b:
                return True
    return False

# O(n) по времени, O(n) по памяти — классический размен
def has_duplicate(items):
    seen = set()
    for x in items:
        if x in seen:
            return True
        seen.add(x)
    return False
```

**Подвох.** Три частые ошибки. Первая — путать O (верхняя граница), Θ (точная)
и Ω (нижняя): корректно сказать, что быстрая сортировка — `O(n²)` в худшем
случае и `Θ(n log n)` в среднем. Вторая — забывать про память: решение
за `O(n)` времени и `O(n)` памяти не всегда лучше `O(n log n)` на месте.
Третья — игнорировать константу: на реальных размерах данных алгоритм с
худшей асимптотикой часто выигрывает за счёт локальности памяти.

**Глубже.** Амортизированная сложность — средняя стоимость операции по
последовательности операций, а не по случайному входу. Добавление в
динамический массив — `O(1)` амортизированно: изредка происходит
перевыделение с копированием за `O(n)`, но по сумме операций стоимость
остаётся константной. Это не то же самое, что «в среднем `O(1)`»: у хеш-таблицы
`O(1)` именно в среднем, а в худшем случае — `O(n)` из-за коллизий.

**В Python:** стоимость операций конкретных типов и Timsort —
[сортировка](../python/sorting.md); хеширование и требования к ключам —
[типы данных](../python/data-types.md).

## Как выбрать структуру данных?

**Коротко.** По профилю операций: что делается чаще — вставка, поиск, обход по
порядку, доступ по индексу — и есть ли требование к упорядоченности. Ниже
типовые оценки в среднем случае.

| Структура | Поиск | Вставка | Удаление | Порядок |
|---|---|---|---|---|
| Динамический массив | `O(n)` / `O(1)` по индексу | `O(1)` в конец | `O(n)` из середины | сохраняется |
| Связный список | `O(n)` | `O(1)` при известном узле | `O(1)` при известном узле | сохраняется |
| Хеш-таблица | `O(1)` | `O(1)` | `O(1)` | нет |
| Сбалансированное дерево | `O(log n)` | `O(log n)` | `O(log n)` | сортированный |
| Куча (heap) | `O(n)`, минимум за `O(1)` | `O(log n)` | `O(log n)` минимума | частичный |
| Дек (deque) | `O(n)` | `O(1)` с обоих концов | `O(1)` с обоих концов | сохраняется |

Практические выводы: проверка вхождения в цикле — множество, а не список
(иначе алгоритм незаметно становится `O(n²)`); «top-K из потока» — куча;
«всегда нужен минимум/максимум и диапазонные запросы» — дерево; очередь
задач — дек, а не список с удалением из головы.

**Подвох.** `O(1)` хеш-таблицы — амортизированная средняя оценка. Она
предполагает хорошую хеш-функцию; при массовых коллизиях всё вырождается
в `O(n)`. Это не теоретическая тонкость: атака на хеш-коллизии — реальный
класс DoS-уязвимостей, из-за которого в языки завезли рандомизацию хеша.

**Глубже.** Асимптотика не учитывает иерархию памяти. Обход массива быстрее
обхода связного списка той же длины при одинаковой сложности, потому что
массив лежит непрерывно и попадает в кеш процессора. Отсюда практическое
правило: при малых n и линейном обходе массив почти всегда выигрывает.

**В Python:** `deque`, `Counter`, `defaultdict` и их сложности —
[модуль `collections`](../python/collections-module.md); что можно класть
в множество и словарь — [типы данных](../python/data-types.md).
**В SQL:** индекс — та же структура данных, вынесенная в СУБД: B-tree против
хеш-индекса и оценка стоимости плана — [индексы](../sql/indexes.md).
