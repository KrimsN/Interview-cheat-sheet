## Что такое free-threading (no-GIL) в CPython?

**Коротко.** В `python 3.13` появилась экспериментальная сборка CPython без
GIL (`python3.13t`, PEP 703) — потоки в ней действительно выполняют
Python-байткод параллельно на нескольких ядрах, а не по очереди. В
`python 3.14+` (PEP 779) free-threaded сборка перестала считаться
экспериментальной и получила статус официально поддерживаемой.

```python
import sys, sysconfig
sys._is_gil_enabled()                       # True в обычной сборке
sysconfig.get_config_var("Py_GIL_DISABLED")  # 0 в обычной, 1 во free-threaded
```

**Подвох.** «Free-threaded в 3.14 официально поддерживается» — не значит
«GIL отключён по умолчанию». Стандартный `python`/`python3.14` по-прежнему
собирается с GIL; free-threaded — это отдельная сборка, которую ставят
явно (`python3.14t`, `uv python install 3.14t`). Часть экосистемы
(расширения на C, написанные без учёта многопоточности) всё ещё может быть
несовместима с ней.

**Глубже.** Без GIL безопасность структур данных стандартной библиотеки
(`dict`, `list`, `deque` и т.д.) обеспечивается не одной глобальной
блокировкой, а более гранулярными механизмами — например, per-object
критическими секциями в реализации на C. Подробнее про конкретный случай
`deque` — в [модуле collections](collections-module.md).

## Чем экспериментальный JIT отличается от free-threading?

**Коротко.** Это независимая фича из того же пакета изменений CPython
3.13+ (PEP 744) — copy-and-patch JIT-компилятор, который транслирует
байткод в машинный код на лету. Он отключён по умолчанию (нужна сборка с
`--enable-experimental-jit`) и пока не даёт заметного прироста
производительности «из коробки» — это фундамент под будущие версии, а не
готовое ускорение.

**Подвох.** Free-threading и JIT — это две ортогональные фичи, добавленные
в CPython примерно в одно время, и их легко перепутать на собеседовании:
free-threading убирает GIL (параллелизм потоков), JIT ускоряет исполнение
байткода одного потока (скорость). Сборка может быть free-threaded без
JIT, с JIT без free-threading, или вообще ни с тем, ни с другим — это две
независимые оси, а не одна фича под двумя именами.

## Чем суб-интерпретаторы отличаются от free-threading?

**Коротко.** Модуль `concurrent.interpreters` (`python 3.14+`, PEP 734)
даёт доступ из стандартной библиотеки к нескольким изолированным
суб-интерпретаторам CPython — каждый со своим GIL и своим состоянием
интерпретатора. Раньше эта возможность существовала только в C API.

**Подвох.** Не путать с free-threading: free-threading — это один
интерпретатор без GIL, где потоки **разделяют** одну и ту же память и
объекты напрямую. Суб-интерпретаторы, наоборот, **изолируют** состояние —
у каждого свой GIL, объекты между ними по умолчанию не расшариваются, а
обмен данными идёт через явные каналы. Это два разных инструмента для
обхода одного и того же ограничения (один GIL на процесс), а не два
варианта одной и той же идеи.

**Глубже.** Суб-интерпретаторы ближе по духу к процессам (изоляция,
явный обмен данными), чем к потокам, но дешевле процесса — не нужно
поднимать отдельный экземпляр интерпретатора и копировать память через
fork/exec.
