## Как вернуть из метода «тип самого себя»: `Self`?

**Коротко.** `typing.Self` (`python 3.11+`) — аннотация для методов, которые
возвращают экземпляр своего же класса: альтернативные конструкторы,
fluent-интерфейсы, контекстные менеджеры. Наследнику не нужно ничего
переопределять в аннотациях — `Self` сам подставит правильный тип.

```python
# python 3.11+
from typing import Self

class Builder:
    def add(self, item) -> Self:
        ...
        return self

class SpecialBuilder(Builder):
    pass

SpecialBuilder().add(1)   # анализатор знает: тип — SpecialBuilder, не Builder
```

**Подвох.** До `Self` эту же задачу решали через `TypeVar`, привязанный к
классу (`T = TypeVar("T", bound="Builder")`), и это было многословно и
легко забыть протащить `TypeVar` через весь класс. `Self` — не новая
возможность рантайма, а просто удобный синоним для этого паттерна:
на выполнение программы не влияет никак, это чистая подсказка анализатору.

**Глубже.** `Self` работает и в аннотациях атрибутов, и как тип параметра
(`def replace(self, other: Self) -> Self`), что удобно для методов вроде
`__copy__` или `with_x()`-паттерна на датаклассах.

## Как объявить дженерик-класс без ручного `TypeVar`?

**Коротко.** С `python 3.12+` (PEP 695) параметры типа объявляются прямо в
сигнатуре класса или функции — `TypeVar`/`ParamSpec`/`TypeVarTuple` руками
создавать больше не нужно.

```python
# python 3.12+
class Stack[T]:
    def push(self, item: T) -> None: ...
    def pop(self) -> T: ...

type IntOrStrSequence[T: (int, str)] = list[T]
```

Тот же синтаксис работает и для обобщённых функций — пример с декоратором
разобран в [Декораторы](decorators.md).

**Подвох.** `type` здесь — не обычное имя, а мягкое ключевое слово
(soft keyword): вне контекста объявления алиаса это по-прежнему встроенная
функция `type()`, конфликта с существующим кодом нет.

**Глубже.** Старый синтаксис (`T = TypeVar("T")`) никуда не делся и
поддерживается наравне с новым — библиотеки, которые должны работать на
версиях до 3.12, используют его осознанно.

## Что такое ковариантность и контрвариантность `TypeVar`?

**Коротко.** Это про то, сохраняется или инвертируется отношение подтипов у
generic-контейнера при подстановке в него отношения подтипов его параметра.
Пусть `Dog` — подтип `Animal`. Вопрос: как соотносятся `Container[Dog]` и
`Container[Animal]`?

- **ковариантный** (`covariant=True`) — направление сохраняется:
  `Container[Dog]` является подтипом `Container[Animal]`. Годится, когда `T`
  только **отдаётся наружу** (read-only, «producer») — так ведут себя
  `Sequence`, `Iterable`, `FrozenSet`.
- **контрвариантный** (`contravariant=True`) — направление инвертируется:
  `Container[Animal]` является подтипом `Container[Dog]`. Годится, когда `T`
  только **принимается на вход** (write-only, «consumer») — так ведут себя
  обработчики/колбэки, `Callable[[T], ...]` по своим аргументам.
- **инвариантный** (по умолчанию, без флагов) — `Container[Dog]` и
  `Container[Animal]` вообще не в отношении подтипов друг с другом, даже если
  `Dog` — подтип `Animal`. Так ведёт себя `list`, потому что в него можно и
  писать, и читать.

```python
from typing import TypeVar, Generic
from collections.abc import Sequence, Callable

class Animal: ...
class Dog(Animal): ...

# ковариантность: Sequence только читает элементы
def process_animals(animals: Sequence[Animal]) -> None: ...
dogs: Sequence[Dog] = [Dog()]
process_animals(dogs)  # OK

# контрвариантность: обработчик, умеющий любое животное, годится и для собак
def make_dog_handler(h: Callable[[Animal], None]) -> Callable[[Dog], None]:
    return h  # OK

# инвариантность: list и читает, и пишет — подмена типа небезопасна
def add_animal(animals: list[Animal]) -> None:
    animals.append(Animal())   # испортило бы list[Dog]

dogs_list: list[Dog] = [Dog()]
add_animal(dogs_list)  # mypy: ошибка, list[Dog] — не list[Animal]
```

Свой ковариантный/контрвариантный `TypeVar`:

```python
T_co = TypeVar("T_co", covariant=True)

class ReadOnlyBox(Generic[T_co]):
    def __init__(self, item: T_co) -> None:
        self._item = item

    def get(self) -> T_co:
        return self._item
```

**Подвох.** Путают направление у контрвариантности — кажется нелогичным, что
`Container[Animal]` оказывается «более специальным» типом, чем
`Container[Dog]`. Мнемоника PECS (Producer Extends, Consumer Super, из Java,
но применима и здесь): производитель (только отдаёт) — ковариантен,
потребитель (только принимает) — контрвариантен.

**Глубже.** Правило по ролям: тип, который **только читается** —
ковариантный; который **только пишется** — контрвариантный; который и
читается, и пишется — инвариантный (иначе подмена типа сломает инвариант в
одну из сторон). У функций аргументы контрвариантны, а возвращаемое значение
ковариантно — поэтому `Callable[[Animal], Dog]` является подтипом
`Callable[[Dog], Animal]`, а не наоборот.

Начиная с `python 3.12+` (PEP 695) вариантность для `class Container[T]` в
новом синтаксисе анализаторы типов (mypy, pyright) **выводят автоматически**
по тому, как `T` используется внутри класса — явно указывать
`covariant=`/`contravariant=` в большинстве нового кода уже не нужно.

**В общей теории:** вариантность — частный случай принципа подстановки
Барбары Лисков (LSP) для параметризованных типов — см.
[Четыре столпа ООП](../fundamentals/oop-basics.md#что-такое-вариантность-обобщённых-типов).

## Зачем нужен `typing.override`?

**Коротко.** `@typing.override` (`python 3.12+`) явно помечает, что метод
переопределяет метод родителя. Статические анализаторы (mypy, pyright)
подсветят ошибку, если в родительском классе такого метода на самом деле
нет — например, из-за опечатки в имени.

```python
# python 3.12+
from typing import override

class Base:
    def get_color(self) -> str: ...

class Child(Base):
    @override
    def get_color(self) -> str:
        return "yellow"
```

**Подвох.** Это чисто статическая проверка — `@override` ничего не делает
в рантайме и не бросает исключение сам по себе (в отличие от аннотации
`@abstractmethod`). Опечатку в имени метода без анализатора в CI никто не
поймает.

**Глубже.** Полезная связка — `@override` в дочернем классе плюс
`@final` (тот же модуль `typing`) на родительском методе, если метод
переопределять запрещено вовсе.

## Что изменилось в вычислении аннотаций в Python 3.14?

**Коротко.** С `python 3.14+` (PEP 649 / PEP 749) аннотации типов
(`def f(x: SomeType)`, переменные класса и т.д.) больше не вычисляются
сразу при определении функции или класса — они лежат «лениво» и
вычисляются по требованию. Раньше для этого нужен был явный
`from __future__ import annotations` (PEP 563, который хранит аннотации
как строки) — теперь ленивое поведение работает по умолчанию, и
forward-ссылки на ещё не объявленные типы не требуют кавычек:

```python
# < python 3.14: без from __future__ import annotations была бы NameError
class Node:
    next: "Node | None" = None

# python 3.14+: кавычки больше не обязательны для forward-ссылок
class Node:
    next: Node | None = None
```

**Подвох.** Из-за ленивого вычисления читать аннотации напрямую из
`__annotations__` стало ненадёжно — на разных этапах жизни объекта там
может быть либо ещё не вычисленное значение, либо иное представление.
Правильный способ — `annotationlib.get_annotations()` или
`typing.get_type_hints()`, которые корректно разрешают и forward-ссылки, и
ленивые значения.

Кстати, сам факт, что **интерпретатор не проверяет типы во время
выполнения**, — отдельный и самый частый вопрос по теме, он разобран в
[Базовом typing](typing-basics.md#проверяет-ли-python-аннотации-типов).
Здесь — только то, что специфично именно для PEP 649.

**Глубже.** Важно не путать PEP 649 с PEP 563: PEP 563 **строкифицирует**
аннотации — в `__annotations__` буквально лежат строки, и, чтобы получить
настоящий объект типа, нужно было вручную звать `eval()` (что и делает
`get_type_hints()` под капотом). PEP 649 хранит не строку, а лениво
вызываемый код: `get_type_hints()`/`annotationlib.get_annotations()`
возвращают настоящие объекты типов сразу, без ручного `eval`. На
собеседовании эти два PEP часто путают именно в этом месте: «раз
лениво — значит, то же самое, что строки» — это не так.
