## Зачем нужен Rust, если есть C++ и Go?

**Коротко.** Rust даёт производительность и предсказуемость C++ (нет сборщика
мусора, нет рантайма поверх ОС) и при этом на этапе компиляции доказывает
безопасность памяти и отсутствие гонок данных. Плата — сложность borrow
checker и время компиляции.

Три языка решают разные задачи, и на собеседовании важно не «продать» Rust, а
показать, что вы понимаете границы.

- **C++** даёт тот же контроль над памятью, но безопасность лежит на
  дисциплине программиста: use-after-free, double free, гонка данных — это
  ошибки, которые компилятор в общем случае не видит. Rust переносит те же
  правила (у объекта один владелец, ссылка не переживает объект) в систему
  типов и проверяет их статически.
- **Go** тоже безопасен по памяти, но за счёт сборщика мусора и рантайма:
  есть паузы GC (пусть и короткие), есть накладные расходы на аллокации.
  Rust убирает GC, но взамен требует явно описывать время жизни данных.

Практический критерий выбора: Rust уместен там, где важны отсутствие пауз и
плотный контроль над памятью (встраиваемые системы, ядра БД, прокси, парсеры,
трейдинг, WebAssembly), либо там, где цена ошибки памяти высока (криптография,
браузеры, драйверы). Для типичного CRUD-сервиса с базой Go или Python обычно
быстрее в разработке.

**Подвох.** «Rust быстрее C++» — неверная формулировка, за неё цепляются.
Rust компилируется тем же LLVM и в среднем даёт сопоставимый машинный код;
выигрыш бывает там, где правила алиасинга (`&mut` гарантированно уникальна)
позволяют оптимизатору больше, а проигрыш — там, где проверки границ срезов
не удалось убрать. Правильный ответ: «сопоставимо, разница в конкретных
бенчмарках, а не в языке как таковом».

**Глубже.** «Zero-cost abstractions» в формулировке Бьярне Страуструпа
означает две вещи: за то, чем вы не пользуетесь, вы не платите; а то, чем
пользуетесь, нельзя было бы написать руками лучше. В Rust это относится к
итераторам, дженерикам, `Option`, `async`. Но zero-cost — про время
выполнения, не про время компиляции: мономорфизация дженериков и раскрытие
итераторных цепочек как раз и делают сборку медленной.

## Чем `let`, `let mut`, `const` и `static` отличаются друг от друга?

**Коротко.** `let` создаёт неизменяемое связывание, `let mut` — изменяемое.
`const` — константа времени компиляции, которая инлайнится в каждое место
использования. `static` — единственный объект с фиксированным адресом и
временем жизни `'static`.

```rust
const MAX_RETRIES: u32 = 3;          // тип обязателен, значение — const-выражение
static GREETING: &str = "hello";     // один объект в памяти на всю программу

fn main() {
    let x = 5;
    // x = 6;                        // ошибка: cannot assign twice to immutable variable
    let mut y = 5;
    y = 6;                           // ок
    println!("{x} {y} {MAX_RETRIES} {GREETING}"); // 5 6 3 hello
}
```

Разница `const` и `static` важнее, чем кажется: `const` — это не переменная, а
именованное значение, у него нет гарантированного адреса, компилятор
подставляет его копию в каждую точку использования. У `static` адрес есть,
поэтому изменяемый `static mut` — источник гонок и доступен только из
`unsafe` (в современном коде вместо него берут `static` c `Mutex`,
`OnceLock` или атомиками).

**Подвох.** Неизменяемость `let` — про связывание, а не про глубокую
заморозку данных. `let v = vec![1, 2, 3];` запрещает и `v = ...`, и
`v.push(4)`, потому что `push` требует `&mut self`. Но внутренняя
изменяемость (`Cell`, `RefCell`, `Mutex`) позволяет менять содержимое через
`&T` — см. [умные указатели](smart-pointers.md).

## Что такое shadowing и чем оно отличается от мутации?

**Коротко.** Shadowing — это новое связывание с тем же именем: старое
значение остаётся жить до конца своей области видимости, а имя начинает
указывать на новое, возможно другого типа. Мутация меняет содержимое одной и
той же переменной и тип менять не может.

```rust
fn main() {
    let spaces = "   ";          // &str
    let spaces = spaces.len();   // usize — то же имя, другой тип
    println!("{spaces}");        // 3

    let count = "5";
    // count = 5;                // ошибка: expected `&str`, found integer
    let count: i32 = count.parse().unwrap();
    println!("{count}");         // 5
}
```

Типичное применение — «конвейер» преобразования входа: строка → распарсенное
значение → проверенное значение, без выдумывания имён `s_raw`, `s_parsed`,
`s_valid`.

**Подвох.** Shadowing внутри блока действует только до конца блока:

```rust
let x = 5;
{
    let x = x * 2;
    println!("{x}"); // 10
}
println!("{x}");     // 5 — внешнее связывание не тронуто
```

## Почему говорят, что Rust — язык выражений?

**Коротко.** Почти всё в Rust возвращает значение: `if`, `match`, `loop`,
блок `{}`. Последнее выражение блока без точки с запятой становится его
результатом; точка с запятой превращает выражение в инструкцию со значением
`()` (unit).

```rust
fn classify(n: i32) -> &'static str {
    if n < 0 { "отрицательное" } else if n == 0 { "ноль" } else { "положительное" }
}

fn main() {
    let parity = match 7 % 2 {
        0 => "чёт",
        _ => "нечёт",
    };

    // loop умеет возвращать значение через break
    let mut i = 0;
    let first_square_over_50 = loop {
        i += 1;
        if i * i > 50 { break i * i; }
    };

    println!("{} {} {}", classify(-3), parity, first_square_over_50);
    // отрицательное нечёт 64
}
```

Отсюда идиома: тернарного оператора в языке нет, потому что `if` и так
выражение. И нет `return` в конце функции — последнее выражение и есть
возвращаемое значение; `return` оставляют для ранних выходов.

**Подвох.** Лишняя точка с запятой ломает тип:

```rust
fn f() -> i32 {
    let x = 5;
    x;            // ошибка: expected `i32`, found `()`
}
```

Компилятор прямо подсказывает «remove this semicolon» — это самая частая
ошибка первых дней.

**Глубже.** `if` без `else` имеет тип `()`, поэтому `let x = if cond { 5 };`
не компилируется: ветки должны иметь общий тип. Ветка, которая расходится
(`panic!`, `return`, `continue`, бесконечный `loop`), имеет тип `!` («never»)
и приводится к любому типу — поэтому `let x = if cond { 5 } else { panic!() };`
компилируется нормально.

## Как устроены циклы и почему `for` работает через `IntoIterator`?

**Коротко.** В Rust три цикла: `loop` (бесконечный, умеет возвращать
значение через `break`), `while` (в том числе `while let`) и `for`, который
всегда работает по итератору — запись `for x in expr` разворачивается в
вызов `expr.into_iter()`.

```rust
fn main() {
    let v = vec![10, 20, 30];

    for x in &v {          // &Vec<T> -> итератор по &T
        print!("{x} ");    // 10 20 30
    }
    println!();

    for (i, x) in v.iter().enumerate() {
        print!("{i}:{x} "); // 0:10 1:20 2:30
    }
    println!();

    // метки циклов — для выхода из вложенных
    'outer: for a in 1..10 {
        for b in 1..10 {
            if a * b > 20 { break 'outer; }
        }
    }

    let mut stack = vec![1, 2, 3];
    while let Some(top) = stack.pop() {
        print!("{top} ");  // 3 2 1
    }
    println!();
}
```

Три формы важно различать: `for x in v` **забирает** вектор во владение и
отдаёт `T` (после цикла `v` использовать нельзя), `for x in &v` даёт `&T`,
`for x in &mut v` — `&mut T`.

**Подвох.** Условие `if`/`while` обязано быть именно `bool`. Никакой
«истинности» чисел, указателей и пустых коллекций, как в C или Python:
`if 1 { }` — ошибка компиляции. Это осознанно убирает целый класс опечаток
вида `if (x = 1)`.

## Что такое editions и зачем они нужны?

**Коротко.** Edition (2015, 2018, 2021, 2024) — набор изменений, которые
нельзя внести без слома совместимости: новые ключевые слова, изменённые
правила разрешения имён, другая семантика отдельных конструкций. Крейт
объявляет своё издание в `Cargo.toml`, и крейты разных изданий свободно
линкуются друг с другом.

```toml
[package]
name = "my-service"
edition = "2024"
```

Ключевая идея — обратная совместимость без застоя: компилятор один, он умеет
все издания, а миграция делается покрейтно и автоматизирована
(`cargo fix --edition`). Издание 2024 стало значением по умолчанию для новых
проектов начиная с Rust 1.85.

**Подвох.** Издание — не версия компилятора. «Мы на edition 2021» ничего не
говорит о том, доступен ли вам `let ... else` или async-функции в трейтах:
это определяет версия toolchain (и, если задан, `rust-version` в манифесте —
MSRV, минимальная поддерживаемая версия).

## Как читать сообщения компилятора и почему это часть навыка?

**Коротко.** `rustc` печатает ошибку с кодом (`E0382`), стрелками на
конкретные места, объяснением «что произошло» и часто готовым исправлением.
Команда `rustc --explain E0382` разворачивает код ошибки в статью с примерами.

```text
error[E0382]: borrow of moved value: `s`
 --> src/main.rs:4:20
  |
2 |     let s = String::from("hi");
  |         - move occurs because `s` has type `String`, which does not implement `Copy`
3 |     let t = s;
  |             - value moved here
4 |     println!("{}", s);
  |                    ^ value borrowed here after move
  |
help: consider cloning the value if the performance cost is acceptable
```

На собеседовании нормально и правильно говорить: «здесь borrow checker
попросит либо клонировать, либо взять по ссылке — я бы посмотрел на его
подсказку». Это демонстрирует рабочий процесс, а не пробел в знаниях.

**Глубже.** Полезно знать не только `--explain`, но и `cargo clippy`
(несколько сотен линтов, включая группу `pedantic`) и `cargo fmt` —
форматирование в Rust каноническое, как `gofmt` в Go, и о стиле в командах не
спорят. Подробнее — в [инструментах](tooling.md).
