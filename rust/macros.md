## Чем макросы Rust отличаются от макросов C?

**Коротко.** Макросы C — подстановка текста препроцессором, без понимания
синтаксиса. Макросы Rust работают с деревом токенов, раскрываются после
разбора и до проверки типов, и они **гигиеничны**: идентификаторы, введённые
внутри макроса, не конфликтуют с именами в месте вызова.

```rust
macro_rules! double {
    ($x:expr) => { $x * 2 };
}

macro_rules! with_temp {
    ($e:expr) => {{
        let value = 100;      // это «своя» переменная value
        $e + value
    }};
}

fn main() {
    println!("{}", double!(2 + 3));   // 10, а не 2 + 3 * 2 — аргумент это одно выражение
    let value = 1;
    println!("{}", with_temp!(value)); // 101 — внешняя value не затёрта
}
```

В C `#define DOUBLE(x) x * 2` дало бы `2 + 3 * 2 = 8`, а внутренняя
переменная затёрла бы внешнюю. В Rust `$x:expr` — уже разобранное выражение, а
не текст.

**Подвох.** Ещё один любимый вопрос: почему `println!` — макрос, а не
функция. Две причины: переменное число аргументов (в Rust его нет) и проверка
строки формата на этапе компиляции — `println!("{} {}", 1)` не соберётся.

## Как написать декларативный макрос `macro_rules!`?

**Коротко.** Это сопоставление с образцом по токенам: слева — шаблон с
захватами `$name:фрагмент`, справа — код, который подставится.

```rust
macro_rules! my_vec {
    () => { Vec::new() };
    ($($x:expr),+ $(,)?) => {{      // один и более элементов, висячая запятая допустима
        let mut v = Vec::new();
        $( v.push($x); )+           // повторение по всем захваченным
        v
    }};
}

macro_rules! impl_greet {
    ($($t:ty),*) => {
        $(
            impl Greet for $t {
                fn greet(&self) -> String { format!("значение {self}") }
            }
        )*
    };
}

trait Greet { fn greet(&self) -> String; }
impl_greet!(i32, f64, bool);

fn main() {
    let v: Vec<i32> = my_vec![1, 2, 3];
    println!("{v:?}");          // [1, 2, 3]
    println!("{}", 42.greet()); // значение 42
    println!("{}", true.greet()); // значение true
}
```

Основные виды фрагментов: `expr` (выражение), `ty` (тип), `ident`
(идентификатор), `literal`, `pat` (образец), `block`, `stmt`, `path`, `tt`
(любое дерево токенов — самый общий и самый неудобный).

Повторения: `$( ... ),*` — ноль и более через запятую, `$( ... );+` — один и
более через точку с запятой.

**Глубже.** Гигиена в Rust частичная: она распространяется на локальные
переменные и лайфтаймы, но не на типы, функции и модули. Поэтому макрос,
подставляющий `Vec::new()`, полагается на то, что в месте вызова `Vec` — это
`std::Vec`; надёжные макросы пишут абсолютные пути: `::std::vec::Vec::new()`.

## Что такое процедурные макросы и какие они бывают?

**Коротко.** Отдельный крейт с `proc-macro = true`, который получает
`TokenStream` и возвращает `TokenStream` — то есть выполняет произвольный код
во время компиляции. Три вида: derive, атрибутные и функциональные.

| Вид | Как выглядит | Примеры |
|---|---|---|
| derive | `#[derive(Serialize)]` | `serde`, `thiserror`, `clap` |
| атрибутный | `#[tokio::main]`, `#[get("/")]` | `tokio`, `actix-web`, `tracing` |
| функциональный | `sqlx::query!("SELECT ...")` | `sqlx`, `regex` (`regex!`) |

```rust
// в крейте my-derive (Cargo.toml: [lib] proc-macro = true)
use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, DeriveInput};

#[proc_macro_derive(Hello)]
pub fn derive_hello(input: TokenStream) -> TokenStream {
    let ast = parse_macro_input!(input as DeriveInput);
    let name = &ast.ident;
    quote! {
        impl #name {
            fn hello() -> String { format!("привет от {}", stringify!(#name)) }
        }
    }.into()
}
```

Экосистема стандартна: `syn` разбирает токены в AST, `quote` собирает код
обратно, `proc-macro2` даёт типы, работающие вне контекста макроса (чтобы код
можно было тестировать).

Самый впечатляющий пример возможностей — `sqlx::query!`: он **подключается к
базе во время компиляции**, проверяет SQL и выводит типы колонок. Ошибка в
запросе становится ошибкой сборки.

## Какие стандартные макросы надо знать?

**Коротко.** `println!`/`format!`/`write!`, `vec!`, `assert!`/`assert_eq!`,
`matches!`, `todo!`/`unimplemented!`/`unreachable!`, `dbg!`, `include_str!`,
`env!`, `cfg!`.

```rust
fn main() {
    let name = "мир";
    println!("Привет, {name}!");            // захват переменной прямо в строке (1.58+)
    println!("{:>8.2}|", 3.14159);          // «    3.14|» — ширина и точность
    println!("{0} {1} {0}", "a", "b");      // a b a — позиционные аргументы

    let v = vec![0u8; 3];                   // [0, 0, 0] — значение и длина
    println!("{v:?}");

    assert_eq!(v.len(), 3, "длина должна быть 3");
    println!("{}", matches!(v.first(), Some(0)));   // true

    let x = dbg!(2 + 2);                    // печатает в stderr: [src/main.rs:12] 2 + 2 = 4
    println!("{x}");

    println!("собрано из {}", env!("CARGO_PKG_NAME")); // имя пакета на этапе компиляции
}
```

`todo!()` и `unimplemented!()` полезны при проектировании: они возвращают тип
`!`, поэтому компилируются в любом контексте, и позволяют написать сигнатуры
целиком, а тела — потом. `unreachable!()` документирует ветку, в которую
попасть нельзя.

**Подвох.** `dbg!` **забирает значение** и возвращает его обратно, поэтому
`dbg!(v)` перемещает `v`. Для заимствования — `dbg!(&v)`. И `dbg!` не должен
уезжать в коммит: за это ругается clippy.

## Как отлаживать макросы и когда их не надо писать?

**Коротко.** `cargo expand` показывает раскрытый код; на nightly есть
`trace_macros!`. Правило: сначала функция, дженерик или трейт — макрос только
тогда, когда без него не выразить.

```bash
cargo install cargo-expand
```

```bash
cargo expand --lib storage
```

Цена макросов вполне конкретна: дольше компиляция, хуже сообщения об ошибках
(они указывают внутрь раскрытия), сложнее чтение и навигация в IDE, тяжелее
отладка. Процедурные макросы к тому же тянут `syn`/`quote`, а это заметный
кусок времени сборки.

Когда макрос оправдан:

- переменное число аргументов или произвольный синтаксис (`vec!`, `json!`);
- кодогенерация по структуре типа, которую нельзя выразить трейтом
  (`#[derive(Serialize)]`);
- проверки на этапе компиляции (`sqlx::query!`);
- устранение действительно повторяющегося бойлерплейта — например, одинаковая
  реализация трейта для десятка примитивных типов.

**Глубже.** `#[macro_export]` кладёт `macro_rules!`-макрос в корень крейта, и
пользователи импортируют его как `use my_crate::my_macro;`. Процедурные
макросы обязаны жить в отдельном крейте — отсюда типовая пара `serde` и
`serde_derive`, `thiserror` и `thiserror-impl`.
