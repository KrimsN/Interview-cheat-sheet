## Что такое rustup и как фиксируют версию тулчейна?

**Коротко.** `rustup` — менеджер тулчейнов: каналы `stable`, `beta`,
`nightly`, компоненты (clippy, rustfmt, miri) и целевые платформы. Версию для
проекта фиксируют файлом `rust-toolchain.toml` — тогда у всей команды и в CI
собирается одно и то же.

```toml
# rust-toolchain.toml
[toolchain]
channel = "1.85.0"
components = ["clippy", "rustfmt"]
targets = ["x86_64-unknown-linux-musl"]
```

```bash
rustup component add clippy rustfmt
```

Стабильный канал выходит каждые шесть недель; обратная совместимость
гарантируется, поэтому обновление тулчейна почти никогда не ломает код (а
ломающие изменения синтаксиса вынесены в [editions](basics.md)).

## Зачем clippy и rustfmt?

**Коротко.** `cargo fmt` — единый канонический стиль, о котором не спорят, как
и `gofmt` в Go. `cargo clippy` — несколько сотен линтов: от реальных багов до
идиоматики.

```bash
cargo clippy --all-targets --all-features -- -D warnings
```

Что ловит clippy на практике: лишние `clone()` и `to_string()`, избыточные
замыкания, `unwrap` там, где есть `expect`, ручные циклы вместо итераторных
методов, `large_enum_variant`, недокументированные `unsafe`-блоки,
подозрительные сравнения чисел с плавающей точкой.

Группы линтов: `correctness` (включена как ошибка), `style`, `complexity`,
`perf` — по умолчанию; `pedantic` и `nursery` — по желанию, включаются в
`Cargo.toml`:

```toml
[lints.clippy]
pedantic = { level = "warn", priority = -1 }
unwrap_used = "warn"
```

**Подвох.** `-D warnings` в CI — стандартная практика, но локально удобнее
без него: иначе любой промежуточный `dbg!` останавливает сборку.

## Чем `cargo check` отличается от `cargo build`?

**Коротко.** `check` выполняет разбор и проверку типов, но не запускает
кодогенерацию LLVM и линковку. Это в несколько раз быстрее и покрывает
большинство ошибок — именно его гоняют в цикле редактирования.

| Команда | Что делает | Когда |
|---|---|---|
| `cargo check` | типы и заимствования | в цикле разработки, в редакторе |
| `cargo build` | + кодогенерация и линковка | когда нужно запустить |
| `cargo build --release` | + оптимизации | замеры, деплой |
| `cargo test` | сборка тестов и запуск | перед коммитом |

`rust-analyzer` — LSP-сервер, который по сути и делает `cargo check` в фоне,
показывая ошибки прямо в редакторе. Это фактический стандарт для любой IDE.

## Как настраиваются профили сборки?

**Коротко.** Два профиля из коробки: `dev` (без оптимизаций, с отладочной
информацией, переполнение — паника) и `release` (`opt-level = 3`,
переполнение оборачивается). Тюнят через `Cargo.toml`.

```toml
[profile.release]
lto = "thin"          # межмодульная оптимизация: меньше и быстрее, дольше сборка
codegen-units = 1     # один блок кодогенерации — лучше оптимизация, нет параллелизма
panic = "abort"       # без раскрутки стека: меньше бинарник, быстрее
strip = true          # убрать символы

[profile.release-debug]   # свой профиль для профилирования
inherits = "release"
debug = true              # символы нужны, чтобы flamegraph был читаемым
```

**Подвох.** `codegen-units = 1` и `lto = "fat"` дают обычно единицы процентов
скорости, но заметно удлиняют сборку. Включать их стоит для релизных
артефактов, а не для повседневной работы.

## Почему Rust долго компилируется и что с этим делать?

**Коротко.** Три причины: мономорфизация (по копии кода на каждый тип),
объём работы LLVM по оптимизации этих копий и то, что единица компиляции —
**крейт целиком**, а не файл.

Что реально помогает:

- `cargo check` вместо `build` в цикле разработки;
- разбиение на несколько крейтов в [workspace](modules-crates.md) —
  компилируются параллельно и кешируются независимо;
- быстрый линкер: `lld` или `mold` (на больших проектах линковка — заметная
  доля времени);
- `sccache` — кеш артефактов, особенно полезен в CI;
- меньше «тяжёлых» proc-macro зависимостей (`syn` тянет за собой много);
- `cargo build --timings` — HTML-отчёт, показывающий, какие крейты и на каком
  этапе съедают время.

```bash
cargo build --timings
```

```toml
# .cargo/config.toml — переключение линкера
[target.x86_64-unknown-linux-gnu]
rustflags = ["-C", "link-arg=-fuse-ld=lld"]
```

## Чем профилировать Rust-программу?

**Коротко.** CPU — `perf` и flamegraph; аллокации — `dhat` или `heaptrack`;
размер бинарника — `cargo bloat`; асинхронные задачи — `tokio-console`.

```bash
cargo install flamegraph
```

```bash
cargo flamegraph --bin my-service
```

Порядок работы, который ценят на собеседовании: сначала измерить и найти
горячую точку, потом менять код, потом измерить снова. Про «оптимизацию по
интуиции» отвечают, что она чаще всего оптимизирует не то.

Важная деталь: профилировать нужно **релизную** сборку с отладочными
символами (`debug = true` в профиле), иначе цифры не имеют отношения к
реальности, а стек нечитаем.

## Как следят за безопасностью зависимостей?

**Коротко.** `cargo audit` — известные уязвимости из базы RustSec,
`cargo deny` — политика по лицензиям, дубликатам версий и запрещённым
крейтам, `cargo geiger` — сколько `unsafe` в графе зависимостей.

```bash
cargo audit
```

```toml
# deny.toml
[licenses]
allow = ["MIT", "Apache-2.0", "BSD-3-Clause"]

[bans]
multiple-versions = "warn"
```

Полезно и просто гигиенически: `cargo tree -d` показывает дубликаты версий
(источник ошибок «expected struct `X`, found struct `X`»), `cargo udeps` —
зависимости, которые никто не использует.

## Как собирают и деплоят Rust-сервисы?

**Коротко.** Кросс-компиляция — `--target` плюс `rustup target add`; полностью
статический бинарник — цель `x86_64-unknown-linux-musl`; в Docker —
многоступенчатая сборка с кешированием зависимостей.

```dockerfile
FROM rust:1.85 AS builder
WORKDIR /app
COPY Cargo.toml Cargo.lock ./
COPY src ./src
RUN cargo build --release

FROM debian:bookworm-slim
COPY --from=builder /app/target/release/my-service /usr/local/bin/
CMD ["my-service"]
```

Итоговый образ получается небольшим: рантайма нет, нужны только системные
библиотеки (а с `musl` — вообще ничего, можно `FROM scratch`). Для
кеширования слоёв зависимостей используют `cargo chef`, для сборки под чужую
платформу — `cross`.

**Глубже.** Диагностика в рантайме: `RUST_BACKTRACE=1` для стека при панике,
`RUST_LOG` вместе с `tracing`/`env_logger` для уровней логирования,
`debug_assertions` для кода, который должен исчезнуть в релизе. Подробнее про
`tracing` — в [экосистеме](ecosystem-web.md).
