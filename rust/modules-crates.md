## Чем пакет отличается от крейта и от модуля?

**Коротко.** Пакет — это `Cargo.toml` и то, что он собирает. Крейт — единица
компиляции: библиотека (`src/lib.rs`) или бинарник (`src/main.rs`,
`src/bin/*.rs`). Модуль — дерево пространств имён внутри крейта. Один пакет
содержит максимум одну библиотеку и сколько угодно бинарников.

```text
my-service/
├── Cargo.toml          пакет
├── src/
│   ├── lib.rs          крейт-библиотека (корневой модуль)
│   ├── main.rs         крейт-бинарник
│   ├── config.rs       модуль config
│   └── storage/        модуль storage
│       ├── mod.rs      (или storage.rs рядом с каталогом — современный стиль)
│       └── postgres.rs модуль storage::postgres
├── tests/              интеграционные тесты — каждый файл отдельный крейт
└── benches/            бенчмарки
```

Различие важно для практики: orphan rule (см. [трейты](traits.md))
формулируется в терминах **крейтов**, а видимость `pub(crate)` — тоже про
крейт, а не про пакет.

## Как работает система модулей и видимость?

**Коротко.** Модули **объявляются** (`mod foo;`), а не находятся
автоматически по файлам. Всё приватно по умолчанию; наружу — `pub`,
`pub(crate)`, `pub(super)`, `pub(in path)`.

```rust
mod storage {
    pub mod postgres {
        pub fn connect() -> String { super::helper() }  // видит приватное родителя
        fn own_helper() -> &'static str { "внутренний" }
    }

    fn helper() -> String { "подключились".into() }    // приватно для storage
}

mod api {
    // pub(crate) fn f() { super::storage::helper(); } // ошибка: helper приватен для соседа
}

fn main() { println!("{}", storage::postgres::connect()); } // подключились
```

Логика видимости обратна привычной по Java: приватный элемент виден **всем
потомкам** своего модуля, но не соседям и не родителю. То есть модуль может
прятать детали от внешнего мира, но его собственные подмодули имеют к ним
доступ.

**Подвох.** Файл, не подключённый через `mod`, просто не компилируется — он
не входит в дерево крейта. Это регулярно ловит новичков: файл создан, код в
нём есть, но компилятор его «не видит».

## Зачем нужен `pub use`?

**Коротко.** Реэкспорт: внутреннюю раскладку модулей можно менять, не ломая
публичный API. Это стандартный приём «фасада» для библиотек.

```rust
// src/lib.rs
mod storage;
mod config;

pub use config::Config;            // пользователь пишет my_crate::Config,
pub use storage::postgres::Client; // не зная про внутренние модули
```

Без реэкспорта пользователи писали бы
`my_crate::storage::postgres::Client`, и любая перестановка модулей была бы
ломающим изменением. С ним внутренняя структура — деталь реализации.

Ещё одна форма — модуль `prelude` (`pub use crate::prelude::*`), удобная для
библиотек с большим числом трейтов, которые нужно импортировать: так делают
`rayon`, `diesel`, `polars`.

## Какие команды Cargo нужно знать?

**Коротко.** Сборка и запуск — `build`/`run`/`check`; качество — `test`,
`clippy`, `fmt`; зависимости — `add`, `update`, `tree`; документация — `doc`.

```bash
cargo check              # быстрая проверка типов без кодогенерации
```

```bash
cargo clippy --all-targets -- -D warnings
```

```bash
cargo tree -d            # показать дублирующиеся версии крейтов в графе
```

`cargo check` — главный инструмент повседневного цикла: он не порождает
машинный код и потому в разы быстрее `build`. Полный список инструментов —
в [теме про tooling](tooling.md).

## Как Cargo выбирает версии зависимостей?

**Коротко.** Требование `serde = "1.2.3"` означает «совместимо по SemVer»,
то есть `>=1.2.3, <2.0.0`. Cargo берёт **максимальную** подходящую версию и
фиксирует выбор в `Cargo.lock`. В графе допускается несколько мажорных версий
одного крейта одновременно.

```toml
[dependencies]
serde = { version = "1", features = ["derive"] }
tokio = { version = "1", features = ["full"] }
anyhow = "1"

[dev-dependencies]
criterion = "0.5"     # только для тестов и бенчмарков
```

**Подвох.** Именно из-за нескольких мажорных версий возникает знаменитая
ошибка «expected struct `Uuid`, found struct `Uuid`»: два ваших крейта тянут
`uuid` версий 0.8 и 1.0, и типы из них — **разные типы**, хотя называются
одинаково. Диагностика — `cargo tree -d`, лечение — согласовать версии.

**Глубже.** Отличие от Go: там MVS (minimal version selection) берёт
минимальную версию, удовлетворяющую всем требованиям, и мажорная версия
входит в путь импорта. Cargo, наоборот, берёт максимальную — поэтому
`Cargo.lock` для воспроизводимости коммитят (для бинарников — обязательно, для
библиотек сейчас тоже принято, чтобы CI был стабилен).

## Что такое features и почему они аддитивны?

**Коротко.** Feature — именованный флаг условной компиляции, включающий кусок
кода или опциональную зависимость. Флаги **объединяются** по всему графу
зависимостей: если один крейт включил `foo/tls`, он включён у всех.

```toml
[features]
default = ["json"]
json = ["dep:serde_json"]
tls = ["dep:rustls"]

[dependencies]
serde_json = { version = "1", optional = true }
rustls = { version = "0.23", optional = true }
```

```rust
#[cfg(feature = "json")]
pub fn to_json<T: serde::Serialize>(v: &T) -> String {
    serde_json::to_string(v).unwrap_or_default()
}
```

Отсюда важное правило: **взаимоисключающих features не бывает**. Пара
`use-openssl` / `use-rustls` рано или поздно окажется включённой целиком, и
крейт перестанет собираться у пользователя, который ни при чём. Правильные
решения — либо выбор в рантайме, либо отдельные крейты.

Отключить лишнее у зависимости можно так:

```toml
reqwest = { version = "0.12", default-features = false, features = ["json"] }
```

**Глубже.** `#![no_std]` — сборка без стандартной библиотеки (микроконтроллеры,
ядра ОС): доступны `core` и, при наличии аллокатора, `alloc`. Библиотеки часто
делают `no_std` опциональным именно через feature `std`, включённую по
умолчанию.

## Что такое workspace и когда он нужен?

**Коротко.** Workspace — несколько крейтов с общим `Cargo.lock`, общим
каталогом `target/` и согласованными версиями зависимостей. Типичная
раскладка сервиса, разрезанного на слои.

```toml
# Cargo.toml в корне
[workspace]
members = ["crates/domain", "crates/storage", "crates/api"]
resolver = "2"

[workspace.dependencies]
serde = { version = "1", features = ["derive"] }
```

```toml
# crates/domain/Cargo.toml
[dependencies]
serde = { workspace = true }   # версия берётся из корня
```

Практический выигрыш: общий `target/` резко ускоряет сборку (зависимости
компилируются один раз), а разделение на крейты даёт параллельную компиляцию
и явные границы между слоями — циклические зависимости между крейтами Cargo
просто запретит.

## Как устроена условная компиляция?

**Коротко.** Атрибут `#[cfg(...)]` выкидывает код на этапе разбора, макрос
`cfg!(...)` даёт булево значение в выражении.

```rust
#[cfg(target_os = "linux")]
fn platform() -> &'static str { "linux" }

#[cfg(target_os = "windows")]
fn platform() -> &'static str { "windows" }

#[cfg(test)]
mod tests {                       // компилируется только под cargo test
    #[test]
    fn works() { assert!(super::platform().len() > 2); }
}

fn main() {
    println!("{} debug={}", platform(), cfg!(debug_assertions));
}
```

`#[cfg(test)]` — идиома для юнит-тестов рядом с кодом: в релизной сборке этого
модуля просто не существует (см. [тестирование](testing.md)).

**Глубже.** `build.rs` — скрипт сборки, который выполняется до компиляции
крейта: генерирует код, ищет системные библиотеки, передаёт флаги линкеру
через `println!("cargo::rustc-link-lib=...")`. Его зависимости объявляются в
`[build-dependencies]`. Нужен в основном для [FFI](unsafe-ffi.md) и
кодогенерации (`prost`, `tonic`).
