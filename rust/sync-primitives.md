## Чем `Mutex` в Rust отличается от мьютексов в Go, Python и C++?

**Коротко.** `Mutex<T>` **владеет данными**: добраться до `T` можно только
через `lock()`, который возвращает RAII-guard, снимающий блокировку в `Drop`.
Забыть разблокировать или обратиться к данным без блокировки невозможно —
не по дисциплине, а по типам.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));

    let handles: Vec<_> = (0..8).map(|_| {
        let c = Arc::clone(&counter);
        thread::spawn(move || {
            for _ in 0..1000 {
                let mut guard = c.lock().unwrap();  // guard: MutexGuard<i32>
                *guard += 1;
            }                                        // разблокировка здесь, автоматически
        })
    }).collect();

    for h in handles { h.join().unwrap(); }
    println!("{}", *counter.lock().unwrap());        // 8000
}
```

Сравните: в Go `sync.Mutex` лежит рядом с данными, и ничто не мешает
обратиться к полю, забыв `Lock()`. В Python `threading.Lock` — то же самое
плюс необходимость `with`. В Rust «данные без блокировки» — просто
невыразимое состояние.

Зачем `Arc` вокруг `Mutex`: `Mutex` даёт **взаимное исключение**, `Arc` —
**разделяемое владение**. Это ортогональные задачи, и каждая решается своим
типом.

## Что такое отравление мьютекса?

**Коротко.** Если поток запаниковал, удерживая блокировку, мьютекс
помечается как отравленный: последующие `lock()` возвращают
`Err(PoisonError)`. Логика — данные могли остаться в несогласованном
состоянии, и об этом надо узнать.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let m = Arc::new(Mutex::new(vec![1, 2, 3]));

    let m2 = Arc::clone(&m);
    let _ = thread::spawn(move || {
        let _g = m2.lock().unwrap();
        panic!("паника с захваченной блокировкой");
    }).join();

    println!("{}", m.lock().is_err());          // true — мьютекс отравлен

    // достать данные всё равно можно, осознанно
    let data = m.lock().unwrap_or_else(|e| e.into_inner());
    println!("{data:?}");                        // [1, 2, 3]
}
```

Именно поэтому в примерах повсюду `.lock().unwrap()`: это не небрежность, а
«если другой поток упал с блокировкой — падаем и мы».

**Глубже.** Крейт `parking_lot` предлагает мьютексы без отравления, меньшего
размера и обычно быстрее в неконкурентном случае. Его стоит знать: он
встречается в больших проектах и в вопросах «чем заменяют std-примитивы».

## Когда `RwLock` лучше `Mutex`?

**Коротко.** `RwLock` пускает много читателей **или** одного писателя.
Выигрывает только при явном перекосе в сторону чтения и длинных критических
секциях; в остальных случаях `Mutex` проще и быстрее.

```rust
use std::sync::RwLock;

fn main() {
    let cache = RwLock::new(vec![1, 2, 3]);

    {
        let r1 = cache.read().unwrap();
        let r2 = cache.read().unwrap();          // два читателя одновременно
        println!("{} {}", r1.len(), r2[0]);      // 3 1
    }

    cache.write().unwrap().push(4);              // писатель — эксклюзивно
    println!("{:?}", cache.read().unwrap());     // [1, 2, 3, 4]
}
```

**Подвох.** `RwLock` дороже `Mutex` в неконкурентном случае (больше состояний
и атомарных операций), а при потоке читателей писатель может голодать —
политика зависит от платформы и не гарантируется. Плюс попытка взять `write`,
уже держа `read` в том же потоке, — дедлок.

## Какие ещё примитивы есть в `std::sync`?

**Коротко.** `Condvar` (ожидание условия), `Barrier` (дождаться N потоков),
`Once`/`OnceLock`/`LazyLock` (однократная инициализация), `mpsc`-каналы,
атомики. Семафора в `std` нет — он в `tokio::sync` или `parking_lot`.

```rust
use std::sync::{Arc, Condvar, Mutex};
use std::thread;

fn main() {
    let pair = Arc::new((Mutex::new(false), Condvar::new()));
    let p2 = Arc::clone(&pair);

    thread::spawn(move || {
        let (lock, cvar) = &*p2;
        *lock.lock().unwrap() = true;
        cvar.notify_one();
    });

    let (lock, cvar) = &*pair;
    let mut ready = lock.lock().unwrap();
    while !*ready {                              // именно while, а не if
        ready = cvar.wait(ready).unwrap();       // отпускает мьютекс на время ожидания
    }
    println!("дождались");                        // дождались
}
```

**Подвох.** `while` вместо `if` вокруг `wait` обязателен: возможны ложные
пробуждения (spurious wakeup), и условие нужно перепроверять. Это общее
правило для condvar во всех языках, и его любят спрашивать.

## Как работают атомики и что такое `Ordering`?

**Коротко.** Атомики (`AtomicUsize`, `AtomicBool`, `AtomicPtr`) — операции,
неделимые для других потоков, доступные через `&self`. Каждая операция
требует указать `Ordering` — насколько строго вокруг неё запрещено
переупорядочивание.

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use std::thread;

fn main() {
    let counter = Arc::new(AtomicUsize::new(0));

    let hs: Vec<_> = (0..4).map(|_| {
        let c = Arc::clone(&counter);
        thread::spawn(move || {
            for _ in 0..1000 { c.fetch_add(1, Ordering::Relaxed); }
        })
    }).collect();
    for h in hs { h.join().unwrap(); }

    println!("{}", counter.load(Ordering::Relaxed));   // 4000

    // compare_exchange — основа lock-free алгоритмов
    let v = AtomicUsize::new(5);
    println!("{:?}", v.compare_exchange(5, 10, Ordering::SeqCst, Ordering::SeqCst)); // Ok(5)
    println!("{:?}", v.compare_exchange(5, 20, Ordering::SeqCst, Ordering::SeqCst)); // Err(10)
}
```

| Ordering | Что гарантирует | Когда брать |
|---|---|---|
| `Relaxed` | только атомарность операции | счётчики, метрики |
| `Acquire` | после чтения не «уедет» вверх ничего из последующего | чтение флага готовности |
| `Release` | до записи всё предыдущее уже видно | публикация данных через флаг |
| `AcqRel` | и то, и другое, для read-modify-write | `fetch_update`, `compare_exchange` |
| `SeqCst` | единый глобальный порядок всех `SeqCst`-операций | когда не уверены |

Практическое правило: `Relaxed` — для счётчиков, чьё значение ничего не
синхронизирует; пара `Release`/`Acquire` — когда флаг «публикует» данные,
записанные до него; `SeqCst` — умолчание, если сомневаетесь. Цена ошибки
здесь — редко воспроизводимые баги на слабых моделях памяти (ARM), а не на
x86.

**Глубже.** ABA-проблема: значение изменилось с A на B и обратно на A, и
`compare_exchange` этого не заметит — сравнивается только значение. Отсюда
приёмы со счётчиком поколения рядом с указателем. Именно поэтому
`compare_exchange` возвращает **предыдущее** значение: чтобы можно было
построить цикл повторных попыток.

## Какая у Rust модель памяти?

**Коротко.** Формально заимствована из C++20: happens-before, атомарные
операции с `Ordering`, а **гонка данных — это UB**. Разница с C++ в том, что
в безопасном коде гонку не написать, поэтому модель памяти нужна в основном
авторам `unsafe`-кода и lock-free структур.

Что стоит удерживать в голове:

- компилятор и процессор вправе переупорядочивать доступ к памяти, если это
  не нарушает установленный `Ordering`;
- `Mutex` и каналы дают happens-before автоматически: всё, что было записано
  до `unlock`, видно после следующего `lock`;
- x86 сам по себе почти последователен, поэтому ошибка с `Relaxed`
  проявляется только на ARM — тестировать надо на целевой платформе.

## Как в Rust получаются дедлоки?

**Коротко.** Язык их не исключает. Четыре типовых способа: два мьютекса в
разном порядке, повторный `lock()` в том же потоке, guard, доживший до
`.await`, и `write` при удерживаемом `read` у `RwLock`.

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(1);

    {
        let _g = m.lock().unwrap();     // guard живёт до конца блока
        // println!("{}", *m.lock().unwrap()); // дедлок: Mutex не рекурсивный
    }                                    // здесь блокировка снята

    println!("{}", *m.lock().unwrap());  // 1

    // let _ = m.lock().unwrap();        // ошибка: non-binding let on a synchronization lock
}
```

Профилактика — стандартная: единый порядок захвата блокировок во всей
программе, минимальные критические секции, никакого пользовательского кода
(колбэков) под блокировкой, `try_lock` с таймаутом в диагностических целях.

**Подвох.** Разница между `let _ = m.lock()` и `let _g = m.lock()` — любимая
задачка на внимательность: паттерн `_` отбрасывает guard немедленно (и
критическая секция мгновенно закрывается), а имя `_g` продлевает его до конца
области видимости. Для блокировок компилятор теперь ловит первый случай
сам — линт `let_underscore_lock` включён как ошибка по умолчанию, — но для
собственных RAII-guard'ов ловушка остаётся.

**Глубже.** Удержание `std::sync::MutexGuard` через `.await` не только рискует
дедлоком, но и не компилируется в `tokio::spawn`: guard не `Send`, а задача
требует `Send`. Для длинных критических секций в async-коде берут
`tokio::sync::Mutex` — см. [async](async-await.md).
