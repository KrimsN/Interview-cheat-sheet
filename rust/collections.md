## Как устроен `Vec<T>` и почему нельзя держать ссылку на элемент во время `push`?

**Коротко.** `Vec` — это три слова на стеке (указатель на буфер в куче,
длина, ёмкость) и данные в куче. При исчерпании ёмкости он выделяет новый
буфер (обычно вдвое больше), перемещает туда элементы и освобождает старый —
все прежние адреса становятся невалидными. Поэтому `&T` на элемент и `push`
одновременно запрещены borrow checker.

```rust
fn main() {
    let mut v = Vec::new();           // Vec::new не выделяет память вовсе
    println!("{} {}", v.len(), v.capacity()); // 0 0

    for i in 0..5 { v.push(i); }
    println!("{} {}", v.len(), v.capacity()); // 5 8 — рост удвоением

    let first = &v[0];
    // v.push(6);                     // ошибка: cannot borrow `v` as mutable
    println!("{first}");              // 0

    let mut w = Vec::with_capacity(100); // одна аллокация заранее
    w.extend(0..100);
    println!("{}", w.capacity());     // 100
}
```

В C++ ровно та же реаллокация делает итераторы невалидными, но это ловится
только в рантайме (и то не всегда). В Rust это ошибка компиляции.

**Подвох.** «Rust мешает работать» — здесь он мешает написать
use-after-free. Правильный ответ на вопрос «как обойти»: работать с
индексами, а не со ссылками, либо разнести операции по времени, либо
зарезервировать ёмкость заранее.

## Какие коллекции есть в `std` и как выбирать между ними?

**Коротко.** По умолчанию — `Vec` и `HashMap`; всё остальное берут под
конкретную задачу.

| Коллекция | Что внутри | Когда брать |
|---|---|---|
| `Vec<T>` | динамический массив | по умолчанию для последовательностей |
| `VecDeque<T>` | кольцевой буфер | очередь: O(1) с обоих концов |
| `HashMap<K, V>` | хеш-таблица (SwissTable) | ассоциативный доступ, O(1) амортизированно |
| `BTreeMap<K, V>` | B-дерево | нужен порядок и диапазонные запросы |
| `HashSet` / `BTreeSet` | те же карты без значений | множества |
| `BinaryHeap<T>` | двоичная куча (max) | приоритетная очередь |
| `LinkedList<T>` | двусвязный список | практически никогда |

```rust
use std::collections::{BTreeMap, BinaryHeap, VecDeque};
use std::cmp::Reverse;

fn main() {
    let mut q: VecDeque<i32> = VecDeque::new();
    q.push_back(1); q.push_front(0);
    println!("{:?}", q);                        // [0, 1]

    let mut heap = BinaryHeap::new();           // max-heap
    heap.push(Reverse(5)); heap.push(Reverse(1)); // Reverse превращает в min-heap
    println!("{:?}", heap.pop());               // Some(Reverse(1))

    let mut b = BTreeMap::new();
    for (k, v) in [(3, "c"), (1, "a"), (2, "b")] { b.insert(k, v); }
    println!("{:?}", b);                        // {1: "a", 2: "b", 3: "c"} — всегда в порядке
    println!("{:?}", b.range(2..).collect::<Vec<_>>()); // [(2, "b"), (3, "c")]
}
```

**Подвох.** `LinkedList` в Rust почти всегда медленнее `Vec` даже там, где
«по учебнику» он выигрывает: нет локальности кеша, каждый узел — отдельная
аллокация. Плюс безопасно писать по нему алгоритмы неудобно. Стандартная
библиотека это прямо признаёт в собственной документации.

## Почему порядок итерации `HashMap` каждый раз разный?

**Коротко.** По умолчанию `HashMap` использует SipHash 1-3 со случайным
ключом, генерируемым при старте процесса. Это защита от HashDoS — атаки, когда
злоумышленник подбирает ключи с одинаковым хешем и превращает O(1) в O(n).
Побочный эффект — неопределённый и меняющийся между запусками порядок.

```rust
use std::collections::HashMap;

fn main() {
    let mut m = HashMap::new();
    for (k, v) in [("a", 1), ("b", 2), ("c", 3)] { m.insert(k, v); }
    // порядок вывода не определён и отличается между запусками
    println!("{:?}", m);

    // детерминированный обход — через сортировку или BTreeMap
    let mut items: Vec<_> = m.iter().collect();
    items.sort_by_key(|(k, _)| *k);
    println!("{items:?}");   // [("a", 1), ("b", 2), ("c", 3)]
}
```

Если хеширование в профиле — узкое место, а вход не контролируется
злоумышленником (внутренние ключи, компилятор, кеши), стандартный хешер
меняют на быстрый: `rustc-hash` (`FxHashMap`) или `ahash`.

**Подвох.** Не путайте с Go: там порядок итерации карты рандомизируется
специально при каждом обходе, чтобы никто не полагался на него. В Rust
рандомизирован ключ хеша (на процесс), а не сам обход.

## Что такое entry API и зачем оно нужно?

**Коротко.** `entry` даёт единственную операцию вместо пары «проверил —
вставил»: один поиск по таблице, одно заимствование карты и никаких гонок с
borrow checker.

```rust
use std::collections::HashMap;

fn main() {
    let words = ["мы", "и", "мы", "они", "мы"];

    // счётчик
    let mut counts: HashMap<&str, u32> = HashMap::new();
    for w in words { *counts.entry(w).or_insert(0) += 1; }
    println!("{}", counts["мы"]);       // 3

    // группировка: значение конструируется только при первой вставке
    let mut by_len: HashMap<usize, Vec<&str>> = HashMap::new();
    for w in words { by_len.entry(w.len()).or_default().push(w); }
    println!("{:?}", by_len.get(&4));   // Some(["мы", "мы", "мы"]) — «мы» это 4 байта

    // and_modify + or_insert — обновить или создать
    let mut m: HashMap<&str, i32> = HashMap::new();
    m.entry("x").and_modify(|v| *v += 1).or_insert(10);
    println!("{:?}", m.get("x"));       // Some(10)
}
```

Наивный вариант `if !map.contains_key(k) { map.insert(k, ...) }` делает два
поиска и в случае с `&mut`-доступом упирается в двойное заимствование.

**Подвох.** `or_insert(expensive())` вычисляет аргумент **всегда**, даже если
ключ уже есть. Когда значение дорогое — `or_insert_with(|| expensive())` или
`or_default()`.

## Какие требования к ключам `HashMap` и `BTreeMap`?

**Коротко.** Для `HashMap` — `Hash + Eq`, причём согласованные: равные
значения обязаны давать равный хеш. Для `BTreeMap` — `Ord`. И ключ **не
должен меняться, пока лежит в коллекции**.

```rust
use std::collections::HashMap;

#[derive(Hash, PartialEq, Eq, Debug)]
struct Key { id: u32, tag: String }

fn main() {
    let mut m = HashMap::new();
    m.insert(Key { id: 1, tag: "a".into() }, "значение");
    println!("{:?}", m.get(&Key { id: 1, tag: "a".into() })); // Some("значение")
}
```

Если ключ мутировать через внутреннюю изменяемость, его хеш изменится и
элемент «потеряется»: он останется в старом bucket, и найти его будет нельзя.
Это не нарушение безопасности памяти, а логическая ошибка — ровно как в
Python при использовании изменяемого объекта в роли ключа.

**Глубже.** `f64` не реализует `Eq` и `Ord` (из-за `NaN`, для которого
`NaN != NaN`), поэтому его нельзя использовать ключом напрямую. Обходы:
обёртка `ordered_float::NotNan`, целочисленное представление или
сортировка через `sort_by(|a, b| a.partial_cmp(b).unwrap())`.

## Чем `iter`, `iter_mut` и `into_iter` отличаются?

**Коротко.** `iter()` даёт `&T`, `iter_mut()` — `&mut T`, `into_iter()` —
`T` и потребляет коллекцию. В цикле `for` вид выбирается тем, что вы написали
после `in`.

```rust
fn main() {
    let mut v = vec![1, 2, 3];

    for x in v.iter() { print!("{x} "); }        // 1 2 3    (&i32)
    println!();
    for x in v.iter_mut() { *x *= 10; }          // изменяем на месте
    println!("{v:?}");                            // [10, 20, 30]

    let sum: i32 = v.iter().sum();
    println!("{sum}");                            // 60

    for x in v { print!("{x} "); }                // into_iter: v потреблён
    println!();
    // println!("{v:?}");                         // ошибка: value moved
}
```

**Подвох.** Классическая ловушка — `for x in v` вместо `for x in &v`, после
чего вектор недоступен ниже по коду. Компилятор в этом случае прямо
предлагает добавить `&`.

## Какие методы коллекций заменяют ручные циклы?

**Коротко.** Почти любой цикл «пройти и что-то изменить» имеет готовый
метод: `retain`, `drain`, `dedup`, `swap_remove`, `sort_unstable_by_key`,
`binary_search`, `chunks`, `windows`, `split_at_mut`.

```rust
fn main() {
    let mut v = vec![5, 1, 5, 3, 2];

    v.sort_unstable();                  // быстрее stable, порядок равных не важен
    println!("{v:?}");                  // [1, 2, 3, 5, 5]
    v.dedup();                          // убирает соседние дубли
    println!("{v:?}");                  // [1, 2, 3, 5]
    println!("{:?}", v.binary_search(&3)); // Ok(2)

    v.retain(|&x| x != 1);              // фильтрация на месте
    println!("{v:?}");                  // [2, 3, 5]

    let removed: Vec<_> = v.drain(..1).collect(); // вынуть часть, не копируя остаток
    println!("{removed:?} {v:?}");      // [2] [3, 5]

    let data = [1, 2, 3, 4, 5];
    println!("{:?}", data.chunks(2).collect::<Vec<_>>());  // [[1, 2], [3, 4], [5]]
    println!("{:?}", data.windows(2).collect::<Vec<_>>()); // [[1, 2], [2, 3], [3, 4], [4, 5]]
}
```

`swap_remove` удаляет за O(1), поменяв элемент с последним (порядок ломается);
`remove` — за O(n) со сдвигом.

**Подвох.** `HashMap::get` возвращает `Option<&V>`, а индексация `map[&k]`
**паникует** на отсутствующем ключе. Это отличается и от Python
(`KeyError` — исключение, которое ловят), и от Go, где отсутствующий ключ
молча даёт нулевое значение. Идиоматично — `get`, `entry` или
`get(&k).copied().unwrap_or(0)`.

**Глубже.** В сигнатурах функций принимайте `&[T]`, а не `&Vec<T>`: срез
примут и вектор, и массив, и часть буфера, а лишнего уровня косвенности не
будет. То же правило, что `&str` вместо `&String` в [строках](strings.md).
