## Как в Rust устроена обработка ошибок без исключений?

**Коротко.** Две категории сбоев: восстановимые возвращаются как значение
`Result<T, E>`, невосстановимые роняют поток через `panic!`. Исключений,
которые «летят» сквозь стек и ловятся где-то наверху, в языке нет.

```rust
use std::fs;
use std::io;

fn read_config(path: &str) -> Result<String, io::Error> {
    fs::read_to_string(path)   // Result<String, io::Error>
}

fn main() {
    match read_config("нет-такого-файла.toml") {
        Ok(text) => println!("прочитали {} байт", text.len()),
        Err(e) => println!("ошибка: {e}"), // ошибка: The system cannot find the file specified.
    }
}
```

Что это даёт: сигнатура функции честно говорит, что она может не сработать;
ошибку нельзя молча проигнорировать (`Result` помечен `#[must_use]`, за
пропуск ругается компилятор); нет невидимых путей выхода из функции, а
значит, проще рассуждать о том, что произойдёт с ресурсами.

**Подвох.** «Значит, в Rust ошибки обрабатывают как в Go — через `if err !=
nil`». Механически похоже, но есть разница: `Result` нельзя проигнорировать
(в Go можно `_ =`), он несёт значение **или** ошибку, а не оба сразу, а
оператор `?` убирает бойлерплейт, которого в Go нет.

## Что делает оператор `?`

**Коротко.** Разворачивает `Ok`/`Some`, а в случае `Err`/`None` немедленно
возвращает его из функции, применив к ошибке преобразование `From`.

```rust
use std::num::ParseIntError;

fn sum_two(a: &str, b: &str) -> Result<i64, ParseIntError> {
    let x: i64 = a.parse()?;   // при ошибке — ранний return Err(...)
    let y: i64 = b.parse()?;
    Ok(x + y)
}

fn main() {
    println!("{:?}", sum_two("2", "40"));   // Ok(42)
    println!("{:?}", sum_two("2", "x").is_err()); // true
}
```

Автоматическое `From` — ключевая часть: если функция возвращает `MyError`, а
внутри вызывается что-то с `io::Error`, достаточно реализовать
`impl From<io::Error> for MyError`, и `?` сам сконвертирует.

`?` работает и в `main`, если она объявлена как
`fn main() -> Result<(), Box<dyn std::error::Error>>` — тогда `Err` печатается
через `Debug`, а процесс завершается с кодом 1.

**Подвох.** `?` в функции, возвращающей `Option`, тоже работает, но смешивать
нельзя: `Option` не превращается в `Result` автоматически. Мосты между ними —
`ok_or`/`ok_or_else` (`Option → Result`) и `.ok()` (`Result → Option`).

**Глубже.** До Rust 1.13 роль `?` играл макрос `try!`; сейчас он устаревший, и
вопрос «чем `?` отличается от `try!`» — проверка на знание истории:
семантика та же, `?` короче и не конфликтует с ключевым словом `try`.

## Как объявить собственный тип ошибки?

**Коротко.** Enum с вариантами-причинами плюс реализации `Display` и
`std::error::Error` (с `source()` для цепочки). Руками это пишется один раз,
в реальном коде генерируется макросом `thiserror`.

```rust
use std::fmt;

#[derive(Debug)]
enum ConfigError {
    NotFound { path: String },
    Invalid(std::num::ParseIntError),
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            ConfigError::NotFound { path } => write!(f, "конфиг не найден: {path}"),
            ConfigError::Invalid(_) => write!(f, "некорректное значение в конфиге"),
        }
    }
}

impl std::error::Error for ConfigError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            ConfigError::Invalid(e) => Some(e), // цепочка причин
            _ => None,
        }
    }
}

impl From<std::num::ParseIntError> for ConfigError {
    fn from(e: std::num::ParseIntError) -> Self { ConfigError::Invalid(e) }
}

fn parse_port(s: &str) -> Result<u16, ConfigError> {
    let n: u16 = s.parse()?;   // сработает From
    Ok(n)
}

fn main() {
    println!("{}", parse_port("x").unwrap_err()); // некорректное значение в конфиге
}
```

То же самое с `thiserror` — примерно десять строк:

```rust
#[derive(Debug, thiserror::Error)]
enum ConfigError {
    #[error("конфиг не найден: {path}")]
    NotFound { path: String },
    #[error("некорректное значение в конфиге")]
    Invalid(#[from] std::num::ParseIntError),
}
```

## Когда `thiserror`, когда `anyhow`, когда `Box<dyn Error>`?

**Коротко.** Библиотека — конкретный enum (`thiserror`): вызывающий должен
уметь разобрать причину и отреагировать по-разному. Приложение — стёртый тип
с контекстом (`anyhow`): наверху всё равно только логируют.
`Box<dyn Error>` — вариант без зависимостей, для прототипов и `main`.

```rust
use anyhow::{Context, Result};

fn load(path: &str) -> Result<String> {
    std::fs::read_to_string(path)
        .with_context(|| format!("не удалось прочитать {path}"))
}

fn main() {
    if let Err(e) = load("нет.toml") {
        println!("{e:#}");
        // не удалось прочитать нет.toml: The system cannot find the file specified.
    }
}
```

`with_context` навешивает человекочитаемый слой поверх низкоуровневой
ошибки — в логе видно и «что делали», и «что сломалось». Это и есть главное
преимущество перед голым `?`.

**Подвох.** `anyhow` в публичном API библиотеки — антипаттерн: пользователь
получает непрозрачный тип и не может написать `match` по причинам, ему
остаётся только напечатать сообщение. Ровно тот же спор, что в Go про
sentinel-ошибки против типизированных.

**Глубже.** Сворачивание множества результатов делается через `collect`:
`iter.map(parse).collect::<Result<Vec<_>, _>>()` даёт `Ok(vec)` или первую
ошибку. Это работает потому, что для `Result` реализован `FromIterator` —
приём, который стоит знать наизусть.

## Когда паника уместна, а когда нет?

**Коротко.** Паника — для ошибок программиста и нарушенных инвариантов:
состояние, которого не должно быть. Всё, что зависит от внешнего мира (ввод
пользователя, сеть, файлы, парсинг), — это `Result`.

Источники паники: `panic!`, `unwrap`, `expect`, выход за границы среза,
целочисленное переполнение в debug-сборке, деление на ноль, двойное
заимствование `RefCell`, `.unwrap()` на отравленном мьютексе.

```rust
fn main() {
    let v = vec![1, 2, 3];
    println!("{:?}", v.get(10));   // None — безопасный доступ
    // println!("{}", v[10]);      // паника: index out of bounds: the len is 3 but the index is 10
}
```

По умолчанию паника **раскручивает стек** (unwind), вызывая деструкторы, и
завершает поток. В профиле можно выбрать `panic = "abort"` — без раскрутки,
меньше бинарник и быстрее, но деструкторы не отработают:

```toml
[profile.release]
panic = "abort"
```

**Подвох.** `catch_unwind` существует, но это не механизм обработки ошибок:
он нужен на границе [FFI](unsafe-ffi.md) (раскрутка через чужой кадр стека —
UB) и в тестовых раннерах. Использовать его как `try/catch` — плохая
практика, к тому же он не поймает панику при `panic = "abort"`.

**Глубже.** Паника в потоке роняет только этот поток; `JoinHandle::join`
вернёт `Err` с полезной нагрузкой паники. В async-задаче Tokio то же самое:
задача завершается, `JoinError::is_panic()` это показывает, рантайм
продолжает работать.

## Чем `unwrap` отличается от `expect` и когда их можно писать?

**Коротко.** Оба паникуют, но `expect` печатает ваше сообщение. В тестах,
примерах и прототипах — нормально; в библиотечном коде — почти никогда; в
приложении — только там, где нарушение действительно означает баг.

```rust
fn main() {
    let cfg: Option<u16> = Some(8080);
    let port = cfg.expect("порт должен быть проставлен на этапе загрузки конфига");
    println!("{port}"); // 8080
}
```

Хорошее сообщение `expect` описывает **инвариант, который нарушен**, а не
действие: не «не удалось получить порт», а «порт должен быть проставлен
раньше». Тогда по логу видно, какое предположение оказалось неверным.

**Глубже.** Переменная окружения `RUST_BACKTRACE=1` включает печать стека при
панике, `RUST_BACKTRACE=full` — с системными кадрами. Полезное умолчание для
сервисов: включать в staging и оставлять выключенным в проде, если стек может
попасть в пользовательский вывод.
