## Чем дженерики Rust отличаются от шаблонов C++ и от дженериков Java?

**Коротко.** Обобщённый код в Rust проверяется **на месте определения**: если
внутри вызывается метод, он должен быть заявлен в границах. В C++ шаблон
проверяется при инстанцировании, поэтому ошибки всплывают в точке
использования простынёй текста. В Java дженерики стираются в рантайме, в Rust
— мономорфизируются, то есть код генерируется под каждый конкретный тип.

```rust
// не скомпилируется: компилятор не знает, что T умеет сравниваться
// fn largest<T>(list: &[T]) -> &T {
//     let mut m = &list[0];
//     for x in list { if x > m { m = x; } }   // error: binary operation `>` cannot be applied
//     m
// }

fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut m = &list[0];
    for x in list { if x > m { m = x; } }
    m
}

fn main() {
    println!("{}", largest(&[3, 7, 2]));               // 7
    println!("{}", largest(&["груша", "яблоко"]));     // яблоко
}
```

Практический вывод для собеседования: контракт обобщённой функции полностью
описан её сигнатурой. Читая `fn f<T: Clone + Send>(x: T)`, вы знаете всё, что
функция может делать с `T`, — заглядывать в тело не нужно.

## Что такое мономорфизация и чем за неё платят?

**Коротко.** Компилятор порождает отдельную копию функции под каждый набор
конкретных типов. Плюс — инлайнинг и нулевая цена абстракции; минус —
раздувание бинарника и время компиляции.

```rust
fn print_it<T: std::fmt::Debug>(x: T) { println!("{x:?}"); }

fn main() {
    print_it(1u8);      // сгенерируется print_it::<u8>
    print_it("текст");  // и print_it::<&str>
    print_it(vec![1]);  // и print_it::<Vec<i32>>
}
```

Именно мономорфизация — настоящая причина, почему Rust компилируется долго:
крейт с обильными дженериками и итераторными цепочками разворачивается в
огромное количество экземпляров, которые потом ещё и оптимизирует LLVM.

**Подвох.** Типичный вопрос «как уменьшить раздувание». Стандартный приём —
тонкая обобщённая обёртка поверх не-обобщённого ядра:

```rust
use std::path::Path;

fn open(path: impl AsRef<Path>) -> std::io::Result<Vec<u8>> {
    fn inner(path: &Path) -> std::io::Result<Vec<u8>> {  // одна копия кода
        std::fs::read(path)
    }
    inner(path.as_ref())                                  // копируется только это
}

fn main() { println!("{}", open("Cargo.toml").is_ok() || true); } // true
```

Так устроены многие функции в `std`. Второй способ — заменить дженерик на
`dyn Trait` там, где производительность не критична.

## Что означает `impl Trait` в аргументе и в возвращаемом типе?

**Коротко.** В аргументе — сахар для обобщённого параметра («любой тип,
реализующий трейт»). В возвращаемом типе — «конкретный тип, который я не
называю»: он один и тот же для всех вызовов, просто скрыт от вызывающего.

```rust
fn takes(x: impl std::fmt::Display) { println!("{x}"); }
// эквивалент: fn takes<T: Display>(x: T)

fn make_adder(n: i32) -> impl Fn(i32) -> i32 {
    move |x| x + n        // тип замыкания анонимный, назвать его нельзя
}

fn evens(limit: u32) -> impl Iterator<Item = u32> {
    (0..limit).filter(|x| x % 2 == 0)   // тип Filter<Range<u32>, {closure}> — не пишут руками
}

fn main() {
    takes("привет");                          // привет
    println!("{}", make_adder(5)(37));        // 42
    println!("{:?}", evens(6).collect::<Vec<_>>()); // [0, 2, 4]
}
```

Разница с `dyn`: `impl Trait` в возврате — **один** конкретный тип, поэтому
две ветки `if` не могут вернуть разные типы. Для этого нужен
`Box<dyn Trait>`.

```rust
fn pick(flag: bool) -> Box<dyn Fn(i32) -> i32> {
    if flag { Box::new(|x| x + 1) } else { Box::new(|x| x * 2) }
}
```

**Глубже.** `impl Trait` в аргументе слегка слабее дженерика: у него нет
имени, поэтому его нельзя задать явно через turbofish и нельзя связать два
аргумента одним типом. Когда важно «оба аргумента одного типа», пишут
`<T: Trait>(a: T, b: T)`.

## Что такое turbofish и зачем он нужен?

**Коротко.** `::<>` — способ указать обобщённые параметры явно, когда вывод
типов не справляется. Чаще всего — при `collect` и `parse`.

```rust
fn main() {
    let v = (1..4).collect::<Vec<i32>>();      // turbofish
    let w: Vec<i32> = (1..4).collect();        // то же через аннотацию переменной
    let n = "42".parse::<u32>().unwrap();
    println!("{v:?} {w:?} {n}");               // [1, 2, 3] [1, 2, 3] 42
}
```

`collect` полиморфен по результату — он умеет собирать в `Vec`, `String`,
`HashMap`, `Result<Vec<_>, E>`, — поэтому без подсказки компилятор
не выберет тип и попросит аннотацию.

## Что такое const generics?

**Коротко.** Параметр-константа в типе: `struct Matrix<const R: usize, const
C: usize>`. Даёт массивы фиксированного размера в обобщённом коде и проверку
размеров на этапе компиляции.

```rust
#[derive(Debug)]
struct Vector<const N: usize>([f64; N]);

impl<const N: usize> Vector<N> {
    fn dot(&self, other: &Vector<N>) -> f64 {
        self.0.iter().zip(other.0.iter()).map(|(a, b)| a * b).sum()
    }
}

fn main() {
    let a = Vector([1.0, 2.0, 3.0]);
    let b = Vector([4.0, 5.0, 6.0]);
    println!("{}", a.dot(&b));      // 32
    // a.dot(&Vector([1.0]));       // ошибка компиляции: размеры не совпадают
}
```

До const generics (стабилизированы в 1.51) `std` реализовывал трейты для
массивов вручную до длины 32 — отсюда старая шутка про «`[T; 33]` ничего не
умеет».

**Глубже.** GAT (generic associated types, стабильны с 1.65) — ассоциированные
типы с собственными параметрами, в первую очередь по временам жизни. Главная
практическая мотивация — «лендинг-итераторы», отдающие ссылки на собственный
буфер, и абстракции над async-кодом.

```rust
trait LendingIterator {
    type Item<'a> where Self: 'a;
    fn next(&mut self) -> Option<Self::Item<'_>>;
}
```

## Правда ли, что итератор компилируется в тот же код, что и цикл?

**Коротко.** Как правило да — это и есть «zero-cost abstraction» на практике.
Цепочка адаптеров разворачивается в один цикл, а итерация по срезу часто ещё
и убирает проверку границ, которая осталась бы при индексации.

```rust
// эти две функции обычно дают одинаковый машинный код
fn sum_loop(v: &[u32]) -> u32 {
    let mut s = 0;
    for i in 0..v.len() { s += v[i]; }   // здесь компилятору нужно доказать, что i < len
    s
}

fn sum_iter(v: &[u32]) -> u32 {
    v.iter().sum()                        // границы проверять не нужно по построению
}

fn main() {
    let v: Vec<u32> = (1..=10).collect();
    println!("{} {}", sum_loop(&v), sum_iter(&v)); // 55 55
}
```

**Подвох.** «Обычно» — не «всегда». Правильный ответ на собеседовании: это
проверяется, а не постулируется — через Compiler Explorer (сравнить
ассемблер), `cargo asm` или бенчмарк на `criterion`. Заявление «итераторы
всегда быстрее циклов» так же неверно, как обратное.

## Чего в дженериках Rust нет?

**Коротко.** Нет специализации (стабильной), нет негативных границ, нет
вариативных обобщений (переменное число параметров типа), нет перегрузки
функций по арности.

- **Специализация** («для `T = u8` возьми более быструю реализацию»)
  существует только на nightly и вряд ли скоро стабилизируется. Обходы:
  отдельный трейт с разными реализациями, внутренние функции, приёмы с
  `TypeId`.
- **Негативных границ** (`T: !Clone`) нет — иначе добавление реализации в
  зависимости ломало бы компиляцию у пользователей.
- **Перегрузка** заменяется трейтами: `From<A>` и `From<B>` для одного типа —
  это и есть «перегрузка конструктора».

**Подвох.** Частый вопрос: «сколько копий сгенерируется для функции с тремя
параметрами типа?» Ответ — по одной на каждую фактически использованную
комбинацию; неиспользованные комбинации не порождают код вовсе, потому что
мономорфизация ленивая, от точек вызова.
