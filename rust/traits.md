## Что такое трейт и чем он отличается от интерфейса в Go или Java?

**Коротко.** Трейт — контракт поведения: набор сигнатур методов, которые тип
обязуется реализовать. Ключевое отличие — реализация **явная**
(`impl Trait for Type`), а не структурная, как в Go, и не по факту наличия
метода, как duck typing в Python.

```rust
trait Greet {
    fn name(&self) -> String;

    // дефолтный метод: реализация получается бесплатно
    fn greet(&self) -> String { format!("Привет, {}!", self.name()) }
}

struct User { login: String }

impl Greet for User {
    fn name(&self) -> String { self.login.clone() }
}

fn main() {
    let u = User { login: "ann".into() };
    println!("{}", u.greet()); // Привет, ann!
}
```

Явность важна: в Go тип случайно удовлетворяет интерфейсу, если у него совпали
имена методов, — иногда это удобно, иногда даёт неожиданные реализации. В Rust
реализация — намеренное утверждение автора типа (или автора трейта).

Дефолтные методы позволяют расширять трейт, не ломая существующие реализации.
Так устроен `Iterator`: реализуете один `next`, получаете `map`, `filter`,
`fold` и ещё сотню методов.

**Подвох.** Трейт — не класс: у него нет полей и нет наследования реализации.
Супертрейт (`trait Ord: Eq`) — это только **требование** реализовать другой
трейт, а не переиспользование его кода.

## Что такое orphan rule и как его обходят?

**Коротко.** Реализовать трейт можно, если в вашем крейте определён либо сам
трейт, либо тип. Чужой трейт для чужого типа — нельзя. Это правило
когерентности: оно гарантирует, что во всей программе существует ровно одна
реализация трейта для типа.

```rust
// impl std::fmt::Display for Vec<u8> {}  // ошибка: only traits defined in
                                          // the current crate can be implemented
                                          // for types defined outside of the crate

use std::fmt;

struct Bytes(Vec<u8>);          // newtype — тип уже наш

impl fmt::Display for Bytes {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        for b in &self.0 { write!(f, "{b:02x}")?; }
        Ok(())
    }
}

fn main() { println!("{}", Bytes(vec![0xde, 0xad])); } // dead
```

Без этого правила два крейта могли бы независимо реализовать
`Display for Vec<u8>` по-разному, и линковка двух библиотек в одном проекте
ломала бы программу. В Go и Python такой проблемы нет по другой причине: там
нет глобального разрешения реализаций на этапе компиляции.

**Глубже.** Newtype-обёртка ничего не стоит в рантайме (особенно с
`#[repr(transparent)]`), но требует ручного проброса методов внутреннего типа.
Частично это лечит реализация `Deref`, хотя злоупотреблять ей не стоит: см.
[идиомы](idioms-api-design.md).

## Когда ассоциированный тип, а когда параметр типа?

**Коротко.** Ассоциированный тип — когда на один реализующий тип должна
приходиться **ровно одна** реализация. Параметр типа — когда реализаций для
одного типа должно быть много.

```rust
trait Container {
    type Item;                       // один Item на контейнер
    fn get(&self, i: usize) -> Option<&Self::Item>;
}

struct Bag(Vec<String>);

impl Container for Bag {
    type Item = String;
    fn get(&self, i: usize) -> Option<&String> { self.0.get(i) }
}

fn main() {
    let b = Bag(vec!["a".into(), "b".into()]);
    println!("{:?}", b.get(1));      // Some("b")

    // From<T> — параметр типа: реализаций много для одного и того же типа
    let s: String = String::from("x");         // From<&str>
    let t: String = String::from('y');         // From<char>
    println!("{s}{t}");                        // xy
}
```

Практическое следствие: `Iterator` имеет `type Item`, потому что один тип
итератора отдаёт элементы одного типа. А `From<T>` — параметр, потому что
`String` умеет конструироваться из `&str`, `char`, `Cow` и других.

**Подвох.** Ассоциированный тип упрощает сигнатуры: `fn sum<I: Iterator<Item =
i32>>(i: I)` вместо необходимости всюду таскать лишний параметр. Именно ради
читаемости их и вводят.

## Чем `impl Trait` отличается от `dyn Trait`?

**Коротко.** `impl Trait`/`<T: Trait>` — статическая диспетчеризация: тип
известен на этапе компиляции, код мономорфизируется и инлайнится, накладных
расходов нет. `dyn Trait` — динамическая: значение за широким указателем
(данные + vtable), вызов идёт через таблицу, зато один экземпляр кода и
разнородная коллекция.

```rust
trait Shape { fn area(&self) -> f64; }

struct Circle(f64);
struct Square(f64);

impl Shape for Circle { fn area(&self) -> f64 { 3.14159 * self.0 * self.0 } }
impl Shape for Square { fn area(&self) -> f64 { self.0 * self.0 } }

fn total_static(shapes: &[impl Shape]) -> f64 {      // все элементы одного типа
    shapes.iter().map(|s| s.area()).sum()
}

fn total_dynamic(shapes: &[Box<dyn Shape>]) -> f64 { // разные типы в одном векторе
    shapes.iter().map(|s| s.area()).sum()
}

fn main() {
    println!("{:.2}", total_static(&[Square(2.0), Square(3.0)]));  // 13.00
    let mixed: Vec<Box<dyn Shape>> = vec![Box::new(Circle(1.0)), Box::new(Square(2.0))];
    println!("{:.2}", total_dynamic(&mixed));                       // 7.14
}
```

Правило выбора: по умолчанию дженерики; `dyn` — когда нужен гетерогенный
контейнер, плагинная точка расширения или когда мономорфизация раздувает
бинарник. Цена `dyn` — косвенный вызов (обычно предсказывается процессором) и
отсутствие инлайнинга; цена дженериков — время компиляции и размер кода.

## Что такое object safety (dyn-совместимость)?

**Коротко.** Не всякий трейт можно превратить в `dyn Trait`. Мешают:
обобщённые методы, `Self` в возвращаемом типе, ассоциированные константы,
методы без `self`. Причина одна — vtable должна содержать конкретные адреса
функций с известными сигнатурами.

```rust
trait NotDyn {
    fn make() -> Self;              // нет self — нельзя вызвать через указатель
    fn clone_me(&self) -> Self;     // Self не Sized — нельзя вернуть по значению
    fn generic<T>(&self, x: T);     // мономорфизировать нечего: типы неизвестны
}
// let x: Box<dyn NotDyn> = ...;    // ошибка: the trait cannot be made into an object

trait Ok {
    fn area(&self) -> f64;                          // ок
    fn describe(&self) -> String where Self: Sized { // исключаем метод из vtable
        "фигура".into()
    }
}
```

Приём `where Self: Sized` на проблемном методе — стандартный способ оставить
трейт dyn-совместимым: такой метод просто не попадает в таблицу и доступен
только по конкретному типу.

**Подвох.** Именно поэтому `Clone` нельзя использовать как `dyn Clone`
(в нём `fn clone(&self) -> Self`). Обход — свой трейт с
`fn clone_box(&self) -> Box<dyn MyTrait>` или крейт `dyn-clone`.

## Что такое blanket impl?

**Коротко.** Реализация трейта сразу для всех типов, удовлетворяющих границе:
`impl<T: Display> ToString for T`. Так в `std` устроены `ToString`, `Into`
(через `From`), `Iterator` для всех `&mut I`.

```rust
trait Loggable {
    fn log(&self);
}

// всё, что умеет Debug, автоматически умеет и log()
impl<T: std::fmt::Debug> Loggable for T {
    fn log(&self) { println!("[log] {self:?}"); }
}

fn main() {
    42.log();                 // [log] 42
    vec!["a", "b"].log();     // [log] ["a", "b"]
}
```

Практическое следствие, о котором спрашивают: **не реализуйте `ToString`
вручную** — реализуйте `Display`, и `to_string()` появится сам. Ровно так же
`Into` не реализуют напрямую: реализуют `From`, а `Into` приходит из blanket
impl (см. [стандартные трейты](std-traits.md)).

**Подвох.** Blanket impl — частый источник конфликтов когерентности: после
него добавить в свой крейт отдельную реализацию для конкретного типа уже
нельзя, компилятор сообщит «conflicting implementations». Поэтому в публичных
библиотеках их вводят осознанно — убрать потом нельзя без слома совместимости.

## Что такое маркерные трейты?

**Коротко.** Трейты без методов, которые несут информацию компилятору, а не
поведение: `Copy`, `Send`, `Sync`, `Sized`, `Unpin`.

- `Copy` — значение можно побитово копировать
  ([владение](ownership.md));
- `Send` — значение можно переместить в другой поток;
- `Sync` — на `&T` можно ссылаться из нескольких потоков
  ([потоки](threads-send-sync.md));
- `Sized` — размер известен на этапе компиляции
  ([типы](types-memory-layout.md));
- `Unpin` — значение можно безопасно перемещать после закрепления
  ([async](async-await.md)).

Большинство из них **автоматические** (auto traits): компилятор выводит их
сам, если они есть у всех полей. Вручную их не пишут — но могут снять,
добавив поле вроде `PhantomData<*const ()>`.

**Глубже.** Границы `where` существуют ровно для читаемости: длинный список
ограничений выносят из угловых скобок вниз.

```rust
fn process<T, U>(a: T, b: U) -> String
where
    T: std::fmt::Debug + Clone + Send,
    U: IntoIterator<Item = T>,
{
    format!("{:?} {}", a, b.into_iter().count())
}
```

## Что происходит с async-методами в трейтах?

**Коротко.** `async fn` в трейтах стабилизирован в Rust 1.75, но такой трейт
**не dyn-совместим**: возвращаемый `Future` — анонимный тип, который нельзя
положить в vtable. Для `dyn` до сих пор используют крейт `async-trait` или
вручную возвращают `Pin<Box<dyn Future>>`.

```rust
trait Fetcher {
    async fn fetch(&self, url: &str) -> String;   // ок для статической диспетчеризации
}

// а вот так — для dyn:
use std::future::Future;
use std::pin::Pin;

trait DynFetcher {
    fn fetch<'a>(&'a self, url: &'a str)
        -> Pin<Box<dyn Future<Output = String> + Send + 'a>>;
}
```

Это живой вопрос на собеседованиях по async-коду: правильный ответ —
«стабилизирован, но с ограничениями по `dyn` и по `Send`-границам
возвращаемого будущего; в библиотечном API часто всё ещё `async-trait`».
