## Что именно разрешает `unsafe`?

**Коротко.** Ровно пять вещей — и borrow checker при этом продолжает
работать. `unsafe` не «выключает Rust», он снимает пять конкретных запретов.

1. разыменовать сырой указатель (`*const T`, `*mut T`);
2. вызвать `unsafe`-функцию или метод (включая любую внешнюю через FFI);
3. обратиться к изменяемой статической переменной или к полю `union`;
4. реализовать `unsafe`-трейт (`Send`, `Sync` вручную);
5. изменить поле упакованной структуры (`#[repr(packed)]`).

```rust
fn main() {
    let mut x = 5;
    let p = &mut x as *mut i32;   // создать сырой указатель можно и в safe-коде

    unsafe {
        *p += 1;                   // а вот разыменовать — только здесь
        println!("{}", *p);        // 6
    }

    // владение и заимствование проверяются как обычно:
    let s = String::from("hi");
    let t = s;
    // unsafe { println!("{s}"); } // всё та же ошибка: value moved
    println!("{t}");
}
```

**Подвох.** Самая распространённая ошибка в формулировке: «`unsafe` отключает
проверки компилятора». Правильный ответ: он расширяет список разрешённых
операций, а всю остальную проверку типов, владения и заимствований компилятор
выполняет по-прежнему.

## Что такое «безопасная абстракция над unsafe»?

**Коротко.** `unsafe`-блок — обещание программиста, что инварианты соблюдены.
Задача — спрятать его за API, который **невозможно** сломать снаружи
безопасным кодом. Так устроены `Vec`, `String`, `RefCell`, `Arc`, `Mutex` —
внутри везде `unsafe`.

```rust
/// Делит срез на две непересекающиеся изменяемые части.
fn split_mut<T>(v: &mut [T], mid: usize) -> (&mut [T], &mut [T]) {
    assert!(mid <= v.len());              // инвариант проверяем ДО unsafe
    let len = v.len();
    let ptr = v.as_mut_ptr();
    // SAFETY: mid <= len, поэтому диапазоны [0, mid) и [mid, len) не пересекаются
    // и оба лежат внутри одной аллокации.
    unsafe {
        (
            std::slice::from_raw_parts_mut(ptr, mid),
            std::slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}

fn main() {
    let mut data = [1, 2, 3, 4];
    let (a, b) = split_mut(&mut data, 2);
    a[0] = 10;
    b[0] = 30;
    println!("{data:?}");   // [10, 2, 30, 4]
}
```

Это ровно реализация `split_at_mut` из стандартной библиотеки: правило «одна
изменяемая ссылка» здесь не нарушено по существу (части не пересекаются), но
компилятор доказать этого не может — поэтому и нужен `unsafe`.

Комментарий `// SAFETY:` перед каждым блоком — обязательная в экосистеме
практика; за его отсутствие ругается clippy (`undocumented_unsafe_blocks`).

## Что считается неопределённым поведением?

**Коротко.** UB — не «программа упадёт», а «компилятор вправе делать что
угодно»: оптимизации построены на предположении, что UB не бывает. Список
конечный, и его полезно уметь перечислить.

- разыменование висячего, невыровненного или нулевого указателя;
- нарушение правил алиасинга — существование `&mut T` одновременно с любой
  другой ссылкой на те же данные;
- гонка данных (незащищённый одновременный доступ с записью);
- чтение неинициализированной памяти;
- некорректное значение типа: `bool` не 0 и не 1, невалидный `char`,
  `null`-ссылка, `enum` с несуществующим тегом;
- выход за границы аллокации при арифметике указателей;
- раскрутка стека через границу FFI.

```rust
fn main() {
    // Пример UB (не запускать в проде): создание некорректного bool
    // let b: bool = unsafe { std::mem::transmute(2u8) };
    // if b { } else { }  // компилятор вправе выполнить обе ветки или ни одной

    // Правильно — проверяемое преобразование
    let v = 2u8;
    println!("{}", v != 0);   // true
}
```

**Подвох.** «У меня работает» — не аргумент: UB может проявиться при смене
версии компилятора, уровня оптимизации или платформы. Именно поэтому
`unsafe`-код проверяют Miri, а не тестами.

## Какие опасные операции есть в стандартной библиотеке?

**Коротко.** `transmute`, `MaybeUninit`, `ptr::read`/`write`,
`slice::from_raw_parts`, `Box::from_raw`/`into_raw`, `get_unchecked`.

```rust
use std::mem::MaybeUninit;

fn main() {
    // MaybeUninit — корректный способ работать с неинициализированной памятью
    let mut slot: MaybeUninit<String> = MaybeUninit::uninit();
    slot.write(String::from("готово"));
    // SAFETY: значение записано строкой выше
    let s = unsafe { slot.assume_init() };
    println!("{s}");    // готово

    // безопасные аналоги «опасных» приёмов
    let bytes = 1u32.to_le_bytes();          // вместо transmute
    println!("{bytes:?}");                    // [1, 0, 0, 0]
    println!("{}", u32::from_le_bytes(bytes)); // 1
}
```

`transmute` — последнее средство: почти всегда есть безопасная замена
(`to_le_bytes`/`from_le_bytes`, `as`-приведение, `TryFrom`, крейты `bytemuck`
и `zerocopy` с проверками на этапе компиляции).

`get_unchecked` убирает проверку границ. Прежде чем его писать, стоит
убедиться, что проверка вообще осталась: часто компилятор её и так устраняет,
если границы очевидны из кода.

## Как устроен FFI с C?

**Коротко.** `extern "C"` задаёт соглашение о вызовах, `#[repr(C)]` —
стабильную раскладку структур, `#[unsafe(no_mangle)]` — сохранение имени
символа. Строки конвертируются через `CString`/`CStr`.

```rust
use std::ffi::{c_char, c_int, CStr, CString};

// вызываем C из Rust
unsafe extern "C" {
    fn strlen(s: *const c_char) -> usize;
}

// экспортируем Rust в C
#[unsafe(no_mangle)]
pub extern "C" fn add(a: c_int, b: c_int) -> c_int { a + b }

#[repr(C)]
pub struct Point { pub x: f64, pub y: f64 }   // раскладка как в C

fn main() {
    let s = CString::new("привет").unwrap();
    // SAFETY: указатель валиден и строка нуль-терминирована по построению CString
    let len = unsafe { strlen(s.as_ptr()) };
    println!("{len}");            // 12 — длина в байтах UTF-8

    let borrowed = unsafe { CStr::from_ptr(s.as_ptr()) };
    println!("{}", borrowed.to_str().unwrap()); // привет
    println!("{}", add(2, 40));   // 42
}
```

Ключевые ловушки FFI:

- **владение**: кто освобождает память? Указатель, полученный из C, обычно
  освобождает C; `Box::into_raw` отдаёт владение наружу, `Box::from_raw`
  забирает обратно — и ровно один раз;
- **строки**: `CString` гарантирует нуль в конце и отсутствие нулей внутри;
  `CStr::from_ptr` не копирует и требует, чтобы данные жили достаточно долго;
- **паника через границу**: раскрутка стека через кадр C — UB. В современных
  версиях `extern "C"` при панике прерывает процесс, но на границе, где это
  недопустимо, ставят `catch_unwind`.

**Глубже.** Инструменты: `bindgen` генерирует Rust-объявления из C-заголовков,
`cbindgen` — заголовки из Rust, `cxx` даёт безопасный двусторонний мост с
C++, `pyo3` — модули для Python, `wasm-bindgen` — мост с JavaScript. Ручное
описание чужого API — источник ошибок; в реальных проектах используют
генераторы.

## Как проверять `unsafe`-код?

**Коротко.** Miri — интерпретатор MIR, который ловит UB прямо в тестах:
обращения к освобождённой памяти, нарушения алиасинга, невыровненный доступ,
утечки.

```bash
rustup +nightly component add miri
```

```bash
cargo +nightly miri test
```

Miri заметно медленнее обычного запуска и не поддерживает FFI, но это самый
практичный инструмент проверки. Дополнительно: санитайзеры
(`-Zsanitizer=address`/`thread` на nightly), `cargo careful`, фаззинг
(`cargo-fuzz`) для парсеров.

**Глубже.** Модель алиасинга для `unsafe`-кода до сих пор не финализирована:
Stacked Borrows и более новая Tree Borrows — экспериментальные модели, которые
Miri и проверяет. Практический вывод: код, который Miri ругает, лучше
переписать, даже если «сейчас работает».

## Когда `unsafe` действительно нужен?

**Коротко.** В прикладном коде — почти никогда. Оправданные случаи: FFI,
низкоуровневые структуры данных (интрузивные списки, свои аллокаторы),
SIMD-интринсики, работа с железом и MMIO, точечные оптимизации,
подтверждённые бенчмарком.

Хороший ответ на собеседовании звучит примерно так: «сначала ищу безопасное
решение или проверенный крейт; если `unsafe` неизбежен — пишу минимальный
блок, документирую инварианты комментарием `// SAFETY:`, оборачиваю в
безопасный API и прогоняю Miri».

**Подвох.** Самая частая реальная ошибка с `unsafe` — не разыменование
указателя, а **ручная реализация `Send`/`Sync`**:

```rust
struct MyType { ptr: *mut u8 }

// SAFETY: обещание, которое компилятор проверить не может.
// Если оно ложно — получаем гонку данных без единого unsafe-блока в коде пользователя.
unsafe impl Send for MyType {}
```

Такое `unsafe impl` снимает защиту сразу со всего многопоточного кода,
который использует тип, — см. [потоки](threads-send-sync.md).
