## Чем enum в Rust отличается от enum в C и от классов-наследников?

**Коротко.** Это полноценный алгебраический тип-сумма: каждый вариант может
нести собственные данные разной формы. Значение — «ровно одно из», и
компилятор знает полный список вариантов.

```rust
enum Shape {
    Point,                        // без данных
    Circle(f64),                  // кортежный вариант
    Rect { w: f64, h: f64 },      // структурный вариант
}

fn area(s: &Shape) -> f64 {
    match s {
        Shape::Point => 0.0,
        Shape::Circle(r) => std::f64::consts::PI * r * r,
        Shape::Rect { w, h } => w * h,
    }
}

fn main() {
    let shapes = [Shape::Point, Shape::Circle(1.0), Shape::Rect { w: 2.0, h: 3.0 }];
    for s in &shapes { print!("{:.2} ", area(s)); } // 0.00 3.14 6.00
    println!();
}
```

Сравните с иерархией классов: там набор наследников открыт (кто угодно
добавит новый в своём модуле), и добавление метода требует правки всех
классов. Enum — наоборот: набор вариантов закрыт, добавить обработку легко,
добавить вариант — значит починить все `match`. Это компромисс «expression
problem», и на собеседовании полезно уметь назвать обе стороны: трейт-объекты
открыты по типам, enum — по операциям.

**Глубже.** Enum занимает размер тега плюс наибольшего варианта, поэтому
«толстые» варианты боксируют — см. [представление в
памяти](types-memory-layout.md).

## Почему `Option<T>` лучше, чем `null`?

**Коротко.** Отсутствие значения выражено в типе, а не в значении:
`Option<T>` и `T` — разные типы, и компилятор не даст обратиться к содержимому,
не обработав `None`. «Ошибки на миллиард долларов» (null dereference) в
безопасном Rust не существует.

```rust
fn find(v: &[i32], target: i32) -> Option<usize> {
    v.iter().position(|&x| x == target)
}

fn main() {
    let v = [10, 20, 30];

    match find(&v, 20) {
        Some(i) => println!("нашли на позиции {i}"), // нашли на позиции 1
        None => println!("нет такого"),
    }

    // комбинаторы вместо match, когда логика простая
    println!("{}", find(&v, 99).map_or(-1, |i| i as i32)); // -1
    println!("{}", find(&v, 30).unwrap_or(0));             // 2
}
```

Практическая разница с языками, где null есть у любого типа: там каждая
переменная потенциально null и проверки расставляют «на всякий случай». Здесь
`Option` в сигнатуре — это документация, а его отсутствие — гарантия.

**Подвох.** `Option<&T>` и `&Option<T>` — разные типы. Перевести одно в
другое: `opt.as_ref()` даёт `Option<&T>`, `as_deref()` — `Option<&str>` из
`Option<String>`. Путаница здесь — типовая ошибка на живом кодировании.

## Что даёт исчерпывающий `match`?

**Коротко.** Компилятор проверяет, что покрыты все варианты; непокрытый —
ошибка `E0004` «non-exhaustive patterns». Значит, добавив вариант в enum, вы
получаете список всех мест, где нужно дописать логику.

```rust
enum Event { Connected, Disconnected, Message(String) }

fn handle(e: Event) -> String {
    match e {
        Event::Connected => "подключились".into(),
        Event::Disconnected => "отключились".into(),
        Event::Message(text) => format!("сообщение: {text}"),
        // убрать любую ветку — ошибка компиляции
    }
}

fn main() { println!("{}", handle(Event::Message("hi".into()))); } // сообщение: hi
```

Это главный аргумент против «строковых типов» (`kind: String`) и `i32`-кодов:
с ними компилятор не поможет, а забытая ветка обнаружится в проде.

**Подвох.** Ветка `_ => {}` отключает эту проверку: добавленный позже вариант
молча уедет в неё. В коде, где важно не пропустить новые состояния, `_`
не пишут вовсе или используют `#[deny(non_exhaustive_omitted_patterns)]`.
Обратная сторона: enum из чужого крейта, помеченный
`#[non_exhaustive]`, **требует** `_`-ветку — иначе добавление варианта было бы
ломающим изменением.

## Какие бывают образцы?

**Коротко.** Литералы, диапазоны, деструктуризация структур, кортежей и
срезов, вложенные образцы, `|` для альтернатив, `_` и `..` для игнорирования,
`@` для привязки, `if`-guard для условий.

```rust
struct Point { x: i32, y: i32 }

fn describe(n: i32) -> &'static str {
    match n {
        0 => "ноль",
        1 | 2 | 3 => "мало",
        4..=9 => "средне",
        x if x < 0 => "отрицательное",
        _ => "много",
    }
}

fn main() {
    println!("{} {}", describe(2), describe(7)); // мало средне

    let p = Point { x: 0, y: 7 };
    match p {
        Point { x: 0, y } => println!("на оси Y, y = {y}"), // на оси Y, y = 7
        Point { x, .. } => println!("x = {x}"),
    }

    let v = [1, 2, 3, 4];
    match v {
        [first, .., last] => println!("{first} {last}"),    // 1 4
    }

    let msg = 5;
    match msg {
        n @ 1..=9 => println!("цифра {n}"),                  // цифра 5
        n => println!("число {n}"),
    }
}
```

**Глубже.** Guard-условие (`x if x < 0`) не участвует в проверке
исчерпаемости: компилятор не умеет доказывать, что условия покрывают всё,
поэтому после ветки с guard всё равно нужна безусловная. И ещё: guard не
может изменять сопоставляемое значение — он получает его по ссылке.

## Когда `if let`, `while let` и `let ... else`?

**Коротко.** `if let` — когда интересен один вариант из многих; `while let` —
цикл, пока сопоставление удаётся; `let ... else` — ранний выход без
вложенности (стабилен с Rust 1.65).

```rust
fn parse_port(s: &str) -> Option<u16> {
    let Ok(port) = s.parse::<u16>() else {
        return None;              // else-ветка обязана расходиться
    };
    if port == 0 { return None; }
    Some(port)
}

fn main() {
    let cfg: Option<&str> = Some("8080");
    if let Some(value) = cfg {
        println!("порт из конфига: {value}");   // порт из конфига: 8080
    }

    let mut stack = vec![1, 2, 3];
    while let Some(top) = stack.pop() { print!("{top} "); } // 3 2 1
    println!();

    println!("{:?} {:?}", parse_port("8080"), parse_port("nope")); // Some(8080) None
    println!("{}", matches!(cfg, Some(s) if s.starts_with('8'))); // true
}
```

`let ... else` — прямая замена «лестницы» из `match` с одним интересным
вариантом: happy path остаётся на верхнем уровне вложенности.

**Подвох.** Простой `let Some(x) = opt;` не компилируется: образец
**опровержимый** (может не совпасть), а `let` требует нерефутабельный. При
этом `let (a, b) = pair;` работает — кортеж всегда совпадает. Именно поэтому
`let ... else` и появился как отдельная конструкция.

## Когда использовать комбинаторы вместо `match`?

**Коротко.** Когда логика — «преобразовать значение внутри» или «подставить
значение по умолчанию». `match` — когда веток несколько и в каждой
собственная логика.

```rust
fn main() {
    let raw: Option<&str> = Some("42");

    // цепочка преобразований без единого match
    let n: i32 = raw
        .and_then(|s| s.parse::<i32>().ok())   // Option<&str> -> Option<i32>
        .filter(|&n| n > 0)
        .unwrap_or_default();
    println!("{n}");                            // 42

    let missing: Option<i32> = None;
    println!("{}", missing.unwrap_or_else(|| 7 * 6)); // 42, замыкание ленивое
    println!("{:?}", missing.ok_or("нет значения"));  // Err("нет значения")

    let mut slot = Some(1);
    println!("{:?} {:?}", slot.take(), slot);   // Some(1) None
}
```

Часто спрашиваемые пары: `unwrap_or` (значение вычисляется всегда) против
`unwrap_or_else` (лениво); `map` (преобразует внутрь) против `and_then`
(преобразует в другой `Option`/`Result`, без вложенности); `ok_or` против
`ok_or_else` — переход `Option → Result` (см. [обработку
ошибок](error-handling.md)).

**Подвох.** `unwrap()` на `None` — паника с бесполезным сообщением. В
библиотечном коде его не место; в приложении минимум `expect("почему это
не может быть None")`, чтобы в логе была причина, а не только номер строки.

## Как enum используют для моделирования состояний?

**Коротко.** Состояние — вариант enum с данными, переход — `match`, который
возвращает новое состояние. Некорректные комбинации полей становятся
непредставимыми.

```rust
enum Connection {
    Idle,
    Connecting { attempts: u32 },
    Ready { session: String },
    Failed(String),
}

fn next(state: Connection) -> Connection {
    match state {
        Connection::Idle => Connection::Connecting { attempts: 1 },
        Connection::Connecting { attempts } if attempts < 3 => {
            Connection::Connecting { attempts: attempts + 1 }
        }
        Connection::Connecting { .. } => Connection::Failed("нет ответа".into()),
        other => other,
    }
}

fn main() {
    let mut s = Connection::Idle;
    for _ in 0..5 { s = next(s); }
    println!("{}", matches!(s, Connection::Failed(_))); // true
}
```

Сравните с плоской структурой `{ connected: bool, session: Option<String>,
error: Option<String> }`: там представимы бессмысленные комбинации
(`connected: true` и `error: Some(...)` одновременно), и их приходится
проверять руками.

**Глубже.** Более строгий вариант — typestate: каждое состояние отдельный
тип, а переходы — методы, потребляющие `self` и возвращающие другой тип. Тогда
вызвать `send()` на неподключённом соединении не получится **на этапе
компиляции**, а не в рантайме. Разбор — в [идиомах](idioms-api-design.md).
