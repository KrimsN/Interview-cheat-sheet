## Откуда у Rust производительность?

**Коротко.** Нативный код через LLVM, отсутствие GC и рантайма,
мономорфизация с инлайнингом и — что менее очевидно — более сильные
гарантии алиасинга, чем у C: `&mut T` уникальна по определению, и оптимизатор
может на это опираться.

Что это даёт практически:

- нет пауз сборщика мусора — предсказуемые хвостовые задержки (p99);
- нет рантайма — быстрый старт, маленький бинарник, пригодность для
  embedded и WebAssembly;
- расположение данных видно из типа: `Vec<Point>` — это непрерывный массив
  структур, а не массив указателей на объекты, как в языках с GC. Локальность
  кеша получается «бесплатно».

**Подвох.** Отсутствие GC не значит «память бесплатна»: вместо пауз GC есть
вызовы `malloc`/`free` в предсказуемых, но вполне реальных точках. Поэтому
оптимизация Rust-кода почти всегда начинается с **уменьшения числа
аллокаций**, а не с микрооптимизации арифметики.

## Как уменьшают число аллокаций?

**Коротко.** Резервировать заранее, переиспользовать буфер, брать `&str`
вместо `String` в горячем пути, для маленьких коллекций — `SmallVec`, для
графов и AST — арена.

```rust
fn main() {
    let words = ["раз", "два", "три"];

    // плохо: новая String на каждой итерации
    let mut slow = Vec::new();
    for w in words { slow.push(format!("<{w}>")); }

    // лучше: один буфер, переиспользуется
    let mut buf = String::with_capacity(64);
    let mut fast = Vec::with_capacity(words.len());
    for w in words {
        buf.clear();
        buf.push('<'); buf.push_str(w); buf.push('>');
        fast.push(buf.clone());   // единственная неизбежная копия
    }

    println!("{}", slow == fast);  // true
}
```

Инструменты по ситуации: `smallvec::SmallVec<[T; 8]>` держит небольшие
коллекции на стеке; `bumpalo`/`typed-arena` дают арену, где освобождение —
одна операция на всё сразу; `Cow` откладывает копию до момента изменения
(см. [строки](strings.md)).

**Подвох.** Классический вопрос «чем плох `String::new()` в цикле»: каждая
строка — отдельная аллокация и последующее освобождение, плюс рост буфера
удвоением по мере записи. На горячем пути это доминирующая стоимость, и
профайлер показывает её первым делом.

## Стек или куча — как это видно из кода?

**Коротко.** По типу. Обычные значения и массивы `[T; N]` — на стеке;
`Box`, `Vec`, `String`, `Rc`/`Arc`, коллекции — данные в куче. Escape
analysis, как в Go или JVM, здесь не нужен: расположение задано типом, а не
выведено компилятором.

```rust
fn main() {
    let on_stack = [0u8; 1024];          // 1 КиБ прямо в кадре стека
    let on_heap = vec![0u8; 1024];       // дескриптор на стеке, данные в куче
    println!("{} {}", on_stack.len(), on_heap.len());  // 1024 1024
}
```

Практические следствия: большие структуры лучше не перемещать по стеку без
нужды (`Box` дешевле, чем копия килобайта), а «толстые» варианты enum
боксируют — иначе размер типа равен наибольшему варианту (см.
[типы](types-memory-layout.md)). То же касается больших футур в
[async](async-await.md).

## Сколько стоят абстракции?

**Коротко.** Итераторы, `Option`, дженерики, newtype, `Result` — как правило
бесплатны. Реальную стоимость имеют `dyn Trait`, `Box<dyn Fn>`, `RefCell`,
`Arc` и любые аллокации.

| Конструкция | Цена |
|---|---|
| Итераторные цепочки | обычно нулевая, разворачиваются в цикл |
| `Option<&T>`, newtype, `#[repr(transparent)]` | нулевая |
| Дженерики | нулевая в рантайме (платит компиляция) |
| `dyn Trait` | косвенный вызов, нет инлайнинга |
| `RefCell` | счётчик заимствований + ветвление |
| `Rc::clone` | инкремент; `Arc::clone` — атомарный инкремент |
| `Mutex::lock` | атомарная операция, при конкуренции — syscall |

```rust
fn main() {
    let v: Vec<u64> = (1..=1_000_000).collect();

    // обе версии обычно компилируются в один и тот же цикл
    let a: u64 = v.iter().filter(|x| *x % 3 == 0).sum();
    let mut b = 0u64;
    for x in &v { if x % 3 == 0 { b += x; } }

    println!("{}", a == b);   // true
}
```

**Подвох.** `Arc::clone` часто считают бесплатным. Это атомарный инкремент, и
при конкуренции нескольких ядер за одну кеш-линию он становится узким местом
— эффект «cache line ping-pong». В горячем цикле счётчики клонируют один раз
снаружи, а не на каждой итерации.

## Что происходит с проверками границ?

**Коротко.** Они есть, но оптимизатор часто их устраняет, когда может
доказать корректность индекса. Итерирование итераторами помогает ему
больше, чем индексация.

```rust
// компилятору сложнее: нужно доказать, что i < v.len() на каждом шаге
fn sum_indexed(v: &[u64]) -> u64 {
    let mut s = 0;
    for i in 0..v.len() { s += v[i]; }
    s
}

// проверки не нужны по построению итератора
fn sum_iter(v: &[u64]) -> u64 { v.iter().sum() }

fn main() {
    let v: Vec<u64> = (1..=10).collect();
    println!("{} {}", sum_indexed(&v), sum_iter(&v));   // 55 55
}
```

Для блочной обработки есть `chunks_exact` — он даёт срезы фиксированного
размера, из-за чего компилятор охотнее векторизует цикл. `get_unchecked`
(`unsafe`) — крайняя мера, оправданная только измерением.

## Какие настройки сборки дают ускорение почти даром?

**Коротко.** `--release` (обязательно), `lto`, `codegen-units = 1`,
`target-cpu=native`, замена аллокатора.

```toml
[profile.release]
lto = "fat"
codegen-units = 1
```

```bash
RUSTFLAGS="-C target-cpu=native" cargo build --release
```

Замена глобального аллокатора заметна на многопоточной нагрузке, где
системный `malloc` становится точкой конкуренции:

```rust
// Cargo.toml: mimalloc = "0.1"
#[global_allocator]
static GLOBAL: mimalloc::MiMalloc = mimalloc::MiMalloc;

fn main() { println!("аллокатор заменён"); }
```

**Подвох.** `target-cpu=native` делает бинарник непереносимым: он может
использовать инструкции, которых нет на другой машине, и упасть с
«illegal instruction». Для дистрибутивных сборок берут разумный базовый
уровень (например, `x86-64-v2`).

## Как ускоряют многопоточный код?

**Коротко.** Уменьшать конкуренцию: `rayon` для данных, шардирование вместо
одного глобального `Mutex`, атомики вместо блокировок, каналы вместо общего
состояния.

```rust
use std::sync::Mutex;

// плохо: все потоки дерутся за один мьютекс
struct Naive { data: Mutex<Vec<u64>> }

// лучше: шардирование — конкуренция падает в N раз
struct Sharded { shards: Vec<Mutex<Vec<u64>>> }

impl Sharded {
    fn push(&self, key: u64, value: u64) {
        let idx = (key as usize) % self.shards.len();
        self.shards[idx].lock().unwrap().push(value);
    }
}

fn main() {
    let s = Sharded { shards: (0..8).map(|_| Mutex::new(Vec::new())).collect() };
    for i in 0..16 { s.push(i, i * 2); }
    println!("{}", s.shards.iter().map(|m| m.lock().unwrap().len()).sum::<usize>()); // 16
}
```

Подробности про примитивы — в
[синхронизации](sync-primitives.md), про `rayon` — в
[потоках](threads-send-sync.md).

## Rust против Go по производительности — что отвечать?

**Коротко.** На CPU-нагрузке Rust обычно быстрее: нет GC, мономорфизация и
инлайнинг, лучше контроль над раскладкой данных. Go выигрывает в скорости
компиляции, простоте конкурентной модели и времени вывода фичи в прод.

Честный ответ признаёт обе стороны:

- **Rust быстрее**, когда важны p99-задержки (нет пауз GC), плотная работа с
  памятью, парсинг, вычисления, embedded;
- **Go быстрее в разработке**, когда сервис — это в основном ожидание базы и
  сети: там разница в языке теряется на фоне сетевых задержек, а горутины
  проще async-кода;
- сравнивать надо **свою** нагрузку: микробенчмарки с сайтов сравнений
  измеряют не то, что у вас в проде.

**Глубже.** Правильный порядок работы над производительностью, который и
ждут услышать: измерить (`criterion`, `perf stat`, flamegraph) → найти
горячую точку → изменить одно → измерить снова. Список трюков без этого цикла
ценится меньше, чем сам цикл.
