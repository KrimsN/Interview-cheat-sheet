## Что возвращает `async fn` и почему без `.await` ничего не происходит?

**Коротко.** `async fn` возвращает `Future` — ленивый конечный автомат,
который не делает **ничего**, пока его не начнут опрашивать. Вызов функции
только создаёт объект; работа начинается на `.await` или когда футуру
передали рантайму.

```rust
async fn work(id: u32) -> u32 {
    println!("работаю {id}");
    id * 2
}

#[tokio::main]
async fn main() {
    let fut = work(21);            // ничего не напечаталось: футура создана, но спит
    println!("футура создана");
    let result = fut.await;         // вот теперь тело выполняется
    println!("{result}");
    // футура создана
    // работаю 21
    // 42
}
```

Это отличает Rust от JavaScript и C#, где `async`-функция начинает
выполняться немедленно, а `await` только ждёт результат. Здесь модель
**pull**: рантайм тянет значение, вызывая `poll`.

**Подвох.** Забытый `.await` — самая частая ошибка новичка. Компилятор
предупреждает: «unused implementer of `Future` that must be used», но код
собирается, и функция просто не выполняется.

## Как устроен трейт `Future`?

**Коротко.** Один метод: `poll(self: Pin<&mut Self>, cx: &mut Context) ->
Poll<T>`. Он возвращает `Ready(значение)` или `Pending`, предварительно
зарегистрировав `Waker` из `Context` — тот разбудит задачу, когда появится
готовность.

```rust
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct Countdown(u32);

impl Future for Countdown {
    type Output = &'static str;

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        if self.0 == 0 {
            Poll::Ready("готово")
        } else {
            self.0 -= 1;
            cx.waker().wake_by_ref();   // просим опросить нас снова
            Poll::Pending
        }
    }
}

#[tokio::main]
async fn main() {
    println!("{}", Countdown(3).await);  // готово
}
```

Компилятор превращает `async`-блок именно в такой автомат: каждая точка
`.await` — состояние, а всё, что живёт через `.await`, становится полем
структуры-футуры. Отсюда практическое следствие: футуры бывают большими, и
рекурсивные `async`-вызовы нужно боксировать (`Box::pin`), иначе размер
типа получается бесконечным.

## Почему в стандартной библиотеке нет исполнителя?

**Коротко.** `std` даёт только трейты (`Future`, `Context`, `Waker`).
Планировщик, таймеры и асинхронный ввод-вывод даёт рантайм: `tokio` (де-факто
стандарт), `async-std`, `smol`, `embassy` для микроконтроллеров.

Причина — Rust должен работать и на сервере, и в ядре, и на
микроконтроллере без ОС; единый встроенный рантайм это исключил бы. Цена
решения — фрагментация: типы ввода-вывода `tokio` и `async-std`
несовместимы, и библиотеки часто привязаны к конкретному рантайму.

```rust
// Cargo.toml: tokio = { version = "1", features = ["full"] }
#[tokio::main]                                   // разворачивается в Runtime::new().block_on(...)
async fn main() {
    let t = tokio::time::Instant::now();
    let (a, b) = tokio::join!(                   // ждём обе задачи одновременно
        tokio::time::sleep(std::time::Duration::from_millis(50)),
        tokio::time::sleep(std::time::Duration::from_millis(50)),
    );
    let _ = (a, b);
    println!("{}", t.elapsed().as_millis() < 90); // true — не 100 мс, значит параллельно
}
```

## Что нужно знать про Tokio на собеседовании?

**Коротко.** `#[tokio::main]`, `tokio::spawn` (задача, а не поток; требует
`Send + 'static`), `spawn_blocking` для блокирующего кода, `select!`,
`JoinSet`, а также `tokio::sync::{Mutex, mpsc, oneshot, Semaphore, watch,
broadcast}`.

```rust
use tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel::<u32>(16);   // ограниченный канал = backpressure

    for i in 0..3 {
        let tx = tx.clone();
        tokio::spawn(async move {
            tx.send(i * 10).await.unwrap();
        });
    }
    drop(tx);

    let mut got = Vec::new();
    while let Some(v) = rx.recv().await { got.push(v); }
    got.sort();
    println!("{got:?}");    // [0, 10, 20]

    // тяжёлые вычисления — не в асинхронную задачу
    let heavy = tokio::task::spawn_blocking(|| (0..10_000_000u64).sum::<u64>());
    println!("{}", heavy.await.unwrap());   // 49999995000000
}
```

Задача (task) — это не поток: тысячи задач живут на нескольких рабочих
потоках, память на задачу — сотни байт вместо мегабайтового стека.

**Подвох.** `tokio::spawn` требует `'static` и `Send` ровно по той же
причине, что и `thread::spawn`: задача может пережить вызывающий кадр и
переехать на другой рабочий поток. Отсюда `Arc` и `move` в async-коде.

## Что означает «нельзя блокировать исполнитель»?

**Коротко.** Асинхронная задача занимает рабочий поток на всё время
выполнения между точками `.await`. `std::thread::sleep`, синхронный
файловый ввод-вывод или тяжёлый CPU-цикл внутри задачи останавливают весь
поток — и вместе с ним все задачи, которые на нём стоят.

```rust
#[tokio::main]
async fn main() {
    // ПЛОХО: блокирует рабочий поток целиком
    // std::thread::sleep(std::time::Duration::from_secs(1));

    // хорошо: возвращает управление планировщику
    tokio::time::sleep(std::time::Duration::from_millis(10)).await;

    // хорошо: блокирующий код уезжает в отдельный пул
    let n = tokio::task::spawn_blocking(|| {
        std::thread::sleep(std::time::Duration::from_millis(10));
        42
    }).await.unwrap();
    println!("{n}");   // 42
}
```

Симптомы в проде: растут хвостовые задержки, счётчики «застряли», при этом
CPU не загружен. Диагностика — `tokio-console`, показывающий задачи, которые
долго не отдают управление.

**Подвох.** Синхронный `std::sync::Mutex` в async-коде **допустим** и даже
предпочтителен, если критическая секция короткая и guard не живёт через
`.await`. `tokio::sync::Mutex` нужен, когда блокировку надо удерживать через
точку ожидания, — он дороже, но задача, снятая с потока, никого не
заблокирует.

## Как в async-коде устроена отмена?

**Коротко.** Футура отменяется простым сбрасыванием (drop) — никакого
`context.Done()`, как в Go, проверять не нужно. Оборотная сторона —
**cancel safety**: отменённая на середине операция может потерять данные.

```rust
use tokio::time::{sleep, timeout, Duration};

#[tokio::main]
async fn main() {
    // таймаут — это просто «уронить футуру, если не успела»
    let r = timeout(Duration::from_millis(20), sleep(Duration::from_millis(100))).await;
    println!("{}", r.is_err());   // true — не успела, футура отброшена

    // select! — кто первый, того и результат; проигравшая ветка отменяется
    tokio::select! {
        _ = sleep(Duration::from_millis(10)) => println!("быстрая ветка"),
        _ = sleep(Duration::from_millis(50)) => println!("медленная ветка"),
    }
    // быстрая ветка
}
```

Cancel safety на практике: в цикле `select!` можно использовать только те
операции, которые безопасно прервать на середине. `mpsc::Receiver::recv`
безопасен (сообщение не теряется), а «прочитать N байт в буфер» — нет:
отмена посреди чтения теряет уже прочитанное. Документация Tokio помечает
cancel safety у каждого метода.

**Подвох.** Отменённая задача не выполняет никакого «кода очистки после
await» — она просто исчезает, отработав деструкторы. Асинхронного `Drop` в
языке нет, поэтому корректное завершение (закрыть соединение, сбросить
буфер) делают явным вызовом `shutdown().await`, а не полагаются на
деструктор.

## Зачем нужен `Pin`?

**Коротко.** Сгенерированная футура может содержать ссылки на собственные
поля (например, `&self.buf`, живущую через `.await`). Такое значение нельзя
перемещать после начала опроса — ссылки станут висячими. `Pin` — тип-обещание
«это значение больше не сдвинется с места».

```rust
use std::pin::Pin;
use std::future::Future;

// рекурсивный async требует боксирования: иначе размер типа бесконечен
fn countdown(n: u32) -> Pin<Box<dyn Future<Output = u32> + Send>> {
    Box::pin(async move {
        if n == 0 { 0 } else { countdown(n - 1).await + 1 }
    })
}

#[tokio::main]
async fn main() {
    println!("{}", countdown(5).await);   // 5
}
```

`Unpin` — маркер «этот тип можно двигать даже под `Pin`»; он есть почти у
всего, кроме сгенерированных футур и самоссылающихся структур.

**Глубже.** Для собеседования достаточно понимать **мотивацию** (футуры
самоссылающиеся, поэтому их нельзя двигать) и знать `Box::pin`/`pin!`.
Ручные реализации `Future` с `Pin` спрашивают редко и обычно только там, где
пишут рантаймы или библиотеки уровня `tower`.

## Async или потоки — как выбрать?

**Коротко.** Async выигрывает на большом числе **ожиданий**: тысячи
соединений, каждое из которых почти всё время простаивает. Потоки проще и
лучше для CPU-нагрузки. Async не ускоряет вычисления.

Дополнительные издержки async, о которых честно говорят на собеседовании:

- «заражение» цветом функции: `async` протекает вверх по стеку вызовов;
- привязка библиотек к рантайму;
- `Stream` (асинхронный итератор) до сих пор живёт в крейте `futures`, а не в
  `std`;
- `async fn` в трейтах стабилизирован в 1.75, но для `dyn` по-прежнему нужен
  `async-trait` (см. [трейты](traits.md));
- отладка сложнее: стек трассировки — это состояние автомата, а не цепочка
  вызовов.
