## Что входит в тулчейн Go «из коробки»?

**Коротко.** Один бинарь `go` со встроенными подкомандами закрывает то, для
чего в других экосистемах нужен набор отдельных утилит: `go build`, `go
run`, `go test`, `go fmt`, `go vet`, `go doc`, `go generate`, `go mod`, `go
work`, `go tool`.

```bash
go fmt ./...     # форматирование по единственному каноническому стилю
go vet ./...     # статический анализ на реальные баги
go doc fmt.Sprintf   # документация функции прямо из терминала
```

Отсутствие споров о форматировании — часть культуры языка: `gofmt`
детерминированно приводит код к одному стилю без настроек, поэтому ревью
никогда не обсуждают расстановку скобок или отступы. Более строгий вариант —
`gofumpt`, надмножество правил `gofmt` (например, запрещает лишние пустые
строки).

**Подвох.** `go vet` — это не линтер в общем смысле, а набор проверок,
которые находят вещи, почти наверняка являющиеся багом (несовпадение
формата `Printf` и аргументов, копирование `sync.Mutex` по значению, захват
переменной цикла в замыкании, потерянный `context.CancelFunc`). `go vet`
запускается автоматически перед `go test`, но не заменяет полноценный
линтер вроде `staticcheck` или агрегатор `golangci-lint`, которые ищут более
широкий класс проблем и требуют настройки.

## Как читать профили pprof: чем отличаются heap, cpu, goroutine, mutex?

**Коротко.** `net/http/pprof` в работающем сервисе (или `go test
-cpuprofile`/`-memprofile` в тестах) даёт снимки по нескольким осям: **cpu**
— куда уходит процессорное время, **heap** — что аллоцировано, **goroutine**
— сколько горутин и где они стоят, **mutex**/**block** — на чём конкурентно
блокируется код.

```go
package main

import (
	"log"
	"net/http"
	_ "net/http/pprof" // регистрирует хендлеры /debug/pprof/* через init()
)

func main() {
	log.Println(http.ListenAndServe("localhost:6060", nil))
}
```

```bash
go tool pprof -http=:8080 http://localhost:6060/debug/pprof/heap
go tool pprof -http=:8080 http://localhost:6060/debug/pprof/profile?seconds=30
```

У профиля **heap** два принципиально разных среза, которые часто путают:
`inuse_space` — что живёт в куче **прямо сейчас** (искать утечки и
избыточное потребление), и `alloc_space` — сколько всего было аллоцировано
с начала работы, включая уже собранное GC (искать источник **давления** на
GC, а не текущий размер памяти). Профиль **goroutine** с параметром
`?debug=2` в HTTP-эндпоинте выводит полные стеки всех горутин текстом —
основной инструмент диагностики зависших/утёкших горутин.

`mutex` и `block` профили не собираются по умолчанию — их нужно явно
включить, иначе `go tool pprof` покажет пустой профиль:

```go
runtime.SetMutexProfileFraction(1) // профилировать конкуренцию за мьютексы
runtime.SetBlockProfileRate(1)     // профилировать блокирующие ожидания
```

**Подвох.** «heap-профиль показывает всю память процесса» — нет, он
показывает только память, которой управляет Go-аллокатор (объекты в куче).
Память, занятую стеками горутин, память под cgo-аллокациями или служебные
структуры рантайма heap-профиль не покажет — для полной картины памяти
процесса нужен `runtime.MemStats`/`runtime/metrics` или инструменты уровня
ОС.

## Что показывает `go tool trace` и чем он отличается от pprof?

**Коротко.** `pprof` отвечает «где горит CPU / сколько памяти», а `go tool
trace` — временнáя развёртка выполнения: что делал планировщик, когда были
паузы GC, когда горутина ждала сеть или синхронизацию. Это инструмент для
вопроса «почему растёт latency при в целом нормальном CPU».

```bash
go test -trace=trace.out ./...
go tool trace trace.out
```

Трассировка визуализирует по каждому P (processor) и каждой горутине, чем
именно был занят рантайм в каждый момент времени: выполнение
пользовательского кода, ожидание планировщика, системный вызов, пауза GC.
Это позволяет увидеть, например, что latency скачет не из-за медленного
кода, а из-за того, что горутины массово упираются в GC-assist или ждут
доступный P.

**Подвох.** Trace-файл может быть тяжёлым и заметно замедлять выполнение
под записью — его снимают точечно, на короткое окно воспроизведения
проблемы, а не постоянно в проде, в отличие от pprof-профилей, которые
достаточно дёшевы для постоянного сбора с семплированием.

## Что такое `GODEBUG` и какие значения полезно знать?

**Коротко.** Переменная окружения, включающая недокументированные в обычном
API диагностические и совместимостные режимы рантайма. Самые ходовые на
собеседовании — `gctrace` и `schedtrace`.

```bash
GODEBUG=gctrace=1 ./app
# gc 1 @0.014s 2%: 0.020+0.51+0.008 ms clock, ...

GODEBUG=schedtrace=1000,scheddetail=1 ./app  # состояние планировщика раз в 1с
```

`gctrace=1` печатает в stderr одну строку на каждый цикл GC: номер цикла,
время с начала работы, долю CPU, ушедшую на GC, длительность фаз. Это
самый дешёвый способ понять, не «горит» ли GC без поднятия pprof-сервера.
`madvdontneed=1` управляет тем, как рантайм возвращает освобождённую память
ОС (влияет на видимый RSS процесса в контейнере). `inittrace=1` печатает
время выполнения `init()` каждого пакета — полезно искать, что тормозит
холодный старт.

**Подвох.** `GODEBUG` — не заменяет профилирование, а даёт грубый
агрегированный сигнал «GC работает много/мало». Найти **какой именно код**
порождает избыточные аллокации — задача `pprof heap` с `alloc_space`, а не
`GODEBUG`.

## Как правильно собирать runtime-метрики?

**Коротко.** Современный способ — пакет `runtime/metrics`: типизированный,
расширяемый набор метрик рантайма без блокировки мира. `runtime.ReadMemStats`
— более старый API, который до сих пор широко встречается в коде, но
исторически требовал полной STW-паузы для консистентного снимка.

```go
package main

import (
	"fmt"
	"runtime/metrics"
)

func main() {
	samples := []metrics.Sample{
		{Name: "/memory/classes/heap/objects:bytes"},
		{Name: "/gc/cycles/total:gc-cycles"},
	}
	metrics.Read(samples)
	for _, s := range samples {
		fmt.Printf("%s = %v\n", s.Name, s.Value)
	}
}
```

Список доступных метрик стабилен по имени и версионируется вместе с
рантаймом (`metrics.All()` возвращает описание всех доступных в текущей
версии Go), что делает `runtime/metrics` пригодным для экспорта в
Prometheus без риска, что имя поля внутренней структуры рантайма внезапно
изменится между релизами Go.

**Подвох.** `runtime.ReadMemStats` в современных версиях Go больше не
требует полного stop-the-world (это исправлено), но остаётся более тяжёлой
операцией, чем точечное чтение конкретных метрик через `runtime/metrics`, —
последний читает только то, что запрошено, а не весь снимок целиком.

## Как корректно сравнивать результаты бенчмарков?

**Коротко.** Единичный запуск `go test -bench` зашумлён (частота CPU,
соседние процессы, тепловой троттлинг). Для статистически значимого
сравнения запускают несколько раз с `-count` и сравнивают через `benchstat`.

```bash
go test -bench=. -benchtime=1s -count=10 ./... > old.txt
# ... внести изменение в код ...
go test -bench=. -benchtime=1s -count=10 ./... > new.txt

benchstat old.txt new.txt
# name        old time/op    new time/op    delta
# Add-8       0.25ns ± 2%    0.18ns ± 1%    -28.00%  (p=0.000 n=10+10)
```

`benchstat` показывает не просто разницу средних, а доверительный интервал
и p-value — то есть отвечает на вопрос «это реальное улучшение или шум
измерения» строже, чем сравнение двух чисел на глаз.

**Подвох.** Сравнивать бенчмарки, снятые на разных машинах или при разной
фоновой нагрузке, — методологическая ошибка: `benchstat` покажет числа, но
их разница будет объясняться окружением, а не изменением в коде. На это
особенно легко попасться в CI на shared runners с непредсказуемым соседним
нагрузками.

## Какими инструментами отлаживают Go-программы?

**Коротко.** `delve` (`dlv`) — стандартный отладчик для Go: понимает
горутины, каналы, инлайнинг компилятора — в отличие от `gdb`, который видит
только «сырой» ассемблер без Go-специфичной семантики.

```bash
dlv debug ./cmd/server        # собрать и запустить под отладчиком
dlv attach <pid>               # подключиться к уже запущенному процессу
```

Для диагностики без полноценного отладчика есть облегчённые средства прямо
в коде:

```go
import "runtime/debug"

func handler() {
	defer func() {
		if r := recover(); r != nil {
			debug.PrintStack() // напечатать стек текущей горутины в stderr
		}
	}()
}
```

При падении процесса переменная `GOTRACEBACK=all` (вместо значения по
умолчанию `single`, показывающего стек только упавшей горутины) заставляет
рантайм напечатать стеки **всех** горутин — незаменимо при диагностике
дедлоков и падений в конкурентном коде, где причина обычно не в той
горутине, что первой запаниковала.

**Подвох.** `debug.PrintStack()` печатает стек **текущей** горутины в момент
вызова, а не всех горутин процесса — для полной картины (как при
`GOTRACEBACK=all`) нужен `pprof goroutine ?debug=2` или сигнал `SIGQUIT`
работающему процессу, который тоже печатает стеки всех горутин.

## Что проверяет `govulncheck` и чем он отличается от простого аудита зависимостей?

**Коротко.** `govulncheck` сверяет граф зависимостей проекта с базой
известных уязвимостей Go (`vuln.go.dev»`), но, в отличие от «плоского»
аудита версий, учитывает **реально вызываемый код** — статический анализ
показывает, доходит ли путь вызова из вашего кода до уязвимой функции.

```bash
go install golang.org/x/vuln/cmd/govulncheck@latest
govulncheck ./...
```

```bash
go list -m -u all   # какие зависимости устарели относительно текущих go.mod
```

Отличие от «в зависимости есть уязвимость, значит она в зоне риска» важно
практически: `govulncheck` может показать, что уязвимая функция пакета
никогда не вызывается транзитивно из вашего кода — тогда апгрейд менее
срочен, чем предупреждение уровня «модуль X содержит CVE» без контекста
вызова.

**Подвох.** `govulncheck` анализирует именно **вызываемый** код — если
уязвимая зависимость подключена, но её функция не достижима из `main`,
инструмент честно покажет это как более низкий риск. Но это не отменяет
необходимости обновиться: код может стать достижимым при следующем
изменении, и `go.sum`/база данных нужно обновлять регулярно, а не полагаться
на разовую проверку.
