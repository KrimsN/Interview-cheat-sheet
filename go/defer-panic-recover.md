## Как работает `defer` — когда вычисляются аргументы и в каком порядке выполняются отложенные вызовы?

**Коротко.** `defer` откладывает вызов до выхода из **функции** (не из блока
и не из итерации цикла). Аргументы вычисляются **в момент объявления**
`defer`, а само тело вызова — при выходе. Несколько `defer` выполняются в
порядке **LIFO**, как стек.

```go
package main

import "fmt"

func main() {
	for i := 0; i < 3; i++ {
		defer fmt.Println("defer value:", i) // аргумент "i" вычислен ЗДЕСЬ и ЗАФИКСИРОВАН
	}
	defer func() {
		fmt.Println("defer closure: done") // а тело замыкания выполнится при выходе
	}()
	fmt.Println("main body finished")
}
// Вывод:
// main body finished
// defer closure: done
// defer value: 2
// defer value: 1
// defer value: 0
```

Разница между `defer fmt.Println(i)` и `defer func() { fmt.Println(i) }()` —
классический вопрос: в первом случае значение `i` "замораживается" сразу,
во втором замыкание захватывает переменную `i` и читает её значение позже,
в момент фактического вызова.

**Подвох.** «`defer` выполняется при выходе из блока `if` / из итерации
цикла» — нет, только при выходе из всей функции. Это и есть причина
следующей ловушки про `defer` в цикле.

## Почему `defer` в цикле — частая причина утечки ресурсов, и как это исправить?

**Коротко.** `defer` внутри цикла копит отложенные вызовы до конца функции
целиком, а не до конца итерации. Если в цикле сотни файлов — все дескрипторы
останутся открытыми, пока функция не завершится.

```go
// ПЛОХО: файлы копятся и закрываются только в самом конце sumSizes
func sumSizes(paths []string) (int64, error) {
	var total int64
	for _, p := range paths {
		f, err := os.Open(p)
		if err != nil {
			return 0, err
		}
		defer f.Close() // накопится на всю функцию при длинном paths
		info, err := f.Stat()
		if err != nil {
			return 0, err
		}
		total += info.Size()
	}
	return total, nil
}
```

Лечится выносом тела итерации в отдельную функцию — тогда `defer`
привязывается к её собственному, короткому времени жизни:

```go
// ХОРОШО: defer живёт ровно одну итерацию
func sumSizesFixed(paths []string) (int64, error) {
	var total int64
	for _, p := range paths {
		size, err := fileSize(p)
		if err != nil {
			return 0, err
		}
		total += size
	}
	return total, nil
}

func fileSize(path string) (int64, error) {
	f, err := os.Open(path)
	if err != nil {
		return 0, err
	}
	defer f.Close() // закроется в конце КАЖДОГО вызова fileSize
	info, err := f.Stat()
	if err != nil {
		return 0, err
	}
	return info.Size(), nil
}
```

**Подвох.** Сам по себе `defer` практически бесплатен — с Go 1.14 компилятор
умеет генерировать "открытый" (open-coded) `defer`, который в большинстве
случаев не аллоцирует. Проблема именно в накоплении вызовов на большую
функцию, а не в цене самого `defer`.

## Как `defer` может изменить возвращаемое значение функции?

**Коротко.** Если результаты функции **именованные**, отложенная функция
имеет доступ к ним по имени и может изменить их уже после `return` — на
этом строится идиома «поймать панику и превратить её в ошибку».

```go
func divide(a, b int) (result int, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recovered: %v", r) // подменяем именованный err
		}
	}()
	result = a / b
	return
}

func main() {
	r, err := divide(10, 0)
	fmt.Println(r, err)
	// Вывод: 0 recovered: runtime error: integer divide by zero
}
```

Тот же приём нужен, чтобы не потерять ошибку от `Close()` при записи —
`return err` на предыдущей строке уже "ушёл", поэтому её нужно вернуть
именно через `defer`:

```go
func writeAll(path string, data []byte) (err error) {
	f, err := os.Create(path)
	if err != nil {
		return err
	}
	defer func() {
		err = errors.Join(err, f.Close()) // не терять ошибку Close при записи
	}()
	_, err = f.Write(data)
	return err
}
```

**Подвох.** Работает это только через **именованные** результаты. Если
результаты безымянные (`func divide(a, b int) (int, error)`), присвоить им
что-то из `defer` невозможно — `recover` там всё ещё поймает панику, но
преобразовать её в возвращаемую ошибку уже не получится.

## Что делают `panic` и `recover`, и почему `recover` работает только внутри `defer`?

**Коротко.** `panic` разворачивает стек вверх, на каждом уровне выполняя
`defer`; если ни один `defer` не сделал `recover`, процесс падает и печатает
стек всех горутин. `recover` останавливает разворачивание, но **только**
если вызван непосредственно внутри отложенной функции.

```go
func safeCall(f func()) (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("panic: %v", r)
		}
	}()
	f()
	return nil
}

func main() {
	err := safeCall(func() { panic("boom") })
	fmt.Println(err) // panic: boom
}
```

Если `recover()` вызван не прямо в `defer`, а в функции, которую тот
вызывает, — он вернёт `nil`, и паника продолжит разворачивать стек:

```go
func recoverWrong() {
	defer func() {
		logRecover() // recover() внутри ДРУГОЙ функции — вернёт nil, не поймает
	}()
	panic("oops")
}

func logRecover() {
	if r := recover(); r != nil {
		fmt.Println("recovered:", r)
	}
}
// recoverWrong() всё равно уронит программу паникой "oops"
```

**Подвох.** Паника в горутине **не ловится** `recover` в родительской
функции — каждая горутина восстанавливается сама, иначе вся программа
упадёт:

```go
func main() {
	go func() {
		defer func() {
			if r := recover(); r != nil {
				fmt.Println("goroutine recovered:", r)
			}
		}()
		panic("goroutine boom")
	}()
	time.Sleep(100 * time.Millisecond)
	// без recover внутри самой горутины программа завершилась бы целиком
}
```

**Глубже.** `recover` не откатывает состояние программы — после
восстановления объект может остаться в неконсистентном виде (например,
захваченный мьютекс, который некому разлочить, или наполовину записанный
буфер). Практическая идиома — восстанавливаться на границе единицы работы
(HTTP-хендлер, задача воркера) и завершать именно её ошибкой, не пытаясь
продолжить как ни в чём не бывало.

## Чем `panic` отличается от `os.Exit` и `runtime.Goexit`?

**Коротко.** Все три завершают выполнение, но по-разному обращаются с
`defer`: `panic` выполняет отложенные вызовы и может быть перехвачена;
`os.Exit` завершает процесс немедленно и **не выполняет `defer` вообще**;
`runtime.Goexit` завершает только текущую горутину, выполнив её `defer`, но
это не паника — как значение её поймать `recover`'ом нельзя.

```go
func main() {
	defer fmt.Println("никогда не будет напечатано")
	os.Exit(1) // немедленный выход из процесса, defer не выполняется
}
```

| Механизм | `defer` выполняются | Что завершает | Перехватывается |
|---|---|---|---|
| `panic` | да, по пути наверх | функцию/программу (если не восстановлена) | `recover()` в `defer` |
| `os.Exit` | нет | процесс немедленно | нет |
| `runtime.Goexit` | да, для этой горутины | только текущую горутину | нет (не паника) |

**Подвох.** Если `runtime.Goexit` вызван в `main`-горутине, программа тоже
завершится — но не так, как при обычном `return` из `main`: сначала
отработают все `defer` этой горутины, и только потом процесс остановится.
На собеседовании это часто путают с "тихим" завершением без вывода.
