## На чём держится стандартная библиотека Go — расскажите про `io.Reader`/`io.Writer`

**Коротко.** Два однометодных интерфейса: `Read(p []byte) (n int, err error)`
и `Write(p []byte) (n int, err error)`. Вокруг них построена вся экосистема
ввода-вывода — файлы, сеть, буферы, сжатие, шифрование реализуют одни и те же
контракты и потому свободно комбинируются.

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}
```

Ключевая деталь контракта `Read`: он может вернуть `n > 0` **и** `err != nil`
одновременно (например, `io.EOF` вместе с последними прочитанными байтами) —
вызывающий код обязан сначала обработать `n` байт и только потом смотреть на
ошибку. `io.EOF` — не аварийная ошибка, а ожидаемый сигнал конца потока,
поэтому его никогда не оборачивают через `fmt.Errorf`, а сравнивают напрямую
или через `errors.Is`.

```go
func copyManually(dst io.Writer, src io.Reader) (int64, error) {
    buf := make([]byte, 4096)
    var total int64
    for {
        n, err := src.Read(buf)
        if n > 0 {
            if _, werr := dst.Write(buf[:n]); werr != nil {
                return total, werr
            }
            total += int64(n)
        }
        if err == io.EOF {
            return total, nil
        }
        if err != nil {
            return total, err
        }
    }
}
```

На практике этот цикл почти никогда не пишут руками — есть `io.Copy`. Он
интересен тем, что не всегда гоняет данные через промежуточный буфер: если
источник реализует `io.WriterTo`, либо приёмник — `io.ReaderFrom`, `io.Copy`
делегирует им копирование напрямую (например, `*os.File` на Linux использует
`sendfile(2)` и данные вообще не попадают в userspace).

Из вспомогательных типов часто спрашивают:

- `io.LimitReader(r, n)` — обрезает поток первыми `n` байтами (защита от
  «пришлите нам гигабайт JSON»);
- `io.MultiWriter(w1, w2)` — пишет в несколько writer'ов одновременно
  (типичный кейс — одновременно в лог и в `http.ResponseWriter`);
- `io.Pipe()` — синхронная труба в памяти: `Write` блокируется, пока кто-то
  не прочитает — удобно, чтобы скормить писателя в API, ожидающее `io.Reader`
  (например, `multipart.Writer` → `http.Client`), без промежуточного буфера.

**Подвох.** «`io.EOF` — это ошибка, значит, надо `return err` не глядя?» Нет —
если `io.EOF` прилетел там, где его ждали (конец файла при построчном чтении),
это успешное завершение, а не сбой. Пробрасывать его наверх как обычную ошибку
— значит заставить вызывающий код гадать, что случилось.

**Глубже.** `io.ReadAll` (замена `ioutil.ReadAll` с Go 1.16) читает до `EOF`,
наращивая буфер вдвое при нехватке места — удобно, но опасно для
непроверенного источника: нет верхнего предела, поэтому в HTTP-хендлерах его
почти всегда комбинируют с `io.LimitReader`/`http.MaxBytesReader`.

## Чем `bufio.Scanner` отличается от `bufio.Reader`, и куда «теряются» длинные строки?

**Коротко.** `bufio.Reader` — низкоуровневая буферизация чтения произвольными
кусками (`ReadString`, `ReadBytes`, `ReadLine`). `bufio.Scanner` — удобная
надстройка для построчного (или иначе токенизированного) чтения, но у неё есть
скрытый потолок размера токена — `bufio.MaxScanTokenSize` (64 КиБ по
умолчанию).

```go
scanner := bufio.NewScanner(strings.NewReader("first\nsecond\nthird"))
for scanner.Scan() {
    fmt.Println(scanner.Text())
}
if err := scanner.Err(); err != nil {
    log.Fatal(err)
}
// first
// second
// third
```

Если в потоке встретится строка длиннее лимита, `scanner.Scan()` молча вернёт
`false`, а `scanner.Err()` — `bufio.ErrTooLong`. Никакой паники, никакого
исключения — просто чтение обрывается, и если `Err()` не проверить, кажется,
что файл «закончился раньше времени». Лечится через `scanner.Buffer(buf,
maxSize)` с явно увеличенным пределом, либо переходом на `bufio.Reader.
ReadString('\n')`, у которого такого потолка нет.

```go
scanner := bufio.NewScanner(r)
scanner.Buffer(make([]byte, 0, 64*1024), 1024*1024) // до 1 МиБ на строку
```

**Подвох.** Забытый `bufio.Writer.Flush()` — классический баг: буферизованная
запись копит данные в памяти и не пишет их в нижележащий `io.Writer`, пока
буфер не заполнится или `Flush`/`Close` не будет вызван явно. Программа
«молча» теряет хвост вывода при завершении процесса. Правило — `defer
w.Flush()` сразу после создания `bufio.Writer`, если только не гарантирован
явный вызов в конце нормального пути.

## Какие особенности `encoding/json` регулярно ловят на собеседовании?

**Коротко.** Теги `json:"name,omitempty"` управляют именем поля и тем,
опускать ли его при "нулевом" значении, но `omitempty` не умеет отличать
«поле явно прислали нулём» от «поле не прислали вообще» — для этого нужны
указатели или `json.RawMessage`.

```go
type Update struct {
    Name  string `json:"name,omitempty"`
    Price *int   `json:"price,omitempty"` // nil = не передано, &0 = явный 0
}
```

`omitempty` реагирует на "нулевое" значение конкретного Go-типа: пустую
строку, `0`, `false`, `nil`-слайс/карту/указатель. Если поле — `int`, различить
`0` и «клиент не прислал цену» невозможно без указателя.

При декодировании JSON-чисел в `map[string]any`/`interface{}` они всегда
становятся `float64` — целые числа за пределами точности `float64`
(`> 2^53`) искажаются. Для точных больших чисел используют `json.Number`
через `Decoder.UseNumber()`.

```go
var payload map[string]any
dec := json.NewDecoder(strings.NewReader(`{"id": 9007199254740993}`))
dec.UseNumber()
dec.Decode(&payload)
fmt.Println(payload["id"]) // 9007199254740993 (json.Number, без потери точности)
```

Полезные детали:

- `json.Decoder`/`json.Encoder` работают потоково поверх `io.Reader`/`io.Writer`
  и не требуют буферизовать весь JSON в памяти — предпочтительны для HTTP-тел
  и больших файлов перед `json.Unmarshal`/`Marshal`.
- `DisallowUnknownFields()` превращает лишние поля во входном JSON в ошибку —
  полезно для строгих API вместо тихого игнорирования опечаток клиента.
- Сопоставление имён полей по умолчанию регистронезависимое: `"Name"` в JSON
  ляжет в поле `Name` даже без тега — источник неожиданных совпадений.
- Типы, реализующие `json.Marshaler`/`Unmarshaler` (методы `MarshalJSON`/
  `UnmarshalJSON`), полностью берут кодирование на себя — так добавляют,
  например, кастомный формат времени.

**Подвох.** «Раз поле `omitempty`, значит оно точно не попадёт в JSON при
`nil`». Это верно для указателей, слайсов, карт — но пустой (не `nil`) слайс
`[]int{}` тоже опустится, а вот `struct{}` без указателя никогда не
«пустая» с точки зрения `omitempty` — так что структуры-значения этот тег
попросту игнорирует.

## Как в Go устроено время, и почему сравнение `time.Time` — не такое тривиальное, как кажется?

**Коротко.** `time.Time` хранит не только «настенное» время, но и, при
возможности, показания монотонных часов — это отдельный счётчик, на который
не влияет перевод системных часов (NTP-коррекция, ручной перевод даты). Метод
`Sub` использует монотонную составляющую, если она есть у обоих значений,
поэтому измерение интервалов остаётся корректным даже если часы ОС «прыгнули»
в этот момент.

```go
start := time.Now()
// ... какая-то работа ...
elapsed := time.Since(start) // считает по монотонным часам, если доступны
```

`Duration` — это просто `int64` наносекунд с удобными константами
(`time.Second`, `time.Millisecond`), поэтому его легко случайно перепутать по
единицам измерения: `time.Sleep(5)` — это 5 наносекунд, а не 5 секунд.

Форматирование в Go необычное — вместо кодов вроде `%Y-%m-%d` используется
«опорное время» `Mon Jan 2 15:04:05 MST 2006`, и любую дату форматируют,
показывая, как выглядело бы именно это опорное время в нужном формате:

```go
t := time.Date(2026, time.September, 2, 14, 5, 0, 0, time.UTC)
fmt.Println(t.Format("2006-01-02 15:04:05")) // 2026-09-02 14:05:00
fmt.Println(t.Format(time.RFC3339))          // 2026-09-02T14:05:00Z
```

Опорные числа — 1, 2, 3 (15 для часа в 24-часовом формате), 4, 5, 6 —
запомнить проще всего как «01/02 03:04:05 ’06» (американский формат даты).

`Timer` и `Ticker` держат внутри системный ресурс и должны быть остановлены
явно — `Ticker` обязательно через `defer ticker.Stop()`, иначе горутина-таймер
живёт, пока жив процесс. `time.After` в цикле — типичный источник мусора:
каждый вызов создаёт новый `Timer`, который не будет собран сборщиком мусора,
пока не сработает (или не истечёт), даже если сам `select` его уже не ждёт.

```go
// плохо: новый таймер на каждой итерации, старые «висят» до срабатывания
for {
    select {
    case <-time.After(time.Second):
    case <-done:
        return
    }
}

// хорошо: один Ticker на весь цикл, с явной остановкой
ticker := time.NewTicker(time.Second)
defer ticker.Stop()
for {
    select {
    case <-ticker.C:
    case <-done:
        return
    }
}
```

**Подвох.** Монотонные часы не сериализуются: как только `time.Time`
проходит через `MarshalJSON`, `String()`, кладётся в БД или проходит `gob`,
монотонная составляющая отбрасывается, и `Sub`/`Equal` дальше работают уже
только по настенному времени. Сравнивать десериализованные значения через
`==` тоже не стоит — используйте `Equal`, потому что у двух `Time` с одинаковым
моментом, но разными монотонными пометками или таймзонами, `==` может дать
неожиданный результат.

## Как работать с пулом соединений `database/sql`?

**Коротко.** `database/sql` — это не сам драйвер, а универсальный интерфейс
поверх пула соединений; конкретную СУБД подключает драйвер через
`sql.Register` (например, `pgx`, `go-sql-driver/mysql`). Пул настраивается
явно, иначе поведение по умолчанию (неограниченное число соединений) может
уронить БД под нагрузкой.

```go
db, err := sql.Open("pgx", dsn)
if err != nil {
    log.Fatal(err)
}
db.SetMaxOpenConns(25)
db.SetMaxIdleConns(25)
db.SetConnMaxLifetime(5 * time.Minute)
```

`sql.Open` не устанавливает соединение сразу — она лишь готовит объект пула;
реальная ошибка подключения всплывёт при первом запросе (или явном
`db.PingContext`).

Работа со строками результата требует аккуратности с ресурсами:

```go
rows, err := db.QueryContext(ctx, "SELECT id, name FROM users WHERE active = $1", true)
if err != nil {
    return err
}
defer rows.Close()

for rows.Next() {
    var id int64
    var name string
    if err := rows.Scan(&id, &name); err != nil {
        return err
    }
    // использовать id, name
}
return rows.Err() // ошибка, оборвавшая цикл — не проверяется в for
```

`rows.Close()` обязателен даже при успешном переборе всех строк (сам `Next()`
закрывает `rows` на последней итерации, но `defer` — страховка на случай
раннего `return`). `rows.Err()` проверяет ошибку, которая могла прервать
цикл `for rows.Next()` — сам цикл её не покажет, он просто перестанет
итерироваться.

Значения, которые могут быть `NULL`, требуют `sql.NullString`/`sql.NullInt64`
(или указателей) — сканирование `NULL` в обычную `string` вернёт ошибку.

Параметры запроса всегда передаются через плейсхолдеры (`$1`/`?` в
зависимости от драйвера), никогда через конкатенацию строк — иначе классическая
SQL-инъекция.

```go
tx, err := db.BeginTx(ctx, nil)
if err != nil {
    return err
}
defer tx.Rollback() // no-op, если Commit уже прошёл успешно

if _, err := tx.ExecContext(ctx, "UPDATE accounts SET balance = balance - $1 WHERE id = $2", amount, from); err != nil {
    return err
}
if _, err := tx.ExecContext(ctx, "UPDATE accounts SET balance = balance + $1 WHERE id = $2", amount, to); err != nil {
    return err
}
return tx.Commit()
```

**Подвох.** `defer tx.Rollback()` после успешного `tx.Commit()` — это не
ошибка и не двойной откат: `Rollback` после `Commit` возвращает
`sql.ErrTxDone`, который в таком паттерне принято молча игнорировать (её и не
проверяют), потому что `defer` — это просто страховка на случай, если функция
вернётся раньше по ошибке.

## `math/rand` или `crypto/rand` — когда какой?

**Коротко.** `math/rand` (и его современный вариант `math/rand/v2`) —
быстрый, но предсказуемый генератор: по нескольким значениям выхода можно
восстановить внутреннее состояние. Годится для симуляций, тестов, jitter в
ретраях. `crypto/rand` — криптостойкий источник (обычно из `/dev/urandom` или
аналога ОС) для всего, что касается безопасности: токены, ключи, соли,
пароли.

```go
// math/rand/v2 — детерминированный при заданном seed, для НЕ-секретных нужд
n := rand.IntN(100)

// crypto/rand — для секретов
buf := make([]byte, 32)
if _, err := cryptorand.Read(buf); err != nil {
    log.Fatal(err)
}
token := base64.URLEncoding.EncodeToString(buf)
```

С Go 1.20 глобальный источник `math/rand` автоматически засеивается случайным
значением при старте программы (раньше без явного `rand.Seed` он всегда
выдавал одну и ту же последовательность) — но предсказуемость алгоритма как
такового это не убирает, для секретов он всё равно не годится.

**Подвох.** «Проект использует `math/rand` для генерации токена сессии» — это
находка для код-ревью: даже с хорошим seed последовательность `math/rand`
восстановима при достаточном числе наблюдений, что делает токены угадываемыми.

## Чем `slices`/`maps`/`cmp` (Go 1.21+) лучше старого `sort.Slice`?

**Коротко.** Начиная с Go 1.21 в стандартную библиотеку добавлены
generic-пакеты `slices`, `maps`, `cmp`, которые заменяют ручные функции
сравнения через `interface{}`/рефлексию на типобезопасные generic-версии —
компилятор проверяет типы, а не рантайм.

```go
type user struct {
    name string
    age  int
}

users := []user{{"bob", 30}, {"ann", 25}, {"cid", 25}}

// раньше: sort.Slice с ручным приведением индексов
sort.Slice(users, func(i, j int) bool { return users[i].age < users[j].age })

// теперь: slices.SortFunc + cmp.Compare, без риска перепутать i/j
slices.SortFunc(users, func(a, b user) int {
    if c := cmp.Compare(a.age, b.age); c != 0 {
        return c
    }
    return cmp.Compare(a.name, b.name)
})

idx, found := slices.BinarySearch([]int{1, 3, 5, 7}, 5) // 2, true
```

`maps.Keys`/`maps.Values` (в связке с пакетом `iter` из Go 1.23) отдают
итераторы по карте без промежуточной аллокации слайса, а `slices.Contains`,
`slices.Equal`, `slices.Index` закрывают большинство ручных циклов «пробежать
и сравнить», которые раньше писали вручную под каждый тип.

**Подвох.** `sort.Slice` не гарантирует стабильность (порядок «равных» по
компаратору элементов может измениться) — если это важно, нужен
`sort.SliceStable` или `slices.SortStableFunc`.
