## Структура — это значение. Что из этого следует?

**Коротко.** При присваивании и передаче в функцию структура копируется целиком,
как `int` или `bool`. Если внутри есть слайс, карта или указатель — копируется
сам заголовок слайса/карты, а не данные, на которые он смотрит: это shallow
copy, и оригинал с копией делят одну и ту же подложку.

```go
type User struct {
    Name string
    Tags []string
}

func rename(u User) {
    u.Name = "renamed"   // меняет только копию
    u.Tags[0] = "admin"  // меняет ОБЩИЙ подлежащий массив
}

func main() {
    u := User{Name: "alice", Tags: []string{"user"}}
    rename(u)
    // u.Name -> "alice"   не изменилось, копия была независимой
    // u.Tags -> [admin]   изменилось, слайс скопирован по заголовку
}
```

Заголовок слайса — это тройка `(указатель, len, cap)`, заголовок карты —
указатель на внутреннюю хеш-таблицу. Копия структуры получает свою тройку
или свой указатель, но они ссылаются на ту же память.

**Подвох.** «Раз Go передаёт всё по значению, значит, изменить структуру внутри
функции нельзя» — не совсем: нельзя изменить сами поля-значения, но поля-ссылки
(слайс, карта, канал, указатель) мутируются сквозь копию, потому что копируется
только заголовок, а не то, на что он указывает.

**Глубже.** Отсюда и правило про горячие структуры: чем больше `sizeof(T)`, тем
дороже передавать `T` по значению — компилятор копирует все поля при каждом
вызове функции. Порядок полей в структуре тоже влияет на размер из-за
выравнивания (padding): компилятор дополняет структуру, чтобы каждое поле
начиналось с адреса, кратного его размеру. `unsafe.Sizeof` и линтер
`fieldalignment` (часть `go vet`/`staticcheck`) показывают, сколько байт
уходит впустую, — но переставлять поля ради экономии стоит только в структурах,
которые создаются миллионами (сетевые пакеты, элементы кэша), а не всегда.

## Как объявить структуру и какие есть подводные камни у литералов?

**Коротко.** Литерал структуры лучше писать с именованными полями:
`T{Name: "x"}`. Позиционный литерал `T{"x", 10}` компилируется, но ломается
молча при добавлении нового поля в структуру — порядок сдвигается, а
компилятор не подскажет, если типы полей случайно совпали.

```go
type Point struct {
    X, Y int
}

p1 := Point{X: 1, Y: 2}  // именованный — переживёт добавление поля
p2 := Point{1, 2}        // позиционный — обязан перечислить ВСЕ поля по порядку

// добавили поле Z в структуру:
type Point3 struct {
    X, Y, Z int
}
// p3 := Point3{1, 2} — не скомпилируется (мало полей), это ещё повезло.
// Опаснее случай, когда типы совпадают и лишнее поле встаёт на чужое место.
```

Теги полей (`json:"name,omitempty"`, `db:"..."`, `validate:"..."`) — это просто
строки в obj-коде структуры, которые читаются через рефлексию библиотеками
вроде `encoding/json`. Сам компилятор их не проверяет и не использует. Тег
работает только для экспортируемых (с большой буквы) полей — `encoding/json`
не видит и не может установить значение неэкспортируемого поля.

```go
type User struct {
    ID    int    `json:"id"`
    Name  string `json:"name,omitempty"`
    email string // неэкспортируемое — json пропустит независимо от тега
}
```

**Подвох.** «Структуры сравнимы через `==`?» — да, если сравнимы все поля.
Как только внутри появляется слайс, карта или функция, `==` перестаёт
компилироваться, и сравнивать приходится через `reflect.DeepEqual` или
`github.com/google/go-cmp`.

## Что такое встраивание (embedding) и чем оно отличается от наследования?

**Коротко.** Встраивание — это анонимное поле в структуре: `type Server struct
{ *log.Logger }`. Методы и поля встроенного типа **промоутируются** наружу —
`s.Printf(...)` работает так, будто метод объявлен прямо на `Server`. Это
композиция под сахаром, а не наследование: никакого полиморфизма и виртуальных
вызовов здесь нет.

```go
type Base struct {
    Name string
}

func (b Base) Greet() string {
    return "hello, " + b.Name
}

type Derived struct {
    Base       // анонимное поле — встраивание
    Age int
}

func main() {
    d := Derived{Base: Base{Name: "alice"}, Age: 30}
    fmt.Println(d.Greet())     // hello, alice — метод промоутирован
    fmt.Println(d.Name)        // alice — поле промоутировано
    fmt.Println(d.Base.Name)   // alice — полный путь всегда доступен
}
```

Ключевое отличие от классического наследования (Java/C++/Python): встроенный
тип **ничего не знает** о внешнем. Если `Derived` переопределит `Greet()`,
вызов `d.Base.Greet()` изнутри метода `Base` (если бы он такое сделал)
по-прежнему звал бы `Base.Greet`, а не `Derived.Greet` — динамической
диспетчеризации «снизу вверх», как в наследовании, не существует. Что вызовется
для `d.Greet()`, определяет только то, есть ли у `Derived` собственный метод с
таким именем — если нет, вызывается промоутированный метод `Base`, и он ничего
не «знает» про `Derived`.

```go
type Base struct{}

func (Base) Describe() string { return "I am " + Base{}.kind() }
func (Base) kind() string     { return "Base" }

type Child struct{ Base }

func (Child) kind() string { return "Child" }

func main() {
    c := Child{}
    fmt.Println(c.Describe())
    // "I am Base" — Describe вызвал Base.kind(), а не Child.kind()
    // никакого виртуального диспетчеризации по факту нет
}
```

**Подвох.** Встраивание нескольких типов с одинаковыми именами методов/полей
разрешается по глубине: если конфликтующее имя есть только на одном уровне
глубины — оно побеждает; если конфликт на одинаковой глубине — обращение к
такому имени **не компилируется** (неоднозначность), хотя сама структура с
такими встраиваниями объявляется без ошибок. Ошибка всплывает только в месте
использования.

```go
type A struct{ X int }
type B struct{ X int }

type C struct {
    A
    B
}

func main() {
    c := C{A{1}, B{2}}
    // c.X            — ошибка компиляции: ambiguous selector c.X
    fmt.Println(c.A.X, c.B.X) // 1 2 — через явный путь работает всегда
}
```

**Глубже.** Отдельная и очень идиоматичная техника — встраивание **интерфейса**
в структуру:

```go
type PartialWriter struct {
    io.Writer // встроенный интерфейс, а не конкретный тип
}
```

Такая структура автоматически удовлетворяет `io.Writer`, даже если сама не
реализовала метод `Write` — вызов идёт к встроенному значению. Это используют
для моков и «декораторов»: переопределяют один метод интерфейса, остальные
делегируют встроенному значению. Опасность в том, что если поле оставить
`nil` и вызвать непереопределённый метод — будет паника разыменования nil, а
не понятная ошибка компиляции: структура типобезопасно удовлетворяет
интерфейсу, но исполнение проверяется только в рантайме.

## Как в Go делают конструкторы и необязательные параметры?

**Коротко.** В языке нет ключевого слова `constructor`. Идиома — обычная
функция `func NewX(...) (*X, error)`, которая инициализирует структуру и,
если нужно, валидирует аргументы. Если нулевое значение структуры (`var x X`)
уже само по себе валидно и полезно, отдельный конструктор вообще не нужен —
классический пример: `var mu sync.Mutex` готов к использованию сразу.

Для необязательных параметров вместо перегрузки функций (которой в Go нет) и
цепочки конструкторов `NewXWithTimeout`, `NewXWithTimeoutAndRetries`... —
используют паттерн функциональных опций:

```go
type Config struct {
    timeout time.Duration
    retries int
}

type Option func(*Config)

func WithTimeout(d time.Duration) Option {
    return func(c *Config) { c.timeout = d }
}

func WithRetries(n int) Option {
    return func(c *Config) { c.retries = n }
}

func NewConfig(opts ...Option) *Config {
    c := &Config{timeout: 5 * time.Second, retries: 3} // значения по умолчанию
    for _, opt := range opts {
        opt(c)
    }
    return c
}

func main() {
    c := NewConfig(WithTimeout(10 * time.Second))
    // c.timeout -> 10s, c.retries -> 3 (значение по умолчанию не тронуто)
}
```

**Подвох.** Если структура содержит `sync.Mutex`, `sync.WaitGroup` или другой
тип с полем-счётчиком, который нельзя копировать после первого использования,
её нельзя передавать по значению — `go vet` (правило `copylocks`) ловит такое
копирование статически. Идиома — держать методы на указателе и никогда не
возвращать/не принимать такую структуру по значению:

```go
type Counter struct {
    mu sync.Mutex
    n  int
}

func (c *Counter) Inc() { // указательный приёмник — обязателен
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n++
}
```

Пустая структура `struct{}` — частный случай, о котором тоже спрашивают:
она занимает 0 байт памяти (у всех значений `struct{}` формально один и тот же
адрес). Её используют как «пустое» значение там, где важен только факт
наличия ключа/сигнала, а не сама нагрузка: `map[string]struct{}` как множество
и `chan struct{}` как канал-сигнал вместо `chan bool`.
