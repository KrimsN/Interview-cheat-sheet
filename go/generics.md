## Как объявить и вызвать дженерик-функцию?

**Коротко.** Дженерики (параметры типа) появились в Go 1.18. Синтаксис —
квадратные скобки со списком параметров типа перед обычными скобками
аргументов: `func Map[T, U any](s []T, f func(T) U) []U`. В большинстве
вызовов параметры типа выводятся из аргументов автоматически, писать их
явно нужно только при неоднозначности.

```go
// go 1.18+
func Map[T, U any](s []T, f func(T) U) []U {
    out := make([]U, len(s))
    for i, v := range s {
        out[i] = f(v)
    }
    return out
}

func main() {
    nums := []int{1, 2, 3}

    doubled := Map(nums, func(n int) int { return n * 2 })
    // вывод типов сработал сам: T=int, U=int
    fmt.Println(doubled) // [2 4 6]

    strs := Map[int, string](nums, func(n int) string { return fmt.Sprintf("#%d", n) })
    // здесь T и U разные — иногда явное указание читаемее вывода
    fmt.Println(strs) // [#1 #2 #3]
}
```

Дженерик-тип объявляется так же:

```go
// go 1.18+
type Stack[T any] struct {
    items []T
}

func (s *Stack[T]) Push(v T) {
    s.items = append(s.items, v)
}

func (s *Stack[T]) Pop() (T, bool) {
    var zero T
    if len(s.items) == 0 {
        return zero, false
    }
    last := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return last, true
}

func main() {
    var s Stack[string]
    s.Push("a")
    s.Push("b")
    v, ok := s.Pop()
    fmt.Println(v, ok) // b true
}
```

**Подвох.** Дженерики параметризуют **тип или функцию целиком**, но не
отдельный метод существующего (уже не дженерик) типа — `func (s *Server)
Handle[T any](v T)` не компилируется. Если методу нужен параметр типа,
параметризовать приходится сам тип `Server[T]`.

## Что такое ограничения (constraints) и зачем нужна тильда `~`?

**Коротко.** Ограничение — это интерфейс, который вместо (или вместе с)
методов может перечислять допустимые типы через `|`. Такой интерфейс годится
только как ограничение параметра типа, а не как обычный интерфейс для
переменной.

```go
// go 1.18+
type Number interface {
    ~int | ~int32 | ~int64 | ~float32 | ~float64
}

func Sum[T Number](nums []T) T {
    var total T
    for _, n := range nums {
        total += n
    }
    return total
}

func main() {
    fmt.Println(Sum([]int{1, 2, 3}))          // 6
    fmt.Println(Sum([]float64{1.5, 2.5}))     // 4

    type Celsius int         // именованный тип с базовым типом int
    temps := []Celsius{20, 25, 30}
    fmt.Println(Sum(temps))  // 75 — Celsius подошёл БЛАГОДАРЯ тильде
}
```

Тильда `~int` означает «любой тип, чей базовый (underlying) тип — `int`», а
не только сам `int`. Без тильды (`int` вместо `~int` в перечислении)
ограничению удовлетворял бы только буквально тип `int`, и `Celsius` из
примера выше отсеялся бы с ошибкой компиляции — это частый вопрос на
понимание разницы.

Встроенные ограничения, которые не нужно объявлять самому: `any` (алиас
`interface{}`, введён вместе с дженериками), `comparable` (типы, поддерживающие
`==` и `!=` — годится как ограничение для ключей карт внутри дженерика). Для
упорядочивания (`<`, `>`) в стандартной библиотеке есть пакет `cmp` (с Go
1.21) с `cmp.Ordered`; до этого пользовались `golang.org/x/exp/constraints`.

**Подвох.** «Раз добавили дженерики, можно параметризовать что угодно» — нет:
не бывает ограничений на **поля** структуры (только на методы и множества
типов), нет специализации кода под конкретный тип внутри дженерика (только
`switch` через `any`, как обычная проверка типов в рантайме), и параметр типа
`T` — это чисто компиляторная сущность: сравнить его с типом в рантейме или
получить `T` как значение нельзя, только через `reflect`.

## Как дженерики реализованы под капотом и почему они не всегда быстрее интерфейсов?

**Коротко.** Компилятор Go использует подход GC shape stenciling: для типов с
одинаковой «формой» с точки зрения сборщика мусора (например, все указатели —
`*T` для любого `T`) генерируется **одна** копия машинного кода, а конкретный
тип передаётся неявным словарём во время выполнения. Для типов с разными
формами (`int` и `string`, например) компилятор всё же может сгенерировать
отдельные копии.

Практический вывод, который стоит явно назвать на интервью: дженерики — это
**не** макроподстановка C++-шаблонов с нулевой рантайм-ценой и **не всегда**
быстрее версии на интерфейсах — иногда из-за словаря типов или недостатка
инлайнинга они оказываются медленнее. Единственный надёжный способ понять,
что выгоднее в конкретном горячем месте, — бенчмарк (`go test -bench`), а не
интуиция.

**Когда применять дженерики:** контейнеры и структуры данных (стек, очередь,
дерево), функции над слайсами/картами, устранение дублирования кода, который
отличается только типом данных, но не поведением.

**Когда не применять:** если достаточно интерфейса с одним-двумя методами
(`Sum(x, y int) int` не нужно параметризовать, если реально используется
только `int`), если тип нужен ровно в одном месте, или если параметризация
добавляется «на будущее» без конкретной потребности — это усложняет API
без выигрыша.

**Глубже.** С появлением дженериков стандартная библиотека получила пакеты,
которые раньше приходилось писать руками для каждого типа отдельно: `slices`
(`slices.Contains`, `slices.Sort`, `slices.Index`), `maps` (`maps.Keys`,
`maps.Clone`), `cmp` (`cmp.Compare`, `cmp.Or`), а также дженерик-хелперы вроде
`sync.OnceValue` и `errors.Join`. Знание того, что для типового «найти элемент
в слайсе» или «отсортировать слайс дженериком» больше не нужно писать свою
реализацию под каждый тип, — хороший сигнал того, что кандидат следит за
изменениями в стандартной библиотеке, а не застрял на Go 1.17.

```go
// go 1.21+
import "slices"

func main() {
    xs := []int{3, 1, 2}
    slices.Sort(xs)
    fmt.Println(xs)                     // [1 2 3]
    fmt.Println(slices.Contains(xs, 2)) // true
}
```
