## Что такое метод в Go и на каких типах его можно объявить?

**Коротко.** Метод — это обычная функция с дополнительным аргументом перед
именем, приёмником (receiver): `func (u User) Name() string`. Объявлять методы
можно только для типов, определённых в **своём** пакете — добавить метод к
`int`, `string` или к типу из чужого пакета нельзя напрямую.

```go
type User struct {
    name string
}

func (u User) Name() string {
    return u.name
}

func main() {
    u := User{name: "alice"}
    fmt.Println(u.Name()) // alice
}
```

Обойти ограничение «нельзя добавить метод к чужому типу» можно, только
определив свой именованный тип поверх чужого:

```go
type MyInt int

func (m MyInt) Double() int {
    return int(m) * 2
}

// func (i int) Double() int { ... } — так нельзя, int не определён в этом пакете
```

**Подвох.** Метод и функция с тем же именем в том же пакете не конфликтуют —
это разные пространства имён, потому что метод всегда вызывается через
значение приёмника (`u.Name()`), а не как свободная функция.

## В чём разница между value receiver и pointer receiver?

**Коротко.** Value receiver (`func (u User) M()`) получает копию значения —
мутации внутри метода снаружи не видны. Pointer receiver (`func (u *User)
M()`) получает адрес оригинала — метод может менять состояние и не копирует
объект целиком при каждом вызове.

```go
type Counter struct {
    n int
}

func (c Counter) IncByValue() {
    c.n++ // меняет копию — снаружи ничего не изменится
}

func (c *Counter) IncByPointer() {
    c.n++ // меняет оригинал через указатель
}

func main() {
    c := Counter{}
    c.IncByValue()
    fmt.Println(c.n) // 0 — мутация потерялась вместе с копией

    c.IncByPointer()
    fmt.Println(c.n) // 1 — изменение видно
}
```

Практические правила выбора:

- если тип содержит `sync.Mutex` или другое некопируемое поле — только
  указатель, копирование такого значения `go vet` пометит как ошибку
  (`copylocks`);
- если метод должен менять состояние — указатель;
- если структура большая, а метод вызывается часто — указатель дешевле по
  копированию, даже если мутация не нужна;
- смешивать value- и pointer-receiver у одного типа без веской причины не
  стоит — это сбивает читателя: непонятно, ждать ли мутацию.

**Подвох.** Вызов `c.IncByPointer()` для переменной `c` компилируется без
явного `&c` — компилятор сам берёт адрес, если `c` адресуемая переменная. Но
если `c` — это результат вызова функции или элемент карты, взять адрес
неявно нельзя (см. ниже).

## Что такое method set и почему `T` иногда «не реализует» интерфейс, который реализует `*T`?

**Коротко.** Method set типа `T` — это только методы, объявленные с value
receiver. Method set типа `*T` — это методы с value receiver **и** с pointer
receiver. Отсюда: если хотя бы один метод объявлен на `*T`, то значение типа
`T` (не указатель) не входит в method set, необходимый для интерфейса, а
`*T` — входит.

```go
type Stringer interface {
    String() string
}

type Point struct{ X, Y int }

func (p *Point) String() string { // pointer receiver
    return fmt.Sprintf("(%d,%d)", p.X, p.Y)
}

func main() {
    p := Point{1, 2}

    var s Stringer = &p // OK: *Point реализует String()
    fmt.Println(s)

    // var s2 Stringer = p // ошибка компиляции:
    // Point does not implement Stringer (method String has pointer receiver)
}
```

Компилятор ругается именно на строке присваивания интерфейсу
(`var s2 Stringer = p`), а не там, где метод объявлен на `*Point`, — это
регулярно сбивает с толку на собеседовании, когда просят объяснить, «почему
ошибка не в методе».

**Подвох.** Внутри `main` вызов `p.String()` (без явного `&`) при этом
**скомпилируется**, потому что `p` — адресуемая переменная и компилятор сам
подставит `(&p).String()`. А вот `Point{1, 2}.String()` (результат литерала,
не переменная) или `m["key"].String()`, где `m` — `map[string]Point`, не
скомпилируются: у элемента карты нельзя неявно взять адрес, потому что карта
Go может в любой момент перехешироваться и переместить элемент в памяти.

```go
m := map[string]Point{"a": {1, 2}}
// m["a"].String() — ошибка: cannot call pointer method on m["a"]
v := m["a"]
v.String() // OK — v уже отдельная адресуемая копия
```

## Легально ли вызывать метод на nil-указателе?

**Коротко.** Да, это рабочая идиома, а не UB (undefined behavior). Вызов
метода — это просто вызов функции с явным первым аргументом-приёмником;
если внутри метода нет разыменования `nil`, паники не будет.

```go
type List struct {
    head *node
}

type node struct {
    val  int
    next *node
}

func (l *List) Len() int {
    if l == nil { // приёмник сам может быть nil
        return 0
    }
    n := 0
    for cur := l.head; cur != nil; cur = cur.next {
        n++
    }
    return n
}

func main() {
    var l *List // nil-указатель, память не выделена
    fmt.Println(l.Len()) // 0 — паники нет, метод сам проверил l == nil
}
```

Так реализуют, например, идиоматичные методы для связных структур и деревьев,
где «пустое дерево» естественно представлено `nil`-указателем, а не отдельным
sentinel-значением.

**Подвох.** Это работает, только если сам метод не разыменовывает поле
приёмника без проверки. `func (l *List) Head() *node { return l.head }` для
`nil`-приёмника упадёт с panic: nil pointer dereference, потому что `l.head`
требует прочитать поле из памяти по адресу `nil`.

## Что такое method value и method expression?

**Коротко.** `f := t.Method` — method value: замыкание, в котором приёмник
уже зафиксирован в момент создания `f`, а не в момент вызова `f()`. `f :=
T.Method` — method expression: обычная функция, где приёмник становится
явным первым аргументом.

```go
type Greeter struct {
    name string
}

func (g Greeter) Greet() string {
    return "hello, " + g.name
}

func main() {
    g := Greeter{name: "alice"}

    mv := g.Greet // method value — g скопирован СЕЙЧАС
    g.name = "bob"
    fmt.Println(mv()) // "hello, alice" — видит старое значение

    me := Greeter.Greet // method expression — приёмник как обычный аргумент
    fmt.Println(me(g))  // "hello, bob" — g передан явно, уже новое значение
}
```

**Подвох.** Классическая ловушка на value receiver — `defer t.Method()`.
Аргументы `defer`, включая неявный приёмник method value, вычисляются в
момент вызова `defer`, а не в момент фактического выполнения:

```go
type Logger struct{ prefix string }

func (l Logger) Flush() {
    fmt.Println(l.prefix, "flushed")
}

func run() {
    l := Logger{prefix: "start"}
    defer l.Flush() // копия l.prefix = "start" фиксируется ЗДЕСЬ
    l.prefix = "end"
    // ...
} // при выходе выведет "start flushed", а не "end flushed"
```

Если приёмник — указатель (`func (l *Logger) Flush()`), фиксируется адрес, а
не значение, поэтому `defer` увидит финальное состояние — ещё один аргумент в
пользу единообразного выбора receiver-а для типа.

## Как выбрать между интерфейсом и конкретным типом в сигнатуре функции?

**Коротко.** Идиома Go — «принимай интерфейсы, возвращай структуры» (accept
interfaces, return structs). Функция должна требовать от аргумента ровно тот
минимум поведения, который ей нужен, а возвращать — конкретный тип, чтобы
вызывающий код видел все доступные методы и не терял информацию.

```go
// хорошо: принимает io.Reader — работает с файлом, буфером, сетевым соединением
func CountLines(r io.Reader) (int, error) { /* ... */ }

// возвращает конкретный тип, а не интерфейс — вызывающий видит все методы *Client
func NewClient(addr string) *Client { /* ... */ }
```

Отсюда же и соглашение об именовании: геттер называют не `GetName()`, а
просто `Name()`; сеттер — `SetName(v string)`. Приставка `Get` в Go-коде
считается избыточной и не идиоматичной.

**Глубже.** Это правило тесно связано с местом объявления интерфейса — тема
следующего файла: интерфейс в Go принято объявлять **на стороне потребителя**
(рядом с функцией, которая его принимает), а не рядом с реализацией.
