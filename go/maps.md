## Что произойдёт при чтении и записи в `nil`-карту?

**Коротко.** `map[K]V` — хеш-таблица, ключ `K` обязан быть сравнимым типом
(слайс, карта и функция ключами быть не могут). Нулевая карта `var m
map[K]V` — это `nil`, и с ней асимметрично можно работать: **читать —
можно** (вернётся zero value типа значения), **писать — паника**. Карту
нужно предварительно создать через `make` или литерал.

```go
var m map[string]int // nil map
fmt.Println(m == nil, m["x"]) // true 0 — чтение безопасно, вернуло zero value

m["x"] = 1
// panic: assignment to entry in nil map
```

**Подвох.** Это симметричная ловушка вопросу про `nil`-слайс (см.
[Массивы и слайсы](arrays-slices.md)): там `append` в `nil`-слайс работает
без паники, а здесь запись в `nil`-карту падает. Собеседующие любят
спрашивать оба вопроса подряд именно из-за этой асимметрии — карта не может
«самостоятельно» выделить память под хеш-таблицу при первой записи, как это
незаметно делает `append` для слайса.

## Как отличить «ключа нет» от «значение равно нулевому»?

**Коротко.** Единственный надёжный способ — двухзначная форма чтения,
comma-ok: `v, ok := m[k]`. `ok` истинно тогда и только тогда, когда ключ
присутствует в карте, независимо от того, какое у него значение.

```go
m := map[string]int{"b": 2, "a": 1, "c": 0}

v, ok := m["c"]
fmt.Println(v, ok) // 0 true — ключ есть, значение действительно 0

v2, ok2 := m["z"]
fmt.Println(v2, ok2) // 0 false — ключа нет вообще
```

`delete(m, k)` безопасен для отсутствующего ключа — просто ничего не
делает, паники не будет:

```go
delete(m, "zzz")
fmt.Println(len(m)) // 3 — карта не изменилась
```

**Подвох.** Порядок итерации по карте намеренно рандомизирован рантаймом —
на него нельзя полагаться, и это сделано осознанно, чтобы код не завязывался
на детали реализации хеш-таблицы. Для стабильного, воспроизводимого вывода
ключи собирают и сортируют явно:

```go
keys := slices.Sorted(maps.Keys(m)) // maps.Keys + slices.Sorted, Go 1.23+
fmt.Println(keys) // [a b c]
```

## Почему `map[k].Field = x` не компилируется и как это обойти?

**Коротко.** Элементы карты в Go не адресуемы: `&m[k]` не компилируется, а
для значения-структуры `m[k].Field = x` — тоже, потому что это фактически
попытка получить адрес временного значения, которое карта возвращает при
чтении. Идиоматичный обход — читать значение целиком, менять локальную
копию и класть обратно, либо изначально хранить указатели `map[K]*V`.

```go
type Point struct{ X, Y int }

m := map[string]Point{"origin": {0, 0}}

// m["origin"].X = 5 // ошибка компиляции: cannot assign to struct field

p := m["origin"]
p.X = 5
m["origin"] = p
fmt.Println(m) // map[origin:{5 0}]

mp := map[string]*Point{"origin": {0, 0}}
mp["origin"].X = 9 // через указатель — работает, разыменование неявное
fmt.Println(*mp["origin"]) // {9 0}
```

**Подвох.** Выбор `map[K]V` со структурой против `map[K]*V` — не только
вопрос удобства записи полей, но и компромисс по аллокациям: указатели
добавляют работу сборщику мусора и лишний уровень косвенности при каждом
чтении, зато позволяют мутировать поле «на месте» и не платить за копирование
крупной структуры при каждом чтении/записи в карту.

Отдельная идиома — `map[K]struct{}` как множество: пустая структура `struct{}`
занимает 0 байт, поэтому такая карта эффективнее по памяти, чем `map[K]bool`.

```go
set := map[string]struct{}{"a": {}, "b": {}}
_, ok := set["a"]
fmt.Println(ok, len(set)) // true 2
```

## Потокобезопасна ли карта и что будет при конкурентной записи?

**Коротко.** Нет, обычная карта не защищена от гонок. Конкурентная запись
(или запись параллельно с чтением) не порождает неопределённое поведение
молча — рантайм **детектирует** это и завершает процесс с
`fatal error: concurrent map writes`. Важная деталь: это не `panic`, и
`recover` его не перехватывает — процесс падает безусловно.

Варианты решения по возрастанию сложности:

- `sync.RWMutex` вокруг обычной карты — самый простой и предсказуемый способ;
- шардирование — несколько карт с мьютексами, ключ распределяется по шардам
  хешем, снижает конкуренцию за одну блокировку;
- `sync.Map` из стандартной библиотеки — специализирована под конкретный
  сценарий: много независимых горутин читают и пишут в основном непересекающиеся
  ключи, а чтений значительно больше, чем записей. На «горячем» общем ключе или
  при частых записях в одни и те же ключи она обычно проигрывает обычной карте
  под `RWMutex`.

**Подвох.** «Раз есть `sync.Map` — надо всегда использовать её вместо
`map` + `Mutex` в конкурентном коде?» Нет, это частая ошибка: `sync.Map`
не generic (до недавнего времени работала через `interface{}`, что добавляет
приведения типов и накладные расходы), и её API специально уже, чем у обычной
карты. Документация самого пакета `sync` прямо рекомендует сначала попробовать
карту под мьютексом и переходить на `sync.Map` только если профилирование
показывает, что это оправдано именно для конкретного паттерна доступа.

**Глубже.** Мутации во время итерации `for range` по карте определены лишь
частично: удаление текущего или любого другого ключа во время итерации
безопасно (удалённый ключ просто не будет посещён, если ещё не был), а
добавление нового ключа во время итерации может быть посещено, а может и
нет — спецификация явно оставляет это неопределённым, и полагаться на
конкретное поведение нельзя.

## Что происходит с памятью карты после массового удаления ключей?

**Коротко.** Карта не сжимается сама: удаление ключей через `delete`
уменьшает логический размер (`len`), но не возвращает память бакетов
операционной системе. Если карта раздулась под пиковую нагрузку, а потом
почти опустела и должна оставаться маленькой — единственный надёжный способ
вернуть память — пересоздать карту заново.

`clear(m)` (Go 1.21+) — встроенная функция, которая быстро очищает
содержимое карты (или слайса), но именно очищает записи, а не уменьшает уже
выделенное число бакетов.

Если конечный размер известен заранее, стоит преаллоцировать через
`make(map[K]V, n)` — это уменьшает число перехеширований при заполнении.

**Глубже.** Внутреннее устройство знать полезно, но на собеседовании обычно
важнее свойства карты, а не детали реализации: классическая (до Go 1.24)
реализация хранит записи бакетами по 8 пар и использует старшие биты хеша
как `tophash` для быстрого отсева несовпадений, с инкрементальным ростом при
переполнении бакетов. Начиная с Go 1.24 реализация в стандартной библиотеке
заменена на Swiss Tables — другую внутреннюю структуру с той же семантикой
языка, но иным поведением по производительности и памяти. Для интервью
обычно достаточно знать сам факт смены реализации и то, что она не меняет
никаких гарантий языка — только характеристики производительности.
