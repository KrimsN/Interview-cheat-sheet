## Почему `int32` нельзя присвоить переменной `int64` без явного преобразования?

**Коротко.** Go — строго статически типизированный язык без неявных числовых
преобразований: даже `int` и `int64` — разные типы для компилятора, и любая
операция между ними требует явного приведения `T(x)`. Это защита от тихой
потери точности, которую C и подобные языки допускают молча.

```go
var a int32 = 10
var b int64 = a       // ошибка компиляции: mismatched types
var c int64 = int64(a) // так — корректно
```

Целочисленные типы: `int`/`uint` (размер платформы, на практике почти всегда
64 бита), `int8`..`int64`, `uint8`..`uint64`, плюс синонимы `byte = uint8` и
`rune = int32`. Переполнение целых **не паникует** — оно определено
стандартом и оборачивается по модулю разрядности:

```go
var x int8 = 127
x++
fmt.Println(x) // -128 — переполнение, не паника
```

**Подвох.** «Раз переполнение не паникует, как его отловить?» Штатно —
никак, это ответственность разработчика: проверять границы вручную или
использовать пакет `math/bits`/`math.MaxInt8` для явных проверок перед
операцией. В отличие от деления на ноль для целых (которое как раз
паникует), переполнение — тихая ошибка.

## Что такое нетипизированные константы и почему `const big = 1 << 62` компилируется?

**Коротко.** Константы в Go вычисляются с произвольной точностью на этапе
компиляции и не имеют типа, пока не будут где-то использованы — тип
подставляется в момент присваивания или передачи в функцию. Поэтому одна и
та же нетипизированная константа может быть использована и как `float64`, и
как `int64`.

```go
const big = 1 << 62 // нетипизированная, точность выше int64 на этапе счёта

var f float64 = big
var i int64 = big
fmt.Println(f, i) // 4.611686018427388e+18 4611686018427387904
```

Если бы `big` была объявлена как `const big int64 = 1 << 62`, присвоить её
`float64` без явного `float64(big)` не получилось бы — типизированная
константа подчиняется тем же правилам, что обычная переменная. Именно
отсутствие типа у нетипизированных констант позволяет писать
`time.Second * 5` или `math.Pi` без постоянных преобразований.

**Подвох.** Популярный вопрос: «а если результат не влезает в тип, к
которому его приводят?» — тогда ошибка возникает не в момент вычисления
константы (оно происходит с произвольной точностью), а в момент попытки
присвоить её переменной конкретного типа: `var x int8 = 1 << 62` не
скомпилируется, хотя `const big = 1 << 62` — валидное выражение само по себе.

## Чем `type UserID int64` отличается от `type Alias = int64`?

**Коротко.** `type X T` объявляет **новый именованный (defined) тип** — он
получает собственную идентичность, свой набор методов и требует явного
преобразования для перехода к `T` и обратно. `type X = T` объявляет
**псевдоним (alias)** — просто другое имя для того же самого типа, полностью
взаимозаменяемое, без преобразований.

```go
type UserID int64 // новый тип
type Alias = int64 // псевдоним для int64

func (id UserID) String() string {
    return fmt.Sprintf("user#%d", id)
}

var id UserID = 42
fmt.Println(id) // user#42 — вызывается метод String()

var a Alias = 5
var b int64 = a // OK: Alias и int64 — буквально один тип

var c int64 = int64(id) // а вот UserID -> int64 требует явного преобразования
```

Практический смысл именованных типов — повесить на примитив собственные
методы и получить проверку компилятором, что `UserID` и `OrderID`, даже если
оба физически `int64`, нельзя перепутать местами в сигнатуре функции.
Псевдонимы же используют в основном для постепенного переезда типа между
пакетами без разрушения обратной совместимости.

**Подвох.** «Значит, `UserID` и `int64` — вообще разные, несовместимые
сущности?» Не совсем: `UserID` **основан** на `int64` (underlying type тот
же), поэтому все арифметические и сравнивающие операторы для него работают
как для `int64`, и явное преобразование `UserID(x)`/`int64(y)` в обе стороны
всегда допустимо и никогда не паникует, в отличие от утверждения типа для
интерфейсов.

## Какие типы сравнимы оператором `==` и когда сравнение интерфейсов паникует?

**Коротко.** Сравнимы (`comparable`): числа, строки, `bool`, указатели,
каналы, интерфейсы и составленные из сравнимых полей массивы и структуры.
**Не сравнимы**: слайсы, карты и функции (кроме сравнения с `nil`). Это
напрямую ограничивает, что можно использовать как ключ карты и что годится
под generic-ограничение `comparable`.

С интерфейсами тоньше: `==` сравнивает и динамический тип, и динамическое
значение. Если типы разные — результат просто `false`. Но если типы
совпадают, а сам этот динамический тип оказывается несравнимым (например,
внутри лежит слайс) — сравнение **не возвращает `false`, а паникует** в
рантайме.

```go
var a, b interface{} = []int{1}, []int{1}
fmt.Println(a == b)
// panic: runtime error: comparing uncomparable type []int
```

**Подвох.** Это одна из немногих операций в Go, которая выглядит абсолютно
безопасной по сигнатуре (`==` — оператор, не функция, которая может вернуть
`error`), но может уронить процесс в рантайме. На собеседовании часто
спрашивают именно контраст: «сравнение интерфейсов с разными типами — не
паникует, с одинаковым несравнимым типом внутри — паникует».

**Глубже.** Для структур, содержащих слайсы или карты, `==` вообще не
скомпилируется на этапе компиляции (компилятор видит несравнимый тип поля
статически). Для их сравнения по значению используют `reflect.DeepEqual`,
но он медленный и не всегда предсказуем на графах с циклами и указателями;
в тестах вместо него обычно берут `github.com/google/go-cmp`, который даёт
понятный diff при несовпадении.

## Чем конвертация типа `T(x)` отличается от утверждения типа `x.(T)`?

**Коротко.** `T(x)` — конвертация: превращает значение одного конкретного
типа в другой на этапе компиляции (или паникует предсказуемо для числовых
переполнений — не паникует вовсе, просто оборачивается). `x.(T)` —
утверждение типа: работает только для интерфейсных значений и проверяет в
рантайме, какой конкретный тип лежит внутри интерфейса сейчас.

```go
var x interface{} = "hello"

s, ok := x.(string) // безопасная форма: ok сообщает об успехе
fmt.Println(s, ok)  // hello true

n, ok := x.(int) // тип не совпал: n=0 (zero value), ok=false, паники нет
fmt.Println(n, ok) // 0 false

// n2 := x.(int) // однозначная форма без ok — здесь была бы паника:
// panic: interface conversion: interface {} is string, not int
```

**Подвох.** Не путать конвертацию числовых типов (`int64(x)`), конвертацию
именованных типов (`UserID(x)`) и утверждение типа для интерфейсов
(`x.(T)`) — это три синтаксически похожих, но семантически разных
механизма: первые два — целиком проверяются компилятором, третий — частично
переносит проверку в рантайм, и именно поэтому у него есть двухзначная
безопасная форма.

## Что вы знаете про `unsafe.Pointer` и когда он оправдан?

**Коротко.** `unsafe.Pointer` — «люк» в системе типов: позволяет
преобразовывать указатели любых типов друг в друга и в `uintptr`, в обход
проверок компилятора и части гарантий сборщика мусора. В прикладном коде
почти никогда не нужен; типичное легитимное применение — zero-copy
конвертация `[]byte` в `string` и обратно в высоконагруженном коде, где
лишняя аллокация и копирование заметны в профиле.

**Подвох.** `uintptr` — просто число, а не указатель: сборщик мусора не
отслеживает объект через `uintptr`, поэтому если между вычислением адреса и
его использованием произойдёт сборка мусора (тем более перемещение объекта
в рантаймах, где это возможно), указатель может «протухнуть». Пакет `unsafe`
документирует конечный список безопасных шаблонов преобразований — писать
что-то за их пределами означает полагаться на детали реализации конкретной
версии компилятора, а не на гарантии языка. В код с ревью такое обычно не
пропускают без очень веской причины (обычно это cgo или совсем горячий путь
после профилирования).
