## Чем массив отличается от слайса?

**Коротко.** Массив `[N]T` — значение фиксированной длины, и длина — часть
его типа: `[3]int` и `[4]int` несовместимы друг с другом даже по элементу.
Слайс — динамический дескриптор поверх массива-хранилища (backing array),
без фиксированной длины в типе. Присваивание и передача массива в функцию
копируют его **целиком**, а слайса — только сам дескриптор (три поля),
данные при этом остаются общими.

```go
func modifyArray(a [3]int) {
    a[0] = 99 // меняет локальную копию
}

func modifySlice(s []int) {
    s[0] = 99 // меняет общие данные через backing array
}

arr := [3]int{1, 2, 3}
modifyArray(arr)
fmt.Println(arr) // [1 2 3] — не изменился

s := []int{1, 2, 3}
modifySlice(s)
fmt.Println(s) // [99 2 3] — изменился

a1, a2 := [3]int{1, 2, 3}, [3]int{1, 2, 3}
fmt.Println(a1 == a2) // true — массивы сравнимы оператором ==, слайсы нет
```

**Подвох.** «Раз слайс передаётся в функцию и функция может менять его
элементы — значит, слайс передаётся по ссылке?» Нет: сам дескриптор
(указатель на backing array, `len`, `cap`) копируется по значению, как и
всё в Go. Именно поэтому `append` внутри функции, приведший к переаллокации,
**не виден** снаружи — изменился локальный дескриптор, а не тот, что у
вызывающей стороны. Подробнее — в следующем вопросе.

## Как устроен `append` и почему его результат обязательно присваивают обратно?

**Коротко.** Слайс — это дескриптор из трёх полей: указатель на backing
array, `len` и `cap`. `append` смотрит на `cap`: если места хватает, новый
элемент пишется в тот же массив на месте `len`, и `len` увеличивается — без
переаллокации. Если места не хватает, выделяется новый, обычно больший
массив, старые данные копируются туда, а связь со старым массивом теряется.
В обоих случаях `append` возвращает **новый дескриптор**, и только
присваивание `s = append(s, x)` гарантирует, что переменная видит актуальные
`len`/`cap`/указатель.

```go
a := make([]int, 3, 5) // len=3, cap=5 — есть запас
a[0], a[1], a[2] = 1, 2, 3

b := a[1:3] // b делит backing array с a: len=2, cap=4
fmt.Println(b, len(b), cap(b)) // [2 3] 2 4

b[0] = 100 // запись через b видна в a — общие данные
fmt.Println(a) // [1 100 3]

b = append(b, 999) // cap(b) хватает -> пишет в тот же массив, за границей len(a)
fmt.Println("a:", a, "a[:4]:", a[:4]) // a: [1 100 3]  a[:4]: [1 100 3 999]
```

`append(b, 999)` не тронул `a` напрямую (его `len` остался 3), но записал
`999` в ячейку backing array сразу за последним элементом `a` — и если
позже кто-то сделает `append(a, x)`, этот `x` молча затрёт то самое `999`,
или наоборот, чужой `append` к `a` неожиданно «появится» в `b`. Это и есть
классическая ловушка «слайс от слайса».

Защита — трёхиндексный срез `s[low:high:max]`, который явно ограничивает
`cap` результата, вынуждая следующий `append` уйти в новый массив:

```go
d := make([]int, 3, 5)
d[0], d[1], d[2] = 1, 2, 3
c := d[1:3:3] // cap ограничен len=2 — расширяться в d[3] некуда
c = append(c, 7) // cap не хватает -> новый backing array, d не тронут
fmt.Println("d:", d, "c:", c) // d: [1 2 3]  c: [2 3 7]
```

Другой способ — явное копирование через `copy` или `slices.Clone`, когда
нужно гарантированно разорвать связь с исходным массивом.

**Подвох.** Если размер результата известен заранее, стоит преаллоцировать
через `make([]T, 0, n)`: рост capacity в реализации Go — примерно удвоение
для небольших слайсов и коэффициент около 1.25 для больших, но точные числа
не закреплены спецификацией и являются деталью реализации, а не гарантией
языка — полагаться на конкретную формулу нельзя, только на амортизированную
константу сложности `append`.

## Что делает `copy` и в чём типичная ошибка при его использовании?

**Коротко.** `copy(dst, src)` копирует `min(len(dst), len(src))` элементов и
возвращает их фактическое число. Частая ошибка — вызвать `copy` в слайс
нулевой **длины** (даже с ненулевой ёмкостью): скопируется ровно ноль
элементов, потому что `copy` ограничен именно `len`, а не `cap`.

```go
dst := make([]int, 0) // len=0, cap=0
src := []int{1, 2, 3}
n := copy(dst, src)
fmt.Println(n, dst) // 0 [] — копировать в нулевую длину некуда

dst2 := make([]int, 3) // len=3
n2 := copy(dst2, src)
fmt.Println(n2, dst2) // 3 [1 2 3]
```

**Подвох.** Отсюда же путаница вокруг `nil`-слайса и пустого `[]T{}`: оба
имеют `len == 0`, с обоими одинаково безопасно работают `len`, `cap`,
`append` и `for range`, но это разные значения — различимы сравнением с
`nil` и при сериализации в JSON (`nil` даёт `null`, пустой слайс — `[]`).

```go
var s []int
fmt.Println(s == nil, len(s), cap(s)) // true 0 0
s = append(s, 1)                       // append работает и с nil-слайсом
fmt.Println(s)                         // [1]

empty := []int{}
fmt.Println(empty == nil) // false — пустой, но не nil
```

## Как удалить элемент из слайса и в чём разница подходов по производительности?

**Коротко.** Готовой функции «удалить элемент» в языке нет (кроме
`slices.Delete` из стандартной библиотеки с Go 1.21). Два ручных идиоматичных
способа отличаются тем, жертвуют ли они порядком элементов ради скорости:

```go
// сохраняет порядок, O(n) — сдвигает хвост
func removeOrdered(s []int, i int) []int {
    return append(s[:i], s[i+1:]...)
}

// не сохраняет порядок, O(1) — переносит последний элемент на место удалённого
func removeFast(s []int, i int) []int {
    s[i] = s[len(s)-1]
    return s[:len(s)-1]
}

a := []int{1, 2, 3, 4, 5}
a = removeOrdered(a, 1)
fmt.Println(a) // [1 3 4 5]

b := []int{1, 2, 3, 4, 5}
b = removeFast(b, 1)
fmt.Println(b) // [1 5 3 4] — порядок сломан, зато без сдвига
```

**Подвох.** Если элементы слайса — указатели или содержат указатели (в том
числе интерфейсы), после `s[:len(s)-1]` «обрезанный» хвостовой элемент
физически остаётся в backing array и удерживает объект живым для сборщика
мусора — классическая утечка памяти. Его нужно явно занулить перед
уменьшением длины: `s[len(s)-1] = nil`. Та же логика утечки применима к
любому маленькому слайсу, взятому от большого (или подстроке от большого
файла в памяти): маленький слайс держит в живых **весь** backing array; если
нужен только небольшой кусок надолго — его явно копируют.

**Глубже.** С Go 1.21 в стандартной библиотеке есть дженерик-пакет `slices`,
который избавляет от большинства таких ручных циклов: `Sort`, `SortFunc`,
`Contains`, `Index`, `Clone`, `Equal`, `BinarySearch`, `Delete`, `Insert`,
`Reverse`.

```go
c := []int{3, 1, 2}
slices.Sort(c)
fmt.Println(c, slices.Contains(c, 2), slices.Index(c, 3))
// [1 2 3] true 2
```

Для многомерных данных `[][]T` — это слайс слайсов, где строки могут быть
разной длины и аллоцируются отдельно друг от друга; для настоящей плотной
матрицы фиксированного размера часто выгоднее (меньше аллокаций, лучше
локальность памяти) один плоский слайс `make([]T, w*h)` с ручным индексом
`i*w + j`.
