## Чем пакет отличается от модуля?

**Коротко.** Пакет — единица компиляции: один каталог с `.go`-файлами
одного `package`. Модуль — единица версионирования и распространения:
дерево пакетов с общим `go.mod`, которое публикуется и подключается целиком
как зависимость.

Один модуль обычно содержит много пакетов. Импортируется всегда конкретный
пакет по его пути, а версия резолвится на уровне модуля целиком:

```go
// go.mod
module example.com/shop

go 1.22

require github.com/google/uuid v1.6.0
```

Имя пакета — короткое, без подчёркиваний и без дублирования в
идентификаторах: `http.Server`, а не `http.HTTPServer`; пакет `strconv`,
а не `string_conv`. Имя каталога и имя пакета обычно совпадают, но не
обязаны — это тоже любят спрашивать: `package main` может лежать в каталоге
`cmd/server/`.

**Подвох.** «Один каталог — один пакет» верно почти всегда, но с одним
исключением: в каталоге допускаются файлы `*_test.go` с суффиксом `package
foo_test` (внешний тестовый пакет) — формально второй `package` в том же
каталоге, но только для тестов, в продовую сборку он не попадает.

## Что такое `init()` и когда он вызывается?

**Коротко.** Функция `init()` без аргументов и без возвращаемого значения,
которая выполняется автоматически после инициализации всех переменных
пакета, но до `main()`. В одном пакете их может быть несколько — все
файлы одного пакета инициализируются в порядке имён файлов, `init`-ы внутри
файла — в порядке объявления.

```go
package main

import (
	"fmt"
	_ "net/http/pprof" // импорт только ради побочного эффекта init()
)

var counter = initCounter()

func initCounter() int {
	fmt.Println("var init")
	return 0
}

func init() {
	fmt.Println("init 1")
}

func init() {
	fmt.Println("init 2")
}

func main() {
	fmt.Println("main")
}
// вывод:
// var init
// init 1
// init 2
// main
```

Импорт с подчёркиванием (`import _ "github.com/lib/pq"`) — идиома
«зарегистрировать побочный эффект», не используя ничего из пакета напрямую:
драйвер БД регистрирует себя в `database/sql` через свой `init()`.

**Подвох.** Порядок инициализации между **разными пакетами** определяется
графом зависимостей: сначала инициализируются все импортируемые пакеты
(рекурсивно), и только потом — сам пакет. Порядок между файлами одного
пакета — по имени файла, но полагаться на это в продовом коде не стоит:
если инициализация одного `init()` зависит от результата другого в том же
пакете, это повод объединить их или явно вызвать по цепочке.

## Почему в Go нет циклических импортов и как их обходить?

**Коротко.** Компилятор запрещает цикл на уровне пакетов: если `a` импортирует
`b`, `b` не может (даже транзитивно) импортировать `a`. Это архитектурное
ограничение, а не техническое неудобство — оно вынуждает явно выделять общие
абстракции.

Типичное лечение — вынести общий интерфейс или тип в третий, более базовый
пакет, от которого зависят оба:

```text
// было: order -> customer -> order (цикл, не скомпилируется)

// стало:
// domain          — общие типы и интерфейсы, ни от кого не зависит
// order  -> domain
// customer -> domain
```

**Подвох.** «Разбить на два файла в одном пакете» цикл не лечит — единица
проверки циклов это пакет (каталог), а не файл; файлы одного пакета видят
друг друга без импорта в принципе.

## Как ограничить видимость пакета: зачем нужен `internal/`?

**Коротко.** `internal/` — единственный настоящий механизм ограничения
видимости **между пакетами** в Go (в отличие от `PascalCase`/`camelCase`,
который ограничивает видимость внутри пакета). Пакеты внутри каталога
`internal/` доступны для импорта только из поддерева, корнем которого
является родитель `internal`.

```text
example.com/shop/
├── internal/
│   └── billing/       // импортируется только из example.com/shop/...
├── cmd/
│   └── server/         // может импортировать shop/internal/billing
└── go.mod
```

Внешний модуль, который зависит от `example.com/shop`, не сможет
импортировать `example.com/shop/internal/billing` — компилятор явно
запретит это на этапе сборки, а не только «по договорённости», как с
экспортируемыми/неэкспортируемыми идентификаторами.

**Подвох.** Заглавная буква (`ExportedFunc`) регулирует видимость **внутри
модуля/пакета** — снаружи пакета всё равно можно импортировать сам пакет и
пользоваться его экспортируемым API. `internal/` регулирует, кто вообще
может **импортировать пакет целиком**, независимо от того, что в нём
экспортировано.

## Что такое `go.mod` и `go.sum`, зачем нужны оба файла?

**Коротко.** `go.mod` описывает сам модуль и его прямые зависимости
(декларативно, что нужно); `go.sum` — криптографические хеши всех модулей
в графе зависимостей (для проверки целостности при каждой загрузке).

```go
// go.mod
module example.com/shop

go 1.22

require (
	github.com/google/uuid v1.6.0
	golang.org/x/sync v0.7.0
)

replace example.com/shop/internal/legacy => ../legacy // локальная замена

exclude github.com/broken/pkg v1.2.0 // явно исключить версию из графа
```

- `go mod tidy` — привести `go.mod`/`go.sum` в соответствие фактическому
  использованию: добавить недостающее, убрать неиспользуемое;
- `go mod why <pkg>` — объяснить, зачем модуль вообще попал в граф зависимостей;
- `go mod graph` — вывести граф зависимостей целиком;
- `go mod vendor` — скопировать все зависимости в каталог `vendor/` (сборки
  без сети).

**Подвох.** `go.sum` — это не lock-файл в смысле npm/yarn (там нет решения
«какую версию ставить», только хеши для проверки того, что скачано именно
то, что ожидалось). Версии резолвит алгоритм MVS, применяясь к `go.mod`.

## Как Go выбирает версии зависимостей?

**Коротко.** Алгоритм **MVS (minimal version selection)**: Go берёт
**минимальную** версию, которая удовлетворяет всем требованиям во всём
графе зависимостей, а не максимальную доступную. Это принципиально отличает
Go от npm/pip, где по умолчанию тянется самая свежая совместимая версия.

Если модуль `A` требует `lib v1.2.0`, а модуль `B` (тоже зависимость
проекта) требует `lib v1.4.0`, итоговая сборка получит `v1.4.0` — минимальную
версию, которая одновременно удовлетворяет **обоим** требованиям
(наибольшую из минимально необходимых). Более новая `v1.9.0`, даже если она
существует, взята не будет, пока кто-то в графе явно её не потребует.

**Подвох.** «MVS даёт более старые и потенциально более уязвимые версии» —
частое возражение, поэтому `go get -u` обновляет зависимости явно, а
`govulncheck` проверяет граф на известные уязвимости независимо от того,
насколько версии свежие. Обратная сторона MVS — воспроизводимость: сборка
одного и того же `go.mod` даёт одинаковый набор версий без «плавающего»
резолвинга.

## Что такое semantic import versioning и псевдоверсии?

**Коротко.** Начиная с major-версии 2, версия становится частью **пути
импорта**: `example.com/mod/v2`. Это позволяет держать в одном бинарнике
одновременно `v1` и `v2` одного модуля как формально разные пакеты.

```go
import (
	old "example.com/mod"     // v0 или v1 — без суффикса
	new "example.com/mod/v3"  // v3 — суффикс обязателен
)
```

Для зависимостей без тегов (взятых по коммиту) Go генерирует **псевдоверсию**
вида `v0.0.0-20240101120000-abcdef123456`: дата коммита в UTC и первые
символы хеша — это позволяет однозначно и воспроизводимо ссылаться на
конкретный коммит там, где семантического тега нет.

**Подвох.** Забыть добавить `/v2` в путь импорта и в `module` в `go.mod` —
частая ошибка при выпуске второй мажорной версии: без суффикса Go считает
это просто продолжением `v1`, и `go mod tidy` откажется резолвить версию
выше `v1.x.x`.

## Как устроены прокси зависимостей и приватные модули?

**Коротко.** По умолчанию `go get` ходит не напрямую в VCS, а через
`GOPROXY` (по умолчанию `proxy.golang.org`) и сверяет хеши с `GOSUMDB`
(публичный реестр контрольных сумм) — это и кеширует загрузки, и защищает
от подмены пакета после публикации.

```bash
# приватные модули компании — не через публичный прокси и sumdb
export GOPRIVATE=example.com/internal/*
export GOFLAGS=-mod=readonly   # не менять go.mod/go.sum неявно при сборке
```

`GOPRIVATE` одной переменной задаёт сразу и `GONOSUMCHECK` (не проверять по
`GOSUMDB`), и `GONOPROXY` (не ходить через публичный прокси) для указанных
префиксов путей — обычно достаточно её одной для внутренних модулей.

**Подвох.** `GOFLAGS=-mod=mod` (поведение по умолчанию до недавних версий)
разрешает командам вроде `go build` неявно дописывать `go.mod`/`go.sum` при
обнаружении недостающей зависимости. В CI это нежелательно — используют
`-mod=readonly` (или `go mod verify`/`go mod tidy -diff` как отдельный шаг),
чтобы сборка падала явно, а не молча меняла файлы модуля.

## Что такое workspaces (`go.work`)?

**Коротко.** `go.work` (с Go 1.18) позволяет разрабатывать несколько
модулей одновременно, используя локальные версии друг друга, — без того,
чтобы прописывать `replace` в `go.mod` каждого модуля (который потом нужно
не забыть убрать перед коммитом).

```go
// go.work
go 1.22

use (
	./shop
	./shop/internal/legacy
	../shared-lib
)
```

Пока действует `go.work`, команды `go build`/`go test`, запущенные из любого
из перечисленных модулей, видят локальные версии остальных модулей списка,
даже если в их `go.mod` указана опубликованная версия.

**Подвох.** `go.work` — инструмент **локальной разработки**, его не
коммитят в общий репозиторий как часть сборки (обычно добавляют в
`.gitignore`), в отличие от `replace` в `go.mod`, который иногда осознанно
коммитят (например, форк зависимости на постоянной основе).

## Что происходит при `go build` и как получить статический бинарь?

**Коротко.** `go build` компилирует пакет `main` со всеми зависимостями в
один исполняемый файл; по умолчанию (без cgo) получается статически
слинкованный бинарь без внешних зависимостей рантайма.

```bash
# кросс-компиляция без установки отдельного тулчейна
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o app ./cmd/server

# уменьшить размер и убрать отладочную информацию, прошить версию в бинарь
go build -ldflags "-s -w -X main.version=1.4.2" -o app ./cmd/server

# воспроизводимая сборка без путей локальной машины в бинарнике
go build -trimpath -o app ./cmd/server
```

`CGO_ENABLED=0` отключает cgo и даёт **действительно** статический бинарь —
это критично для образов `FROM scratch`/`distroless`: с включённым cgo (по
умолчанию, если в системе есть C-тулчейн и код использует cgo) бинарь может
динамически линковаться с `libc`, и в минимальном образе без `libc` просто не
запустится.

**Подвох.** cgo — это не только «медленнее»: каждый переход Go↔C дорог
(смена стека, синхронизация с планировщиком), кросс-компиляция «из коробки»
перестаёт работать без соответствующего C-тулчейна под целевую платформу, и
блокирующий C-вызов занимает отдельный поток ОС (Go-планировщик не может
приостановить C-код так же дёшево, как горутину).

## Что такое build tags и файлы с суффиксами платформ?

**Коротко.** Build constraints управляют тем, какие файлы попадают в сборку
для конкретной платформы или конфигурации — либо директивой `//go:build`,
либо суффиксом имени файла (`_linux.go`, `_amd64.go`, `_test.go`).

```go
//go:build linux && amd64

package platform

func osName() string { return "linux/amd64" }
```

```go
//go:build !windows

package platform

func supportsSyslog() bool { return true }
```

Рядом стоят две другие директивы-комментарии, которые часто путают с build
tags: `//go:embed` (встраивает файл или каталог в бинарь как `[]byte`/
`string`/`embed.FS` на этапе компиляции) и `//go:generate` (маркер команды,
которую запускает `go generate`, но не сам `go build`, — типично для
генерации кода из `.proto` или мока интерфейса).

**Подвох.** У директивы `//go:build` обязательна пустая строка перед
`package` и она должна идти в самом начале файла (до неё — только
комментарии и пустые строки), иначе она молча не действует как build
constraint, а остаётся обычным комментарием.
