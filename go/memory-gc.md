## Как компилятор решает, класть значение на стек или в кучу?

**Коротко.** Это делает **escape analysis** на этапе компиляции: если значение
не может «пережить» функцию, оно остаётся на стеке; если указатель на него
может утечь наружу — уходит в кучу. Правило «`new`/`&T{}` — всегда куча»
неверно: место размещения решает не синтаксис, а то, как используется
результат.

Стек в Go — это стек конкретной горутины, а не общий системный стек. Класть
значение на него дёшево: выделение — это просто сдвиг указателя стека,
освобождение — возврат из функции, без участия GC. Поэтому компилятор всегда
старается оставить значение на стеке и переносит его в кучу только когда
не может доказать, что это безопасно.

Типичные причины «убегания» в кучу:

- указатель на локальную переменную возвращается из функции или сохраняется
  в структуре/канале/глобальной переменной, которая переживёт функцию;
- размер значения неизвестен на этапе компиляции (например, `make([]T, n)`
  с переменным `n`);
- значение кладётся в интерфейс (`interface{}`, `any`), а не используется
  как конкретный тип — если только он не помещается в само слово интерфейса;
- значение захватывается замыканием, которое живёт дольше вызывающей функции
  (например, передаётся в горутину или сохраняется как callback);
- значение слишком большое — компилятор считает работу со стеком дороже
  копирования и сам решает вынести его в кучу.

Проверить решение компилятора можно флагом `-m` (два `-m` — подробнее,
с указанием причины):

```go
package main

// go build -gcflags="-m -l" escape.go
// (флаг -l отключает инлайнинг, иначе обе функции подставятся в main
// и сообщения об escape будут относиться уже не к ним, а к main)

func onStack() int {
	x := 42       // не убегает: значение используется только внутри функции
	return x      // возвращается КОПИЯ, а не указатель
}

func onHeap() *int {
	y := 42       // возвращается указатель на y,
	return &y     // значит y должно пережить возврат из onHeap
}

func main() {
	_ = onStack()
	_ = onHeap()
}
```

Компилятор для этого файла напечатает:

```text
./escape.go:12:2: moved to heap: y
```

Про `x` компилятор не печатает ничего — молчание и есть ответ: раз
escape-анализ не нашёл причины вынести `x` в кучу, он остаётся на стеке без
отдельного сообщения. А про `y` явно сказано `moved to heap`, потому что
наружу возвращается указатель на него.

**Подвох.** «Слайс или структура, переданные по значению в функцию, точно
останутся на стеке?» Нет — если внутри функции их адрес куда-то сохраняется
(в глобальную переменную, в другую структуру с большим временем жизни,
передаётся в горутину), escape analysis всё равно вынесет их в кучу, даже
если сам параметр был передан по значению.

**Глубже.** Popular пример с интерфейсом: `var w io.Writer = buf` может
заставить `buf` убежать в кучу, даже если без интерфейса он остался бы на
стеке, — потому что интерфейсное значение хранит указатель на данные, если
они не помещаются в одно машинное слово. Отсюда правило: не стоит
абстрагировать через интерфейс на «горячем пути», если профиль показывает
рост аллокаций.

## Как растёт стек горутины?

**Коротко.** Стек горутины начинается маленьким (несколько килобайт) и растёт
**копированием**: при нехватке места рантайм выделяет новый стек вдвое
большего размера, переносит содержимое старого и поправляет все указатели,
включая указатели внутри самого стека.

Это возможно, потому что Go-рантайм контролирует все точки, где стек может
переполниться (вставляет проверку в пролог функции), и знает точное
расположение указателей на стеке благодаря информации о типах, собранной
компилятором. Именно поэтому в Go нельзя брать «сырой» адрес переменной на
стеке и хранить его как `uintptr` через `unsafe` — при следующем росте стека
адрес станет невалидным, а рантайм об этом указателе не узнает и не поправит
его.

```go
func recurse(n int) int {
	var buf [128]byte // на каждом уровне рекурсии выделяется на стеке
	_ = buf
	if n == 0 {
		return 0
	}
	return 1 + recurse(n-1)
}
```

При глубокой рекурсии стек горутины несколько раз удвоится и переедет — это
прозрачно для Go-кода, но объясняет, почему адреса локальных переменных
«ассемблерно» нестабильны.

**Подвох.** «У горутины стек фиксированного размера, поэтому их дёшево
создавать тысячами» — верно лишь отчасти: стартовый размер маленький (около
2 КБ), но верхняя граница по умолчанию — 1 ГБ (настраивается через
`debug.SetMaxStack`), и при глубокой рекурсии или больших локальных массивах
рост стека — не бесплатная операция: копирование линейно по размеру стека.

## Как устроен аллокатор Go?

**Коротко.** Это адаптация **TCMalloc**: память делится на классы размеров
(`mspan`), у каждого P (processor, планировочная единица) есть локальный кэш
`mcache` без блокировок, за ним — общий `mcentral`, а дальше — `mheap`,
который запрашивает память у ОС.

Путь аллокации мелкого объекта (до 32 КБ): сначала пробуем взять свободный
блок нужного размерного класса из `mcache` текущего P — это быстрый путь без
блокировок, потому что P у каждой запущенной горутины свой. Если в `mcache`
пусто, идём в `mcentral` (общий для всех P, но уже с блокировкой), а если и
там нечем пополнить кэш — в `mheap`, который может попросить память у ОС.
Крупные объекты (>32 КБ) выделяются напрямую из `mheap`, минуя размерные
классы.

**Подвох.** Размерные классы означают, что реальная аллокация почти всегда
чуть больше запрошенной (округление вверх до ближайшего класса) — это
источник заметной на профиле «внутренней фрагментации», а не бага в
приложении.

## Как работает сборщик мусора в Go?

**Коротко.** Конкурентный, **не перемещающий** (non-moving) сборщик с
трёхцветной разметкой (tri-color mark-and-sweep) и write barrier. Он
работает параллельно с программой; полные stop-the-world паузы — доли
миллисекунды, а не десятки миллисекунд, как в наивной реализации.

Идея трёхцветной разметки:

- **белый** — потенциальный мусор (пока не посещён сборщиком);
- **серый** — объект найден и помещён в очередь, но его поля ещё не
  просканированы;
- **чёрный** — объект и все поля, на которые он ссылается, просканированы.

Цикл идёт так: сначала все объекты белые, корни (стеки, глобальные
переменные, регистры) красятся в серый. Затем GC-воркеры конкурентно с
программой берут серые объекты, красят их в чёрный и красят в серый всё, на
что они ссылаются, — пока серых не останется. Всё оставшееся белым — мусор,
его память возвращается аллокатору (в non-moving сборщике объекты **не
двигаются** в памяти — в отличие от, например, JVM, — поэтому указатели не
инвалидируются, но и дефрагментации кучи не происходит).

Проблема в том, что программа продолжает выполняться во время разметки и
может переписать указатели так, что чёрный объект получит ссылку на белый —
тогда объект будет ошибочно собран. Это решает **write barrier**: пока GC
активен, каждая запись указателя перехватывается рантаймом и красит целевой
объект в серый, если это необходимо, — гарантируя инвариант «чёрный объект
никогда не ссылается на белый напрямую».

Полные STW-паузы в современном Go остались всего в двух местах: в начале
цикла (включить write barrier, просканировать корни) и в конце (выключить
write barrier, финальная синхронизация) — обе занимают микросекунды, а не
зависят от размера кучи.

**Подвох.** «GC останавливает программу на время сборки» — устаревшее
представление о Go до версии 1.5. С конкурентным сборщиком STW-паузы не
масштабируются с размером кучи; основная работа (сканирование, разметка)
идёт параллельно с горутинами приложения, отнимая у них часть CPU-времени
через механизм assist (горутина, которая аллоцирует слишком агрессивно во
время цикла GC, сама помогает разметке).

## Что запускает цикл GC и как его настраивать?

**Коротко.** Три триггера: рост живой кучи в `GOGC` процентов от размера
после предыдущего цикла (по умолчанию 100 — то есть цикл при удвоении),
фоновый таймер (не реже раза в 2 минуты) и явный вызов `runtime.GC()`.

```go
package main

import (
	"fmt"
	"runtime/debug"
)

func main() {
	// GOGC=100 (по умолчанию): следующий цикл — когда живая куча удвоится
	debug.SetGCPercent(50) // цикл чаще: меньше памяти, больше нагрузка на CPU

	// GOMEMLIMIT (Go 1.19+): мягкий верхний лимит памяти процесса
	debug.SetMemoryLimit(512 << 20) // 512 МиБ
	fmt.Println("настроено")
	// вывод: настроено
}
```

`GOGC` — это компромисс «память ↔ CPU»: меньшее значение чаще запускает GC,
экономя память ценой CPU; большее (или `GOGC=off`) снижает частоту сборок
ценой роста потребления памяти. `GOMEMLIMIT` задаёт **мягкий** абсолютный
лимит — рантайм старается не превышать его, чаще запуская GC при
приближении к границе. В контейнерах это особенно важно: без лимита процесс
ориентируется на `GOGC` относительно живой кучи и может расти, пока не
упрётся в cgroup-лимит и не получит OOM-kill. Частая продовая настройка —
`GOMEMLIMIT`, выставленный чуть ниже лимита контейнера, вместе с `GOGC=off`
или большим `GOGC`, чтобы решение о запуске цикла принимал именно лимит
памяти, а не относительный рост кучи.

**Подвох.** `GOMEMLIMIT` — это **мягкий** лимит, а не жёсткая граница: при
резком всплеске аллокаций рантайм может кратковременно превысить его перед
тем, как успеет собрать мусор. Это не замена контроля памяти на уровне ОС
или cgroup, а инструмент подсказать GC, где граница.

**Глубже.** Финализаторы (`runtime.SetFinalizer`, а в новых версиях —
`runtime.AddCleanup`) вызываются GC-ом перед освобождением объекта, но не
гарантируют **когда** и вообще **что** будут вызваны (например, при
`os.Exit()` — не будут). Они не замена явному `Close()` для ресурсов вроде
файлов и соединений, а скорее подстраховка «на всякий случай».

## Какие типичные утечки памяти бывают в Go-программах?

**Коротко.** В Go нет утечек в смысле C (забытый `free`) — GC собирает всё
недостижимое. «Утечка» здесь означает удержание живых ссылок на объекты,
которые по смыслу программы уже не нужны.

Частые источники:

- **подслайс или подстрока удерживают весь backing array** — `s[:10]` от
  гигабайтного слайса не даст собрать остальные 999990 байт, пока жив срез;
- **незакрытые ресурсы** — `http.Response.Body`, `sql.Rows`, `time.Ticker`
  держат внутренние буферы и горутины живыми;
- **утёкшие горутины** — заблокированная навсегда горутина (например, пишет
  в канал, который никто не читает) удерживает свой стек и все захваченные
  объекты бесконечно — сама горутина недостижимой для GC не считается;
- **глобальные карты/кэши без вытеснения**, которые только растут;
- **неправильное использование `sync.Pool`** — не «утечка» технически (пул
  чистится GC между циклами), но хранение в нём крупных редко используемых
  объектов может продлевать их жизнь дольше, чем нужно.

```go
package main

func leakSubslice(huge []byte) []byte {
	return huge[:10] // держит живым весь массив huge, а не только 10 байт
}

func fixSubslice(huge []byte) []byte {
	small := make([]byte, 10)
	copy(small, huge[:10])
	return small // теперь huge освобождается целиком
}
```

**Подвох.** «Раз GC собирает всё недостижимое, утечки в Go невозможны» —
неверно: недостижимость определяется графом ссылок, а не намерением
программиста. Слайс на 10 байт от гигабайтного массива **достижим и жив**
ровно потому, что он ссылается на тот же backing array — с точки зрения GC
всё корректно, с точки зрения бизнес-логики это утечка.

## Как снижать давление на GC?

**Коротко.** Меньше аллокаций и меньше указателей — меньше работы для
сборщика: преаллокация с известной ёмкостью, переиспользование буферов,
избегание лишней укладки в интерфейс, значения вместо указателей для мелких
структур.

```go
package main

import "strings"

func buildBad(words []string) string {
	s := ""
	for _, w := range words {
		s += w + " " // на каждой итерации новая строка — O(n²) аллокаций
	}
	return s
}

func buildGood(words []string) string {
	var b strings.Builder
	b.Grow(64) // преаллокация буфера под примерный размер результата
	for _, w := range words {
		b.WriteString(w)
		b.WriteByte(' ')
	}
	return b.String()
}
```

`sync.Pool` — способ переиспользовать временные буферы между вызовами вместо
того, чтобы аллоцировать их заново каждый раз (типичный кейс — буфер под
сериализацию JSON в HTTP-хендлере). Важно: пул не гарантирует, что объект
останется в нём между вызовами GC — рантайм вправе очистить пул полностью
между циклами, так что `sync.Pool` — оптимизация для «горячего» переиспользования,
а не постоянное хранилище и не механизм ограничения числа живых объектов.

Измерять, а не гадать: `go test -bench=. -benchmem` показывает `allocs/op` и
`B/op` на бенчмарк, `pprof heap` (профиль `alloc_space` — сколько всего
аллоцировано с начала работы против `inuse_space` — сколько живёт сейчас) и
`GODEBUG=gctrace=1` — построчный вывод статистики каждого цикла GC в stderr.

**Подвох.** Оптимизация «заменить указатели на значения» помогает не всегда:
если структура крупная, копирование её по значению между функциями может
стоить дороже, чем экономия на GC. Решение принимается по профилю
(`pprof`/`benchstat`), а не по общему правилу.
