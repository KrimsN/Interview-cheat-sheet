## Как правильно использовать `sync.Mutex`?

**Коротко.** `sync.Mutex` не рекурсивный (повторный `Lock` в той же
горутине — гарантированный дедлок) и не привязан к горутине: разблокировать
может любая горутина, не обязательно та, что заблокировала. Нулевое значение
уже готово к работе, отдельной инициализации не нужно.

```go
type Counter struct {
	mu    sync.Mutex
	value int
}

func (c *Counter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.value++
}
```

Идиома — объявлять мьютекс прямо рядом с полем, которое он защищает, и
снимать блокировку через `defer` сразу после захвата, чтобы не забыть при
раннем `return` или панике.

**Подвох.** Копирование структуры с мьютексом ломает синхронизацию — после
копии это уже два независимых мьютекса, защищающих (как думает код) одно и
то же состояние. `go vet` ловит это правилом `copylocks`:

```go
type Bad struct {
	mu sync.Mutex
}

func (b Bad) Broken() { // получатель ПО ЗНАЧЕНИЮ — мьютекс копируется на каждом вызове!
	b.mu.Lock()
	defer b.mu.Unlock()
}
// go vet: Broken passes lock by value: sync.Mutex contains sync.noCopy
```

Отсюда правило: методы, работающие с мьютексом, всегда объявляются на
указателе.

## Когда `sync.RWMutex` выгоднее обычного `Mutex`?

**Коротко.** `RWMutex` допускает либо много одновременных читателей, либо
одного писателя. Выигрыш реален только при заметно долгих чтениях и высокой
конкуренции за чтение — на коротких критических секциях накладные расходы
на саму блокировку делают обычный `Mutex` быстрее.

```go
type Cache struct {
	mu   sync.RWMutex
	data map[string]string
}

func (c *Cache) Get(key string) (string, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.data[key]
	return v, ok
}

func (c *Cache) Set(key, value string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.data[key] = value
}
```

**Подвох.** Ожидающий `Lock()` (писатель) блокирует новые `RLock()` — это
намеренная защита от голодания писателя, но означает, что `RWMutex` не
всегда "чем больше читателей, тем быстрее": один медленный писатель в
очереди мгновенно ставит всех новых читателей на паузу.

## Как правильно использовать `sync.WaitGroup`, и что изменилось в Go 1.25?

**Коротко.** `Add` вызывается **до** запуска горутины, `Done` — внутри неё
(обычно через `defer`), `Wait` — снаружи, после того как все горутины
запущены. `Add` внутри самой горутины — гонка: `Wait` может успеть
завершиться раньше, чем горутина вызовет `Add`.

```go
// НЕПРАВИЛЬНО: Add вызывается внутри горутины — гонка с Wait в другой горутине
func brokenFanOut(tasks []int) {
	var wg sync.WaitGroup
	for _, t := range tasks {
		go func(t int) {
			wg.Add(1) // может не успеть выполниться до wg.Wait()
			defer wg.Done()
			process(t)
		}(t)
	}
	wg.Wait()
}

// ПРАВИЛЬНО: Add до запуска горутины
func fanOut(tasks []int) {
	var wg sync.WaitGroup
	for _, t := range tasks {
		wg.Add(1)
		go func(t int) {
			defer wg.Done()
			process(t)
		}(t)
	}
	wg.Wait()
}

func process(t int) { _ = t }
```

Go 1.25 добавил метод `wg.Go`, который снимает целый класс таких ошибок —
`Add` и `Done` вызываются рантаймом сами:

```go
// go 1.25+
func fanOutModern(tasks []int) {
	var wg sync.WaitGroup
	for _, t := range tasks {
		wg.Go(func() {
			process(t)
		})
	}
	wg.Wait()
}
```

**Подвох.** `WaitGroup` — не про порядок и не про результат, только про факт
завершения. Собрать сами результаты нужно отдельным механизмом (канал,
слайс с индексами под мьютексом) — про это подробнее в
[паттернах конкурентности](concurrency-patterns.md).

## Как работает `sync.Once`?

**Коротко.** `Do` гарантирует, что переданная функция выполнится ровно один
раз за всё время жизни `Once`, и что все конкурентные вызовы `Do`
дождутся её завершения, прежде чем продолжить, — классический паттерн
ленивой потокобезопасной инициализации.

```go
var (
	once     sync.Once
	instance *Config
)

func GetConfig() *Config {
	once.Do(func() {
		instance = loadConfig() // выполнится ровно один раз, даже при гонке вызовов GetConfig
	})
	return instance
}
```

**Глубже.** С Go 1.21 добавились `sync.OnceFunc`, `sync.OnceValue` и
`sync.OnceValues` — обёртки, которые сразу возвращают функцию с
кешированием результата, без ручного объявления поля `Once` рядом с
переменной.

## Чем `atomic`-операции лучше мьютекса для счётчиков, и почему атомарность — не то же самое, что корректность?

**Коротко.** Для одиночного счётчика `sync/atomic` (`atomic.Int64`,
`atomic.Pointer[T]`, `CompareAndSwap`) в разы дешевле мьютекса — нет
захвата, нет постановки горутины в очередь ожидания. Но атомарность
защищает только **одну** операцию: составленная из нескольких атомарных
шагов логика гонкой быть не перестаёт.

```go
func raceyCounter() int {
	var counter int
	var wg sync.WaitGroup
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			counter++ // read-modify-write не атомарна — гонка
		}()
	}
	wg.Wait()
	return counter // результат непредсказуем, часто меньше 1000
}

func atomicCounter() int64 {
	var counter atomic.Int64
	var wg sync.WaitGroup
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			counter.Add(1)
		}()
	}
	wg.Wait()
	return counter.Load() // всегда 1000
}
```

`go run -race` (или `go test -race`) на `raceyCounter` укажет ровно на эту
строку как на гонку данных. Race detector ловит только те гонки, что реально
случились в конкретном прогоне, замедляет выполнение в 5–10 раз и повышает
потребление памяти — но в CI его включение того стоит.

**Подвох.** Композиция из двух атомарных операций — снова гонка:

```go
// TOCTOU: между Load и Add другая горутина может успеть изменить counter
if counter.Load() == 0 {
	counter.Add(1)
}
```

Здесь нужен либо `CompareAndSwap`, либо обычный мьютекс вокруг всей проверки
целиком — атомарность отдельных шагов от этого не спасает.

## Что гарантирует модель памяти Go, и почему "флаг без синхронизации на практике работает" — не аргумент?

**Коротко.** Без синхронизации компилятор и процессор вправе переупорядочить
операции — модель памяти Go описывает, какие именно события гарантированно
видны другим горутинам в правильном порядке (**happens-before**): запуск
горутины, обмен по каналу (отправка happens-before завершения приёма,
закрытие happens-before приёма нулевого значения), `Unlock` перед следующим
`Lock`, `Once.Do`, атомарные операции.

```go
// НЕ делайте так: обращение к общим переменным без синхронизации
var ready bool
var data string

func writer() {
	data = "payload"
	ready = true // компилятор/CPU вправе переставить эти две строки местами
}

func reader() {
	for !ready { // гонка данных: неопределённое поведение, а не "просто медленно"
	}
	fmt.Println(data) // может напечатать пустую строку, даже если ready уже true
}
```

Языконезависимое объяснение гонок, deadlock, livelock и starvation, а также
понятия видимости памяти как явления, отдельного от гонки за порядок, — в
разделе [Конкурентность и параллелизм](../fundamentals/concurrency.md).

**Подвох.** "На моей машине работает" не аргумент: без happens-before
компилятор и процессор оптимизируют так, будто других горутин не существует.
Правильное решение — заменить `bool` на `atomic.Bool` или защитить обе
переменные одним мьютеком, а не полагаться на то, что оптимизатор "в этот раз
не тронул порядок".

**Глубже.** Рантайм умеет обнаружить только **полный** дедлок — когда
абсолютно все горутины программы одновременно заснули
(`fatal error: all goroutines are asleep - deadlock!`). Частичный дедлок,
где висят не все горутины, а часть, — рантайм не диагностирует вообще,
такое ловится только вручную через `pprof goroutine` или через таймауты в
собственном коде.
