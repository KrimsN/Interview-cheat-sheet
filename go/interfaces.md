## Как в Go тип реализует интерфейс?

**Коротко.** Неявно — structural typing. Ключевого слова `implements` нет:
тип удовлетворяет интерфейсу автоматически, если в его method set есть все
методы интерфейса. Отсюда идиома — интерфейс объявляют **на стороне
потребителя** (рядом с функцией, которой он нужен), а не рядом с реализацией:
пакет с реализацией может вообще не знать, что у него есть потребители,
которым для тестов нужен мок за интерфейсом.

```go
type Notifier interface {
    Notify(msg string) error
}

// EmailSender ничего не знает про Notifier — просто имеет нужный метод
type EmailSender struct{}

func (EmailSender) Notify(msg string) error {
    fmt.Println("email:", msg)
    return nil
}

func Alert(n Notifier, msg string) error {
    return n.Notify(msg)
}

func main() {
    Alert(EmailSender{}, "disk full") // EmailSender подошёл без единого упоминания Notifier
}
```

Это же объясняет один из «Go Proverbs»: «the bigger the interface, the weaker
the abstraction» — чем меньше методов в интерфейсе, тем больше типов ему
случайно или намеренно удовлетворяют, и тем он полезнее как абстракция.
Эталонные примеры маленьких интерфейсов стандартной библиотеки — `io.Reader`,
`io.Writer`, `error`, `fmt.Stringer` (один метод каждый), `sort.Interface`
(три метода). Их можно комбинировать встраиванием: `io.ReadWriter` — это
просто встраивание `Reader` и `Writer` в одну декларацию.

**Подвох.** Раз проверка неявная, лёгкий способ случайно нарушить контракт —
переименовать или изменить сигнатуру метода в реализации и не заметить, что
тип перестал удовлетворять интерфейсу, если нигде в коде явно не
присваивается переменной этого интерфейса. Идиома для перехвата такой
ошибки на этапе компиляции, а не в рантайме:

```go
var _ Notifier = (*EmailSender)(nil) // если EmailSender сломает контракт — ошибка компиляции здесь
```

## Как устроено интерфейсное значение изнутри?

**Коротко.** Интерфейсное значение — это пара `(тип, значение)`, а не сам
объект. Для интерфейса с методами (непустого) в рантайме Go это структура
`iface{ tab *itab, data unsafe.Pointer }`; для пустого интерфейса
(`interface{}` / `any`) — `eface{ _type *_type, data unsafe.Pointer }`. `itab`
кэширует и конкретный тип, и таблицу указателей на методы этого типа под
данный интерфейс — вызов метода через интерфейс идёт косвенно, по указателю
из `itab`, поэтому компилятор обычно не может его заинлайнить, а сама
упаковка значения в интерфейс нередко вызывает escape to heap (значение
«убегает» из стека, потому что интерфейс должен пережить текущий кадр).

```go
type Animal interface {
    Sound() string
}

type Dog struct{}

func (Dog) Sound() string { return "woof" }

func main() {
    var a Animal      // (nil-тип, nil-данные) — полностью пустая пара
    fmt.Println(a == nil) // true

    a = Dog{}          // теперь пара: (тип=Dog, данные=Dog{})
    fmt.Println(a == nil) // false — у пары уже есть тип
}
```

Из этого устройства следует главное правило сравнения интерфейсов: `i == nil`
истинно, только если **обе** половины пары нулевые — и тип, и значение.
Если заполнена хотя бы половина, сравнение с `nil` даст `false`, даже если
«на глаз» переменная выглядит пустой.

## Классическая ловушка: почему `err != nil`, хотя в него явно положили nil?

**Коротко.** Потому что в интерфейсную переменную положили не буквальный
`nil`, а типизированный `nil`-указатель на конкретный тип. Пара
`(тип=*MyErr, значение=nil)` не равна `(тип=nil, значение=nil)` — сравнение
`err != nil` смотрит на пару целиком, а типовая часть заполнена.

```go
type MyErr struct{ msg string }

func (e *MyErr) Error() string { return e.msg }

func mayFail(ok bool) *MyErr {
    if !ok {
        return &MyErr{msg: "failed"}
    }
    return nil // это nil конкретного типа *MyErr
}

func do(ok bool) error {
    var err *MyErr = mayFail(ok) // err имеет тип *MyErr, здесь err == nil как указатель
    return err                    // но кладём его в error — упаковываем пару (*MyErr, nil)
}

func main() {
    err := do(true) // mayFail вернул честный nil-указатель

    fmt.Println(err == nil)       // false! — типовая часть пары не пуста
    fmt.Println(err)              // <nil> — печатается как nil, что ещё больше сбивает с толку
    var me *MyErr
    fmt.Println(errors.As(err, &me), me == nil) // true true — под интерфейсом реально лежит nil
}
```

Официальный Go FAQ разбирает ровно этот пример под заголовком «Why is my nil
error value not equal to nil?» — настолько частый баг, что попал в
документацию языка.

**Подвох.** Правило для собеседования звучит так: **никогда не возвращайте
`error` из переменной конкретного указательного типа**, если эта переменная
может быть `nil`. Правильный вариант — возвращать `error` напрямую, без
промежуточной типизированной переменной:

```go
func do(ok bool) error {
    if !ok {
        return &MyErr{msg: "failed"}
    }
    return nil // литеральный nil -> упаковывается в (nil, nil), err == nil будет true
}
```

Здесь ключевое отличие: `return nil` из функции, объявленной как
`func(...) error`, кладёт в интерфейс полностью пустую пару, потому что
компилятор не оборачивает буквальный `nil` в тип — а вот присваивание
`*MyErr`-переменной, даже равной `nil`, интерфейсу `error` всегда заполняет
типовую часть пары.

**Глубже.** Та же ловушка бьёт и через встраивание интерфейса в структуру
(см. [структуры и встраивание](structs-embedding.md)): если структура
встраивает интерфейс и полю не присвоено значение, оно остаётся `nil` как
интерфейс (пара `(nil, nil)`) — вызов непереопределённого метода такой
структуры паникует на `nil`-интерфейсе (`invalid memory address or nil
pointer dereference`), а не на конкретном типе, потому что вызывать вообще
нечего — у `itab` нет ни типа, ни данных.

## Как проверить содержимое интерфейса — type assertion и type switch?

**Коротко.** Type assertion `v, ok := i.(T)` пытается достать из интерфейса
`i` конкретное значение типа `T`; без формы с `ok` при несовпадении будет
паника. Type switch — `switch v := i.(type) { case T1: ...; case T2: ... }` —
последовательно проверяет несколько вариантов и в каждой ветке `v` уже имеет
конкретный тип.

```go
func describe(i interface{}) string {
    switch v := i.(type) {
    case int:
        return fmt.Sprintf("int: %d", v)
    case string:
        return fmt.Sprintf("string: %q", v)
    case nil:
        return "nil interface"
    default:
        return fmt.Sprintf("other: %T", v)
    }
}

func main() {
    fmt.Println(describe(42))     // int: 42
    fmt.Println(describe("hi"))   // string: "hi"
    fmt.Println(describe(nil))    // nil interface
    fmt.Println(describe(3.14))   // other: float64
}
```

Ту же механику type assertion используют для проверки опциональных
расширений интерфейса в рантайме — типичный паттерн стандартной библиотеки:

```go
func writeSmart(w io.Writer, data []byte) {
    if rf, ok := w.(io.ReaderFrom); ok {
        _ = rf // w умеет ReadFrom — можно использовать более эффективный путь
    }
    w.Write(data)
}
```

Так `net/http` проверяет, реализует ли конкретный `http.ResponseWriter`
дополнительно `http.Flusher`, прежде чем звать `Flush()`.

**Подвох.** `interface{}` (или его алиас `any`, введённый в Go 1.18) — это
«значение любого типа», а не «динамическая типизация» в духе Python. Само по
себе оно ничего не умеет: чтобы сделать со значением что-то конкретное,
всегда нужен либо type switch/assertion, либо рефлексия (`reflect`), либо —
чаще правильный ответ на собеседовании — дженерики, если операция должна быть
типобезопасной и известна на этапе компиляции.

**Глубже.** Интерфейсы с параметрами типа (появились вместе с дженериками,
Go 1.18) могут содержать не только методы, но и множества типов:
`type Number interface { ~int | ~int64 | ~float64 }`. Такой интерфейс **не
годится** как обычный интерфейс для переменной (`var n Number = 5` не
скомпилируется) — он годится только как ограничение (constraint) для
параметра типа в дженерике. Подробнее — в следующем файле про дженерики.

Рефлексия (`reflect`) — три закона, о которых спрашивают на сеньорских
интервью: (1) от интерфейса можно получить `reflect.Value`; (2) от
`reflect.Value` можно вернуться к интерфейсу; (3) чтобы **изменить**
`reflect.Value`, значение внутри него должно быть адресуемым (получено через
указатель, а не просто прочитано). Рефлексия работает поверх той же пары
`(тип, значение)`, что и обычные интерфейсы, только даёт доступ к ней в
рантайме. Цена — заметно медленнее прямого вызова и полная потеря проверок
компилятора, поэтому в проде её держат в узких местах: сериализация (`json`,
`yaml`), ORM, DI-контейнеры — там, где типы заранее не известны.
