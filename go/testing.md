## Как устроен стандартный пакет `testing` без ассертов?

**Коротко.** Тест — обычная функция `func TestX(t *testing.T)` в файле
`*_test.go`. Вместо `assert.Equal` — методы `t.Error`/`t.Errorf`
(зафиксировать провал и продолжить) и `t.Fatal`/`t.Fatalf` (зафиксировать и
прервать текущий тест немедленно).

```go
package calc

import "testing"

func Add(a, b int) int { return a + b }

func TestAdd(t *testing.T) {
	got := Add(2, 3)
	want := 5
	if got != want {
		t.Errorf("Add(2, 3) = %d, want %d", got, want)
	}
}
// go test ./...
// ok  	calc	0.002s
```

`t.Fatal` нельзя вызывать из горутины, отличной от той, в которой выполняется
тест: он вызывает `runtime.Goexit()`, а не панику — если сделать это из
дочерней горутины, тест зависнет или завершится некорректно, а не упадёт
предсказуемо. `t.Helper()` помечает функцию-хелпер так, чтобы в сообщении об
ошибке номер строки указывал на вызывающий тест, а не на саму хелпер-функцию.

**Подвох.** «Раз в `testing` нет ассертов — надо тянуть `testify`» — не
обязательно: отсутствие ассертов — намеренное решение авторов языка (явное
условие `if` понятнее в сообщении об ошибке, чем обёртка над рефлексией), и
многие проекты сознательно остаются на голом `testing` + табличных тестах.

## Что такое table-driven tests и почему это идиома номер один?

**Коротко.** Один тест перебирает слайс структур-кейсов, для каждого
запускает подтест через `t.Run(tc.name, ...)`. Это даёт именованные,
независимо фильтруемые подтесты вместо копипаста одинаковой проверки.

```go
package calc

import "testing"

func TestAdd_Table(t *testing.T) {
	tests := []struct {
		name     string
		a, b     int
		want     int
	}{
		{"positive", 2, 3, 5},
		{"negative", -1, -1, -2},
		{"zero", 0, 0, 0},
	}

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got := Add(tc.a, tc.b)
			if got != tc.want {
				t.Errorf("Add(%d, %d) = %d, want %d", tc.a, tc.b, got, tc.want)
			}
		})
	}
}
// go test -run TestAdd_Table/negative -v
// === RUN   TestAdd_Table
// === RUN   TestAdd_Table/negative
// --- PASS: TestAdd_Table (0.00s)
//     --- PASS: TestAdd_Table/negative (0.00s)
```

Имена подтестов позволяют запускать один конкретный кейс через `-run
Name/subname`, а вывод `-v` показывает дерево прогона по именам — что резко
упрощает отладку упавшего кейса среди сотни.

**Подвох.** «`-run` фильтрует по regexp» — да, и это регулярно ловит людей на
именах кейсов со спецсимволами regexp (`.`, `(`, `)` в `tc.name`) — они либо
экранируются, либо просто не используются в именах.

## Как работают параллельные тесты и какие у них ловушки?

**Коротко.** `t.Parallel()` внутри теста сигнализирует, что он может
выполняться параллельно с другими такими же тестами — сам тест
приостанавливается до тех пор, пока не завершатся все **непараллельные**
тесты в том же пакете, а затем параллельные запускаются вместе.

```go
func TestParallelExample(t *testing.T) {
	tests := []struct{ name string; n int }{
		{"a", 1}, {"b", 2}, {"c", 3},
	}

	for _, tc := range tests {
		tc := tc // до Go 1.22: обязательно копировать переменную цикла
		t.Run(tc.name, func(t *testing.T) {
			t.Parallel()
			// tc.n — своя копия на каждой итерации
			_ = tc.n
		})
	}
}
```

`go 1.22+` убрал необходимость в `tc := tc`: с этой версии переменная цикла
`for _, tc := range tests` — новый экземпляр на каждой итерации, а не одна
переменная, переиспользуемая между итерациями (частый источник багов до
1.22, когда все параллельные подтесты видели одно и то же последнее
значение).

**Подвох.** Параллельные подтесты фактически стартуют не в момент вызова
`t.Parallel()`, а после того, как **функция родительского теста дойдёт до
конца** (т.е. после выхода из цикла `for`, породившего `t.Run`). Отсюда
классическая ловушка: `defer cleanup()` в родительском тесте выполнится
**до того**, как параллельные подтесты успеют отработать — потому что
`defer` срабатывает при возврате из родительской функции, которая с точки
зрения планировщика уже «закончилась», хотя её подтесты формально ещё в
процессе. Решение — не `defer` в родителе, а `t.Cleanup()` в самом подтесте,
который знает свою настоящую точку завершения.

## Чем `t.Cleanup`, `t.TempDir`, `t.Setenv` лучше ручного `defer`?

**Коротко.** Это стандартные средства изоляции теста: регистрация отложенной
очистки, которая выполняется в правильном порядке даже с параллельными
подтестами, временный каталог с автоудалением и переменная окружения,
которая автоматически восстанавливается после теста.

```go
func TestWithResources(t *testing.T) {
	dir := t.TempDir() // удаляется автоматически по завершении теста
	t.Setenv("APP_ENV", "test") // возвращается к исходному значению после теста

	conn := openConn()
	t.Cleanup(func() {
		conn.Close() // выполнится и при t.Fatal, и при панике в самом тесте
	})

	_ = dir
	_ = conn
}
```

`t.Cleanup` в отличие от `defer` можно вызывать многократно из разных мест
(в том числе из вспомогательных функций-сеттеров), и вызовы выполняются в
порядке LIFO уже **после** самого тела теста, что и решает проблему с
параллельными подтестами из предыдущего вопроса.

**Подвох.** `t.Setenv` (и `t.TempDir` с точки зрения параллелизма файловой
системы) паникует, если вызван внутри теста, помеченного `t.Parallel()`, —
потому что изменение переменной окружения процесса не может быть
изолировано между параллельно исполняющимися тестами.

## Зачем нужен `TestMain`?

**Коротко.** `func TestMain(m *testing.M)` — точка входа для всего пакета
тестов вместо стандартного раннера: позволяет выполнить общую подготовку
(поднять контейнер, накатить миграции) один раз до всех тестов и явную
очистку после.

```go
package repo

import (
	"os"
	"testing"
)

var testDB *sql.DB

func TestMain(m *testing.M) {
	testDB = mustStartTestDB() // поднять контейнер один раз на весь пакет
	code := m.Run()             // запустить все Test*-функции пакета
	testDB.Close()
	os.Exit(code)
}
```

**Подвох.** Забыть `os.Exit(code)` и просто вызвать `m.Run()` без
возвращения его результата — тесты формально выполнятся, но код возврата
процесса всегда будет `0`, и упавшие тесты не завалят CI, если он полагается
на exit code, а не только на текстовый вывод `go test`.

## В чём разница между внутренним и внешним тестовым пакетом?

**Коротко.** `package foo` в файле `foo_test.go` — внутренний тестовый пакет:
видит неэкспортируемые идентификаторы. `package foo_test` — внешний: видит
только публичный API `foo`, как обычный потребитель пакета.

```go
// файл foo.go
package foo

func add(a, b int) int { return a + b } // неэкспортируемая

// файл foo_internal_test.go — package foo
package foo

import "testing"

func TestAddInternal(t *testing.T) {
	if add(2, 3) != 5 { // доступ к неэкспортируемой функции
		t.Fatal("bad")
	}
}

// файл foo_external_test.go — package foo_test
package foo_test

import (
	"testing"

	"example.com/mod/foo"
)

func TestAddExternal(t *testing.T) {
	if foo.Add(2, 3) != 5 { // только то, что foo экспортирует
		t.Fatal("bad")
	}
}
```

Внешний тестовый пакет заодно проверяет удобство самого публичного API (тест
пишется так же, как его будет использовать реальный потребитель) и разрывает
циклы импортов: тест может импортировать другой пакет, который сам зависит
от тестируемого, — что было бы циклом, если бы тест жил в `package foo`.

**Подвох.** Оба файла (`package foo` и `package foo_test`) могут сосуществовать
в одном каталоге одновременно — это единственное официально разрешённое
исключение из правила «один каталог — один пакет».

## Как принято делать тестовые дублёры (моки/фейки) в Go?

**Коротко.** Идиоматичный путь — небольшой интерфейс, объявленный на стороне
**потребителя**, и ручной фейк, реализующий его для теста; DI-фреймворк для
этого не нужен. Генераторы моков (`mockery`, `gomock`) используют, когда
интерфейсов и их методов действительно много.

```go
package billing

// Интерфейс объявлен там, где используется, а не там, где реализован —
// ключевая идиома Go (в отличие от Java, где интерфейс обычно у поставщика).
type NotificationSender interface {
	Send(to, msg string) error
}

type Service struct {
	sender NotificationSender
}

func (s *Service) Charge(to string) error {
	// ...
	return s.sender.Send(to, "charged")
}
```

```go
package billing_test

type fakeSender struct {
	sent []string
	err  error
}

func (f *fakeSender) Send(to, msg string) error {
	f.sent = append(f.sent, to)
	return f.err
}

func TestCharge(t *testing.T) {
	sender := &fakeSender{}
	svc := &billing.Service{}
	// ... подставить sender через конструктор или экспортируемое поле
	_ = sender
}
```

**Подвох.** «Интерфейс должен быть у реализации» — Go-идиома ровно
противоположная: маленький интерфейс объявляется рядом с кодом, который его
**использует**, а конкретная реализация о нём может даже не знать (не
импортирует пакет с интерфейсом). Это и делает мокирование лёгким без
DI-контейнера — потребителю достаточно любой структуры с нужным методом.

## Как писать и корректно измерять бенчмарки?

**Коротко.** `func BenchmarkX(b *testing.B)` с циклом, который выполняется
`b.N` раз (в новых версиях — циклом `for b.Loop()`), запускается флагом
`-bench` и обычно вместе с `-benchmem` для учёта аллокаций.

```go
package calc

import "testing"

func BenchmarkAdd(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		Add(2, 3)
	}
}

// go 1.24+ — упрощённая форма, сама управляет таймером и счётчиком
func BenchmarkAddLoop(b *testing.B) {
	for b.Loop() {
		Add(2, 3)
	}
}
// go test -bench=. -benchmem
// BenchmarkAdd-8    1000000000    0.25 ns/op    0 B/op    0 allocs/op
```

`b.ResetTimer()` нужен, если перед циклом есть дорогая подготовка (загрузка
фикстур), которую не хочется засчитывать в измерение. Сравнивать результаты
двух прогонов «на глаз» ненадёжно из-за шума — для этого есть `benchstat`,
который прогоняет `-count=10` и даёт статистически значимую разницу.

**Подвох.** Компилятор может **выкинуть** бенчмаркируемый вызов целиком, если
увидит, что результат нигде не используется (dead code elimination) — тогда
бенчмарк покажет нереалистично маленькое время. Стандартное лечение —
присваивать результат в package-level переменную:

```go
var sink int

func BenchmarkAddSafe(b *testing.B) {
	var r int
	for i := 0; i < b.N; i++ {
		r = Add(2, 3)
	}
	sink = r // не даёт компилятору выбросить вызов как мёртвый код
}
```

## Что такое fuzzing в Go и как его запускать?

**Коротко.** Встроенный (с Go 1.18) fuzzing генерирует случайные входные
данные на основе «сидов», ищет входы, которые вызывают панику или падение
инварианта, и сохраняет упавшие случаи в `testdata/` как регрессионные тесты.

```go
package calc

import "testing"

func FuzzAdd(f *testing.F) {
	f.Add(2, 3) // сид — стартовый пример для мутаций
	f.Add(-1, 1)

	f.Fuzz(func(t *testing.T, a, b int) {
		got := Add(a, b)
		if got != a+b {
			t.Errorf("Add(%d, %d) = %d, want %d", a, b, got, a+b)
		}
	})
}
// go test -fuzz=FuzzAdd -fuzztime=30s
```

Найденные падающие входы автоматически сохраняются в `testdata/fuzz/FuzzAdd/`
и при обычном `go test` (без `-fuzz`) выполняются как обычные регрессионные
кейсы — так упавший однажды случай больше не пропадает.

**Подвох.** `f.Fuzz` принимает только ограниченный набор типов аргументов
(строки, числа, `[]byte`, `bool` и их комбинации) — нельзя зафаззить
произвольную структуру напрямую, для сложных входов пишут генератор из
`[]byte` внутри самой функции.

## Как измерять покрытие тестами и что оно на самом деле показывает?

**Коротко.** `go test -cover` даёт процент, `-coverprofile=cover.out` +
`go tool cover -html=cover.out` — построчную HTML-визуализацию, какие
строки выполнялись хотя бы раз. С Go 1.20 можно также собирать покрытие с
интеграционных прогонов **собранного бинарника**, а не только `go test`.

```bash
go test -coverprofile=cover.out ./...
go tool cover -html=cover.out -o cover.html

# покрытие интеграционных сценариев (запуск собранного бинарника, не go test)
go build -cover -o app ./cmd/server
GOCOVERDIR=./covdata ./app
go tool covdata textfmt -i=./covdata -o=cover.out
```

**Подвох.** Процент покрытия — метрика-индикатор, а не цель: строка
«выполнилась» не значит «проверена» — тест может пройти через код, ничего не
утверждая про результат (нет ни одного `t.Error`/сравнения). 100% покрытия
достижимо без единой содержательной проверки.

## Какие флаги `go test` важно знать?

**Коротко.** `-race` включает детектор гонок (обязателен в CI для любого
конкурентного кода), `-count=1` обходит кэш результатов тестов, `-timeout`
задаёт предел на весь пакет, `-short` вместе с `testing.Short()` в коде
теста позволяет пропускать медленные тесты в обычном прогоне.

```bash
go test -race -count=1 -timeout=30s ./...

go test -short ./...   # быстрый прогон в CI на каждый коммит
```

```go
func TestSlowIntegration(t *testing.T) {
	if testing.Short() {
		t.Skip("skipping integration test in short mode")
	}
	// ...
}
```

Для HTTP-кода без реальных сетевых портов используют `net/http/httptest`:
`httptest.NewServer` поднимает настоящий (но локальный, эфемерный) сервер, а
`httptest.NewRecorder` подменяет `http.ResponseWriter` для юнит-тестов
хендлеров без сети вообще. Для внешних зависимостей вроде БД —
`testcontainers-go`, поднимающий реальный Docker-контейнер на время теста.

**Подвох.** `go test` **кеширует** результат пакета, если ни код, ни флаги
запуска не изменились с прошлого успешного прогона, — и повторный запуск
покажет `(cached)` вместо реального выполнения. Если тест недетерминирован
(зависит от времени, сети, случайности), это может маскировать флейки;
`-count=1` принудительно отключает кеш.
