## Какие идиомы считаются «правильным» стилем в Go?

**Коротко.** Go сознательно сузил пространство выбора: форматирование задаёт
`gofmt` и не обсуждается, а стиль кода описывается набором коротких
принципов-поговорок, которые в сумме сводятся к «явное и скучное лучше
неявного и умного».

`gofmt` (и `goimports` поверх него) — не рекомендация, а стандарт: отступы
табами, единая расстановка скобок, автоматическая группировка импортов
(стандартная библиотека отдельно от внешних пакетов). Комментарий к
экспортируемой сущности начинается с её имени — это не только стиль, но и
формат, который разбирает `go doc`:

```go
// Server handles incoming HTTP requests and dispatches them to the
// appropriate use case.
type Server struct {
    // ...
}
```

Из содержательных идиом, которые реально проверяют на понимание:

- **«Принимай интерфейсы, возвращай структуры»** — функция принимает
  минимально нужный интерфейс (проще подставить мок, проще менять
  реализацию), а возвращает конкретный тип (вызывающему нужны все методы и
  поля, а не урезанный контракт).
- **«Интерфейс объявляет потребитель»** — интерфейс живёт в пакете, который
  его использует, а не в пакете, который его реализует (в отличие от Java,
  где интерфейс обычно объявляет поставщик реализации).
- **«The zero value should be useful»** — тип должен быть рабочим сразу
  после `var x T`, без обязательного вызова конструктора. Пример —
  `sync.Mutex`: нулевое значение уже разблокированный мьютекс, готовый к
  использованию.
- **Ранний возврат вместо вложенности** — «happy path» идёт по левому краю
  функции без вложенных `if/else`, ошибки отсекаются в начале:

```go
func process(data []byte) (Result, error) {
    if len(data) == 0 {
        return Result{}, errors.New("empty data")
    }
    parsed, err := parse(data)
    if err != nil {
        return Result{}, fmt.Errorf("parse: %w", err)
    }
    // основная логика — без вложенности
    return build(parsed), nil
}
```

- **«Don't panic»** — паника не средство контроля потока и не замена
  `error`; она сигнализирует о программной ошибке (выход за границы слайса,
  разыменование `nil`), а не о штатной проблемной ситуации вроде «файл не
  найден».
- **«A little copying is better than a little dependency»** — небольшой
  дублирующийся кусок кода часто дешевле, чем связывание модулей общей
  зависимостью ради экономии десяти строк.
- **«Clear is better than clever»** — предпочтение читаемого кода
  компактному трюку: явный цикл лучше плотной цепочки однострочников, если
  вторые требуют напряжения, чтобы понять, что происходит.

**Подвох.** «`gofmt` — это дело вкуса, можно настроить по-другому?» Нет —
именно отсутствие вариативности форматирования в Go является идиомой: весь
код на Go, от стандартной библиотеки до стороннего пакета, форматируется
одинаково, и код-ревью никогда не тратится на споры о стиле скобок.

## Как называть переменные, функции и пакеты в Go?

**Коротко.** Правило масштаба: чем уже область видимости переменной, тем
короче может быть её имя. Экспортируемые (публичные) имена начинаются с
заглавной буквы и обычно длиннее и говорящее, чем внутрипакетные.

```go
// короткие имена уместны в узкой, локальной области видимости
for i, r := range runes {
    if r == '\n' {
        break
    }
}

// в широкой области (поле структуры, экспортируемая функция) — имя длиннее
type ConnectionPool struct {
    maxOpenConnections int
}
```

Регистр слова целиком — `MixedCaps`/`mixedCaps`, никогда не `snake_case`
(`snake_case` в Go читается как нарушение соглашений, а не как альтернативный
стиль). Аббревиатуры пишутся в одном регистре целиком, а не по правилам
CamelCase для отдельных букв: `userID`, не `userId`; `HTTPServer`, не
`HttpServer`; `URL`, не `Url`.

Интерфейсы с одним методом принято называть по имени метода с суффиксом
`-er`: `Reader` (`Read`), `Writer` (`Write`), `Stringer` (`String`),
`Closer` (`Close`). Это не жёсткое правило, а конвенция, которая делает
маленькие интерфейсы узнаваемыми по имени без чтения тела.

**Подвох.** «Раз `err` и `ok` — это просто соглашение, можно называть их
как угодно?» Формально да, но повсеместность этих имён — тоже часть
идиомы: код, где вместо `if err != nil` использовано `if e != nil`, читается
дольше, потому что глаз читателя настроен на конкретные, привычные всей
экосистеме имена служебных переменных.

## Как правильно организовать структуру Go-проекта?

**Коротко.** Пакеты группируют по предметной области (`billing`, `user`,
`inventory`), а не по техническому слою (`models`, `services`, `utils`,
`helpers`) — последнее считается антипаттерном, потому что заставляет менять
несколько несвязанных пакетов при любом изменении одной бизнес-фичи.

Типичная раскладка модуля:

```
cmd/
  api/
    main.go        // composition root: собирает зависимости, запускает сервер
internal/
  billing/
    service.go
    repository.go
  user/
    service.go
    repository.go
pkg/                // опционально: код, безопасный для импорта извне модуля
go.mod
```

`internal/` — не просто соглашение, а механизм, который поддерживает
компилятор: пакеты внутри `internal/` может импортировать только код из
дерева, корень которого — родитель `internal/`. Это единственный способ в Go
сделать пакет «публичным внутри модуля, но не наружу» без городить
интерфейсы-обёртки.

Пакет `util`/`common`/`helpers` без конкретной предметной области — тревожный
сигнал на ревью: со временем он превращается в «пакет-бог», куда сваливают
всё подряд, и который в итоге зависит от половины проекта и от которого
зависит другая половина.

**Подвох.** «Слоистая структура (`models`/`services`/`repositories`) — это же
стандартный подход из других языков, почему в Go это плохо?» Проблема не в
слоях как таковых (слоистая или гексагональная архитектура в Go тоже
применяются), а в том, что деление **пакетов** по слоям вместо предметной
области ломает главное преимущество пакетов Go — инкапсуляцию: приватные
типы `billing` не могут быть приватными, если сущность биллинга размазана
между пакетами `models`, `services` и `repositories`.

## Как в Go реализуют внедрение зависимостей и слоистую архитектуру без DI-фреймворка?

**Коротко.** Идиоматичный Go обычно обходится без контейнера внедрения
зависимостей: `main` выступает «корнем компоновки» (composition root) —
единственным местом, где создаются конкретные реализации и вручную
передаются друг другу через конструкторы, принимающие интерфейсы.

```go
func main() {
    db := mustOpenDB(cfg.DSN)
    repo := postgres.NewUserRepository(db)
    svc := user.NewService(repo)
    handler := httpapi.NewUserHandler(svc)

    mux := http.NewServeMux()
    mux.Handle("/users/", handler)
    // ...
}
```

`user.NewService` принимает не `*postgres.UserRepository`, а маленький
интерфейс `user.Repository`, объявленный в пакете `user` (см. «интерфейс
объявляет потребитель» выше) — это и есть внедрение зависимости: `postgres`
реализует контракт, `user` о `postgres` ничего не знает.

Гексагональная архитектура (ports & adapters) и чистая архитектура в Go
реализуются буквально теми же средствами: «порт» — это интерфейс в доменном
пакете, «адаптер» — реализация в отдельном пакете инфраструктуры. Подробнее
про сами архитектурные стили и общие принципы DI — в языконезависимых темах
[архитектура](../fundamentals/architecture.md) и
[внедрение зависимостей](../fundamentals/dependency-injection.md); здесь же
важно, что в Go это не требует ни рефлексии, ни специального фреймворка.

DI-контейнеры вроде `google/wire` (генерация кода компоновки на этапе сборки)
или `uber-go/fx` (рантайм-контейнер с жизненным циклом) применяют, когда граф
зависимостей вырастает настолько, что ручная сборка в `main` становится
громоздкой — но это оптимизация, а не обязательный стартовый выбор.

**Подвох.** «Раз в Go нет DI-фреймворка по умолчанию — значит, внедрения
зависимостей там нет?» Нет — DI как принцип (зависимость передаётся, а не
создаётся внутри) в Go используется повсеместно, просто механизм — не
контейнер с рефлексией, а обычные аргументы конструктора и маленькие
интерфейсы.

## Какие Go-специфичные code smells стоит уметь называть на ревью?

**Коротко.** Кроме общих антипаттернов, у Go есть свой набор «запахов»,
специфичных для его модели типов и конкурентности.

- **Голый `interface{}`/`any` в сигнатуре** там, где можно было объявить
  конкретный тип или дженерик — сигнал, что типобезопасность принесена в
  жертву без необходимости.
- **«Геттеры-сеттеры на всё»** — в Go нет культуры `GetX()/SetX()` для
  каждого поля; если поле должно быть доступно снаружи, его обычно просто
  экспортируют (`X`), а метод пишут только когда за доступом стоит реальная
  логика.
- **Гигантские интерфейсы** — интерфейс на 10+ методов сложно реализовать
  для тестового мока и сложно переиспользовать; идиоматичный Go тяготеет к
  интерфейсам из одного-двух методов, скомпонованных при необходимости.
- **Пакеты-«боги»** (`utils`, `common`, `shared`) — см. вопрос про структуру
  проекта выше.
- **Глобальное изменяемое состояние** — пакетные переменные, которые
  меняются во время работы программы, особенно опасны в Go из-за горутин:
  без синхронизации это гарантированная гонка данных.
- **`init()` с побочными эффектами** — `init()` вызывается неявно при
  импорте пакета, до `main()`, и в порядке, который не всегда очевиден при
  нескольких файлах/пакетах; регистрация (как в `database/sql` драйверах)
  — приемлемое использование, а вот поход в сеть или чтение файлов конфигурации
  внутри `init()` затрудняет тестирование и делает поведение программы
  зависимым от побочного эффекта импорта.
- **Каналы там, где нужен мьютекс** — канал ради простой защиты одного
  разделяемого счётчика обычно избыточен и медленнее, чем `sync.Mutex`;
  каналы оправданы, когда речь о передаче владения данными или сигнализации
  между горутинами, а не о защите общего состояния.
- **Преждевременные горутины** — `go func()` без чёткого понимания, кто и
  когда её дождётся (через `sync.WaitGroup`, канал или `errgroup`), почти
  всегда означает либо утечку горутины, либо потерянную ошибку.

**Подвох.** «Раз в языке нет линтера из коробки, который бы всё это ловил —
значит, это не строгие правила, а вкусовщина?» Часть этого действительно
ловится статически (`go vet`, `golangci-lint` с правилами вроде
`unused`, `errcheck`, `bodyclose`), но часть — вопрос архитектурного
суждения, которое и проверяют на код-ревью и на собеседовании отдельно от
инструментов.

## Как Go поддерживает обратную совместимость API при развитии кода?

**Коротко.** Go 1 даёт формальное обещание совместимости: код, написанный
под Go 1.x, должен продолжать компилироваться и работать под более поздними
версиями Go 1 без изменений. Это касается языка и стандартной библиотеки; для
собственных публичных API разработчики следуют похожим неписаным правилам,
чтобы не ломать зависящий код при минорных релизах.

Практические приёмы, которые позволяют расширять API, не ломая его:

- **Добавлять методы к структурам можно свободно** — это не влияет на
  существующий код, который создаёт такие структуры или вызывает их старые
  методы.
- **Добавлять методы к интерфейсам — нельзя без слома совместимости**: любой
  тип, реализующий этот интерфейс во внешнем коде, перестанет ему
  удовлетворять, пока не добавит новый метод. Отсюда — практика оставлять
  публичные интерфейсы маленькими и стабильными, а расширяемость закладывать
  через отдельные более широкие интерфейсы (как `io.Reader` и `io.ReaderAt`
  сосуществуют, вместо того чтобы `Reader` разросся).
- **Функциональные опции** вместо роста списка параметров конструктора —
  добавление новой опции не требует менять существующие вызовы:

```go
type Server struct {
    timeout time.Duration
    logger  *slog.Logger
}

type Option func(*Server)

func WithTimeout(d time.Duration) Option {
    return func(s *Server) { s.timeout = d }
}

func WithLogger(l *slog.Logger) Option {
    return func(s *Server) { s.logger = l }
}

func NewServer(opts ...Option) *Server {
    s := &Server{timeout: 30 * time.Second, logger: slog.Default()}
    for _, opt := range opts {
        opt(s)
    }
    return s
}

// вызывающий код не ломается, когда через полгода добавится WithRetries(...)
srv := NewServer(WithTimeout(10 * time.Second))
```

**Подвох.** «Добавить новое поле в публичную структуру — всегда безопасно?»
Почти всегда — кроме случая, когда где-то во внешнем коде эту структуру
сравнивают через `==` или используют как ключ карты: новое поле меняет
семантику сравнения, а если тип поля несравнимый (слайс, карта, функция),
структура вообще перестаёт быть сравнимой, и внешний код перестаёт
компилироваться.
