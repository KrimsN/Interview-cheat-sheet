## Как в Go устроены ошибки и почему их не бросают, как исключения?

**Коротко.** `error` — это обычный интерфейс с единственным методом
`Error() string`. Ошибки в Go — это значения: их создают, возвращают как
последний результат функции и проверяют сразу после вызова, а не
перехватывают через try/catch где-то выше по стеку.

```go
type error interface {
    Error() string
}

func divide(a, b int) (int, error) {
    if b == 0 {
        return 0, errors.New("division by zero")
    }
    return a / b, nil
}

func main() {
    result, err := divide(10, 0)
    if err != nil {
        fmt.Println("error:", err) // error: division by zero
        return
    }
    fmt.Println(result)
}
```

Идиома — `if err != nil { return ..., err }` на каждом уровне, где ошибка
может возникнуть. Это выглядит многословно по сравнению с исключениями, но
даёт предсказуемость: путь ошибки виден прямо в сигнатуре функции и в коде,
а не прячется в невидимом альтернативном потоке управления.

**Подвох.** Игнорировать ошибку через `_` без явного комментария, почему это
безопасно, — плохая практика, которую ловят линтеры (`errcheck`). Игнорирование
`err` молча — один из самых частых источников продовых багов на code review в
Go-командах.

## Как сравнивать и классифицировать ошибки — sentinel-ошибки и свои типы?

**Коротко.** Простейший способ — sentinel-ошибка: пакетная переменная вида
`var ErrNotFound = errors.New("not found")`, которую сравнивают через
`errors.Is`. Более информативный способ — свой тип ошибки (структура с полями
+ метод `Error()`), который извлекают через `errors.As`.

```go
var ErrNotFound = errors.New("not found")

func find(id int) error {
    if id != 1 {
        return ErrNotFound
    }
    return nil
}

func main() {
    err := find(2)
    if errors.Is(err, ErrNotFound) {
        fmt.Println("не нашли запись") // выполнится
    }
}
```

```go
type ValidationError struct {
    Field string
    Msg   string
}

func (e *ValidationError) Error() string {
    return fmt.Sprintf("validation failed on %s: %s", e.Field, e.Msg)
}

func validate(age int) error {
    if age < 0 {
        return &ValidationError{Field: "age", Msg: "must be non-negative"}
    }
    return nil
}

func main() {
    err := validate(-1)

    var ve *ValidationError
    if errors.As(err, &ve) {
        fmt.Println("плохое поле:", ve.Field) // плохое поле: age
    }
}
```

Sentinel-ошибки становятся частью публичного API пакета в момент, когда их
экспортируют (`io.EOF`, `sql.ErrNoRows`) — вызывающий код начинает полагаться
на конкретное значение, и убрать или переименовать его потом — ломающее
изменение. Вводить их стоит осознанно, а не для каждой мелкой ошибки внутри
пакета.

**Подвох.** Если функция возвращает не сам интерфейс `error`, а сохраняет
промежуточный результат в переменной конкретного указательного типа
(`var ve *ValidationError = validate(age)`), а потом кладёт эту переменную в
`error` — можно напороться на классическую ловушку «`nil` внутри интерфейса»:
`err != nil` окажется истинным, даже если функция логически «ошибки не
вернула». Это устройство интерфейсов разобрано подробно в
[интерфейсах](interfaces.md) — там же лежит и правило, как её избежать
(возвращать `error` напрямую, не через промежуточную типизированную
переменную).

## Как оборачивать ошибки и разворачивать цепочку — `%w`, `Unwrap`, `Is`, `As`, `Join`?

**Коротко.** С Go 1.13 у `fmt.Errorf` появился глагол `%w`, который
оборачивает исходную ошибку, сохраняя её в цепочке: `fmt.Errorf("get user
%d: %w", id, err)`. Разворачивают цепочку через `errors.Unwrap` (один шаг),
`errors.Is` (сравнение по значению на любую глубину цепочки) и `errors.As`
(поиск по типу на любую глубину).

```go
var ErrNotFound = errors.New("not found")

func fetchUser(id int) error {
    return ErrNotFound // "сырая" ошибка нижнего уровня
}

func getUser(id int) error {
    if err := fetchUser(id); err != nil {
        return fmt.Errorf("get user %d: %w", id, err) // оборачиваем с контекстом
    }
    return nil
}

func main() {
    err := getUser(42)

    fmt.Println(err)                       // get user 42: not found
    fmt.Println(errors.Is(err, ErrNotFound)) // true — нашёл ErrNotFound внутри цепочки
    fmt.Println(errors.Unwrap(err))          // not found — на один уровень вглубь
}
```

С Go 1.20 `errors.Join` объединяет несколько независимых ошибок в одну (для
случаев, когда операций несколько и все они могли не сработать), а `%w` в
`fmt.Errorf` можно указывать несколько раз для той же цели:

```go
// go 1.20+
func closeAll(closers ...io.Closer) error {
    var errs []error
    for _, c := range closers {
        if err := c.Close(); err != nil {
            errs = append(errs, err)
        }
    }
    return errors.Join(errs...) // errors.Join(nil-слайса) вернёт nil
}
```

**Правило про текст ошибки** при оборачивании: добавляйте контекст, которого
ещё нет у вызывающего (`"get user %d: %w"`, а не просто `"error: %w"`), и не
начинайте сообщение с заглавной буквы и не заканчивайте точкой — линтер
`go vet` (правило `ST1005` из staticcheck) это проверяет, потому что
сообщения об ошибках обычно склеиваются в цепочку через `: ` и заглавная
буква/точка посреди строки выглядят некрасиво. Также не стоит одновременно
логировать ошибку и возвращать её выше по стеку — так одна и та же проблема
попадает в лог несколько раз; выбирают что-то одно: либо залогировать и
проглотить на этом уровне, либо вернуть выше без логирования.

**Подвох.** Стандартная библиотека **не хранит стектрейс** вместе с ошибкой —
`errors.New` и `fmt.Errorf` дают только текст и (если использован `%w`) цепочку
причин, но не место, откуда ошибка возникла. Исторически это закрывал пакет
`pkg/errors` (до 1.13 добавлял стектрейсы), сейчас для этого чаще используют
`github.com/cockroachdb/errors` или структурное логирование (`log/slog`,
доступен с Go 1.21) с явным полем, откуда пришла ошибка.

## Когда использовать `panic`/`recover`, а не `error`?

**Коротко.** `panic` — для программных ошибок и невозможных состояний
(обращение по `nil`-указателю, выход за границы слайса, нарушенный инвариант),
а не для ожидаемых сбоев вроде «файл не найден» или «сервер не ответил» —
это всегда `error`. `recover` работает только внутри вызванной через `defer`
функции и обычно уместен на границе системы (HTTP middleware, обработчик
задачи в воркер-пуле), чтобы одна паника не уронила весь процесс.

```go
func safeHandler(next func()) {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("recovered from panic:", r)
        }
    }()
    next()
}

func main() {
    safeHandler(func() {
        var s []int
        _ = s[5] // panic: index out of range
    })
    fmt.Println("процесс жив") // выполнится — паника не убила программу
}
```

**Подвох.** `recover` **не спасает** от фатальных ошибок рантайма — это
принципиально другая категория, чем паника: `fatal error: concurrent map
writes`, дедлок всех горутин (`fatal error: all goroutines are asleep -
deadlock!`), переполнение стека, нехватка памяти (OOM). Такие ошибки
завершают процесс безусловно, независимо от того, есть где-то `recover` или
нет, — и это популярный уточняющий вопрос, отличающий кандидата, который
реально сталкивался с продакшеном.

Второй частый вопрос — паника в горутине. Если внутри самой горутины нет
своего `recover`, паника убивает **весь процесс**, а не только эту горутину:

```go
func main() {
    go func() {
        panic("boom") // recover в main() эту панику не поймает
    }()
    time.Sleep(time.Second)
    fmt.Println("до этой строки выполнение не дойдёт")
}
```

Значит, у каждой горутины, где в принципе возможна паника (в частности, любой
обработчик, вызывающий чужой код), должен быть свой `defer`/`recover` —
перехватить чужую панику из другой горутины снаружи невозможно.
