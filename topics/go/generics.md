# Go: дженерики (type parameters)

[🏠 Карта тем по Go](README.md)

## Что нужно знать

- **Появились в Go 1.18.** Синтаксис: `func Map[T, U any](s []T, f func(T) U) []U`,
  `type Stack[T any] struct { items []T }`.
- **Ограничения (constraints)** — это интерфейсы, расширенные множествами
  типов: `type Number interface { ~int | ~int64 | ~float64 }`. Тильда `~int`
  означает «любой тип с базовым типом int», то есть и `type Celsius int`.
- **Встроенные ограничения**: `any` (= `interface{}`), `comparable`
  (поддерживает `==`), плюс пакет `golang.org/x/exp/constraints`
  (`Ordered`, `Integer`, `Float`) — для `<` и `>`.
- **Вывод типов** в большинстве случаев позволяет писать `Map(s, f)` без явных
  параметров; при неоднозначности указываются явно: `Map[int, string](...)`.
- **Чего дженерики не умеют** (частые вопросы):
  - **нет методов с параметрами типа** — параметризовать можно тип или
    функцию, но не отдельный метод существующего типа;
  - нет специализации по конкретному типу внутри дженерика (только type switch
    через `any`);
  - нет ограничений на поля структур — только на методы и множества типов;
  - нет «дженериковых» значений в рантайме: `T` нельзя сравнить с типом.
- **Реализация — GC shape stenciling**: компилятор генерирует одну копию кода
  на «форму» типа (указатели делят одну копию), а нужный itab передаётся
  словарём. Практический вывод: дженерики **не всегда быстрее** интерфейсов,
  иногда медленнее — измеряйте.
- **Когда применять**: контейнеры и структуры данных, функции над слайсами и
  картами, устранение дублирования кода, отличающегося только типом. **Когда
  не применять**: если хватает интерфейса с методом, если тип используется
  ровно один раз, ради «красоты».
- **Стандартные дженерик-пакеты**: `slices`, `maps`, `cmp` (Go 1.21+),
  `sync.OnceValue`, `errors.Join`. Знание того, что ручные хелперы больше не
  нужны, — хороший сигнал на интервью.
