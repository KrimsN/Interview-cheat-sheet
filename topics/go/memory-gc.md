# Go: память, стек, куча, сборщик мусора

[🏠 Карта тем по Go](README.md)

## Что нужно знать

- **Escape analysis**: компилятор сам решает, где разместить значение —
  на стеке или в куче. Правило «`new` = куча» неверно. Значение «убегает» в
  кучу, если указатель на него переживает функцию, если размер неизвестен на
  этапе компиляции, если оно кладётся в интерфейс, канал или замыкание,
  переживающее вызов. Смотреть решение: `go build -gcflags='-m -m'`.
- **Стек горутины растёт копированием**: при нехватке рантайм выделяет вдвое
  больший стек и переносит содержимое, поправляя указатели. Поэтому адреса
  локальных переменных нельзя считать стабильными на уровне ассемблера
  (для Go-кода это прозрачно).
- **Аллокатор** — вариант TCMalloc: `mspan` по размерным классам, локальный
  кэш на P (`mcache`) → `mcentral` → `mheap`. Мелкие объекты идут по классам,
  крупные (>32 КБ) — напрямую из кучи.
- **Сборщик мусора**: конкурентный трёхцветный mark-and-sweep, **не
  перемещающий** (non-moving), с write barrier. Работает параллельно с
  программой; **stop-the-world фазы очень короткие** (доли миллисекунды) —
  на них уходит включение/выключение барьеров.
- **Что триггерит цикл GC**: рост кучи относительно живого объёма после
  прошлого цикла (`GOGC`, по умолчанию 100 — то есть цикл при удвоении),
  таймер (раз в 2 минуты), явный `runtime.GC()`.
- **Тюнинг**: `GOGC` (компромисс «память ↔ CPU»), `GOMEMLIMIT` (Go 1.19+) —
  мягкий лимит памяти, критичен в контейнерах: позволяет ставить `GOGC=off`
  и полагаться на лимит, снижая риск OOM-kill.
- **Финализаторы** (`runtime.SetFinalizer`, `runtime.AddCleanup` в новых
  версиях) — знать о существовании; не гарантируют вызов, не заменяют `Close`.
- **Типовые утечки памяти в Go** (не «утечки» в смысле C, а удержание ссылок):
  - подслайс/подстрока удерживает большой backing array;
  - глобальные карты и кэши без вытеснения;
  - утёкшие горутины держат свои стеки и захваченные объекты;
  - незакрытые `time.Ticker`, `http.Response.Body`, `sql.Rows`;
  - `sync.Pool` неправильно использован (хранит крупные объекты вечно —
    на самом деле очищается, но объекты в нём живут до конца цикла).
- **Снижение аллокаций**: преаллокация слайсов и карт, `strings.Builder`,
  переиспользование буферов через `sync.Pool`, избегание лишней укладки в
  интерфейс, значения вместо указателей для маленьких структур (меньше
  давления на GC).
- **Инструменты**: `go test -benchmem` (`allocs/op`), `pprof heap` (inuse_space
  vs alloc_space), `GODEBUG=gctrace=1`, трассировка `go tool trace`.

- [Go FAQ: Stack or heap?](https://go.dev/doc/faq#stack_or_heap) — официальный ответ про escape analysis.
- [Language Mechanics On Stacks And Pointers — Ardan Labs](https://www.ardanlabs.com/blog/2017/05/language-mechanics-on-stacks-and-pointers.html) — серия статей про стеки, escape analysis и профилирование памяти.
