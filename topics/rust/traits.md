# Rust: трейты

[🏠 Карта тем по Rust](README.md)

## Что нужно знать

- **Трейт — это контракт поведения**, ближайший аналог интерфейса, но
  реализация **явная** (`impl Trait for Type`), а не структурная, как в Go, и
  не по факту наличия метода, как duck typing в Python.
- **Реализовать чужой трейт для своего типа и свой трейт для чужого типа
  можно; чужой для чужого — нет.** Это orphan rule (правило сироты), оно же
  coherence: гарантирует, что реализация в программе одна. Обход — newtype.
- **Дефолтные методы** в трейте: расширяют интерфейс без поломки реализаций.
  Так устроены `Iterator` (реализуешь `next`, получаешь сотню методов) и
  расширяющие трейты (`Ext`-трейты).
- **Ассоциированные типы vs параметры типа**: `trait Iterator { type Item; }` —
  один вариант реализации на тип; `trait From<T>` — много реализаций для
  разных `T`. Вопрос «когда что» — классический.
- **Обобщённая диспетчеризация (static) vs трейт-объекты (dynamic)**:
  `impl Trait`/`<T: Trait>` разворачивается на этапе компиляции
  (мономорфизация, инлайнинг, ноль накладных расходов); `&dyn Trait`/
  `Box<dyn Trait>` — таблица виртуальных методов и один экземпляр кода.
  См. [дженерики](generics-monomorphization.md).
- **Object safety (dyn-совместимость)**: метод с обобщёнными параметрами, с
  `Self` в возвращаемом типе или без `self` делает трейт непригодным для
  `dyn`. Отсюда типовая ошибка «the trait cannot be made into an object».
- **Супертрейты** (`trait Ord: Eq`) — требование реализовать другой трейт;
  наследования реализации, как в ООП, нет.
- **Blanket impl**: `impl<T: Display> ToString for T` — реализация для всех
  типов, удовлетворяющих границе. Мощный приём и одновременно источник
  конфликтов когерентности.
- **Маркерные трейты** без методов: `Copy`, `Send`, `Sync`, `Sized`,
  `Unpin` — несут информацию для компилятора, а не поведение.
- **Обобщённые константы и `where`-клаузы**: длинные границы выносят в
  `where`, читаемость важнее краткости.
- **Async-методы в трейтах** (`async fn` в трейте) стабилизированы в Rust 1.75;
  для `dyn`-использования по-прежнему нужен `async-trait` или ручной
  `Pin<Box<dyn Future>>` — актуальный вопрос на собеседовании по async-коду.
